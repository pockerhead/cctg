# Domain: transcript
# NORMATIVE when active — a constraint to satisfy, not a claim for you to audit.

## Invariants
- Path of a session transcript: `~/.claude/projects/<encoded-cwd>/<session-id>.jsonl`. Encoded cwd = path with `:`, `\`, `/`, spaces and `_` replaced by `-` (`C:\Users\user\dev` becomes `C--Users-user-dev`; `_` verified in TASK-004). Prefer `transcript_path` from the hook over re-deriving the path.
- The transcript file may not exist at all: with `CLAUDE_CODE_CHILD_SESSION=1` inherited, Claude Code turns transcript saving off. Missing file is a normal state for `/brief`/`/full`, not a read error.
- Rendering is an ALLOWLIST: only `type: "user"` and `type: "assistant"` records. Real transcripts also contain `attachment` (a third of all records), `atis-latch`, `queue-operation`, `file-history-delta`, `mode`, `permission-mode`, `file-history-snapshot`, `ai-title`, `last-prompt`, `system`, `summary`, `cost-state`; any unknown type is skipped, never an error. `ai-title` is read once by a separate pure function for the topic title. `message.content` is a string (typed prompts, many `isMeta` records) or an array of blocks `text | tool_use | tool_result | thinking | image`; both shapes are real.
- A real `assistant` record almost always carries one content block (subagent records with 2-8 blocks exist, code must handle several); one API response is split over several records sharing `message.id`, and thinking sits in its own record. Renderers must not assume one record = one response.
- The id of a subagent spawned by an `Agent` call is in the result record's top-level `toolUseResult.agentId`; `toolUseResult` is a string, not an object, on error results. `tool_result.content` is a string or an array of `text`/`tool_reference` items; `is_error` is often absent.
- Inbound channel messages (`<channel source=...>` text) land as `user` records with `isMeta: true`. Do not hide every `isMeta` turn: that would hide Telegram-originated prompts.
- The implemented API (TASK-005, `crates/transcript/src/lib.rs`): `parse(&str) -> Vec<Turn>`, `ai_title(&str) -> Option<String>`, `Turn { role, blocks, is_meta, is_sidechain }`, `Block::{Text, ToolUse{id,name,input}, ToolResult{tool_use_id,content,is_error,agent_id}}`. No thinking variant exists; `image` blocks and a BOM-prefixed first line are dropped (accepted).
- Every record has `uuid`, `parentUuid`, `timestamp`, `cwd`, `sessionId`, `gitBranch`, `isSidechain`, `isMeta`. Parse only needed fields with `#[serde(default)]`; unknown records must not fail the parse.
- Subagent transcripts live in `<session-id>/subagents/agent-<agent_id>.jsonl` (plus `.meta.json`), same record format, `isSidechain: true`, `agentId` set. They are NOT duplicated in the parent jsonl. The hub gets this path from `SubagentStop.agent_transcript_path`; constructing it is only a fallback. The library never reads `.meta.json` or any file: hub does IO.
- `.meta.json` always has string `agentType`, `description`, `toolUseId` and int `spawnDepth` (optional: `model`, `parentAgentId`, `stoppedByUser`, ...); `toolUseId`/`agentType`/`description` equal the parent `Agent` call's id/`subagent_type`/`description`. Every parent `Agent` result is `async_launched` with `toolUseResult.agentId`; no parent jsonl contains sidechain records. The first record of a subagent jsonl is the spawn prompt (non-meta string, often >4096) and is never rendered in the block body. A subagent that called `SubagentHandback` also has it in its own jsonl as a `tool_use` with `input.message`.
- Subagent API (TASK-007, `src/subagent.rs`): `parse_subagent_meta(&str)`, `SubagentInput { agent_id, agent_type, meta, report, transcript, last_assistant_message }` -> `Subagent::new` (private fields; a compile_fail doctest guards that hub cannot bypass the order) with `SubagentBody` = Report > finished transcript brief (only when `last_assistant_message` equals its final text) > LastMessage > InProgress > Empty. Parents render with `render_brief_with_subagents`/`render_full_with_subagents`; the embedded body is always brief. Hub must pass `last_assistant_message` from `SubagentStop`, otherwise a lagging transcript can look finished.
- TASK-015: `SubagentInput` also has optional `description` (the parent `Agent` call's, used when the meta has none) and `Subagent::header()` is public (first line of `render`); the struct is not frozen.
- Transcript files are written asynchronously and may lag the turn that just ended; the text of the current turn comes from the hook field `last_assistant_message`, the jsonl is for history.
- `render_brief`: user prompts, final assistant text, one-line tool calls (`Bash: description`, `Edit: file`); `Agent` calls as `↳ <type> <agent_id>` plus subagent summary. `render_full`: adds tool inputs and truncated results, never `thinking`. Subagents always expand in brief form.
- Output is split for Telegram's 4096 limit, counted in UTF-16 code units via `transcript::telegram_len` / `TELEGRAM_TEXT_LIMIT` (conservative under either Telegram rule; hub code reuses them, never `chars().count()`); `split_for_telegram` never cuts a grapheme cluster and drops whitespace-only chunks; above `max_chunks` (default 4) it recommends sending a file.
- `message.stop_reason` is `end_turn` on the final answer and `tool_use` on text that precedes a tool call in main transcripts. In subagent transcripts only the last record of a response carries it; earlier records, and often the final text itself, have `null`. Brief shows `end_turn` text as the answer and, for null/other, text with no tool call before the next prompt; an unfinished tail renders «в работе…» (TASK-006).
- User slash commands (`<command-name>` first for built-ins, `<command-message>` first for skills) render in brief and full as one prompt line `> /name args` and count as a prompt boundary (TASK-020). A local command with no assistant reply (e.g. `/model` at the tail) therefore shows «в работе…»; hub push logic (TASK-016) should not treat that as a live turn.
- Brief hides service records (`<task-notification>`, `<local-command-stdout>`, the post-`/compact` summary `This session is being continued...`, and the other `SERVICE_PREFIXES` in `render.rs`); full shows them.
- `crates/transcript` depends only on `serde`, `serde_json` and `unicode-segmentation` (pinned 1.13.3, CPU-only UAX #29 tables, no transitive deps); `tests/purity.rs` enforces the exact list.
- The crate has no IO/network dependencies: `parse(&str) -> Vec<Turn>`. IO lives in hub.
- Tests are mandatory. Fixtures are anonymized slices of real jsonl from `~/.claude/projects`, stored in `crates/transcript/tests/fixtures/`. Never commit real user ids, tokens or private paths in fixtures.
