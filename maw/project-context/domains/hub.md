# Domain: hub
# NORMATIVE when active — a constraint to satisfy, not a claim for you to audit.

## Invariants
- One hub process per main device. It owns the bot token; the bot is admin in one private supergroup with forum topics enabled.
- A forum topic is a slot `(device, folder, ordinal)`. A new session occupies the first slot of its folder with no live session; a concurrent session gets the next ordinal (`[host] folder #2`). Title `[host] folder · ai-title` (short session id until ai-title appears). Icon via `icon_custom_emoji_id` reflects state: alive / dead / waiting for permission / no channel. Session change inside a slot is rendered as a separator line, never as a per-message prefix. Resume (`claude -p --resume <id>` via the device agent) and handoff (summary from the old session as first prompt of a new one) both stay in the same slot. The `General` topic is dashboard plus commands.
- Subagents and nested `claude -p` runs get NO topic. They render inside the parent topic (`↳ <type> <id>` collapsed block for subagents, `⇣ nested <id>` for nested runs). Nested runs are recognised by the nesting flag sent by the hook.
- Registry: `slot -> (device, folder, ordinal, topic_id, current_session_id?, state)` plus `session_id -> (slot, transcript_path, parent_session_id?)`. Persisted in `registry.json`, reconciled with live agent connections on start.
- Agent transport: TCP, newline-delimited JSON, first message is shared-secret auth. No WebSocket until a browser client exists.
- Telegram client: bare `reqwest` (rustls) behind one `BotApi` module with narrow `#[serde(default)]` structs for the ~11 methods we use (getUpdates long polling, sendMessage, sendDocument, editMessageText, deleteMessage, answerCallbackQuery, createForumTopic, editForumTopic, getForumTopicIconStickers, getChatMember, getMe). Named fallback if typed models start paying for themselves: `frankenstein` (tracks Bot API 10.x). `teloxide` is not used (last release 2025-07, Bot API 9.1; its dispatcher and Throttle are redundant with our registry routing and outbound queue). Decided 2026-09-22.
- Flood control: documented limits are ~1 message/s per chat and 20 messages/min per group, shared by every topic of every session on every device. All sends go through one outbound queue: token bucket, FIFO per topic, permission requests first, edits coalesced, 429 honoured via `retry_after`. Edits and topic mutations have no published numeric limit; serialize them and handle 429.
- Security gate is by `from.id` allowlist, never by chat. Permission Allow/Deny buttons carry `request_id` in callback data and are honoured only from allowlisted users.
- Inbound routing: message in topic goes to the current session of that slot. Dead session: never close the topic; buffer up to 50 messages (drop oldest, warn once), offer a Resume button.
- Local transcripts are read directly from `transcript_path` (works for dead sessions); remote devices serve the file through their agent on request.
- Messages longer than 4096 are split or sent as a file; measure with `transcript::telegram_len` and split with `transcript::split_for_telegram` (see transcript domain).

- Implemented in TASK-008 (`crates/cctg/src/hub/{api,config,updates,scheduler}.rs`, crate is lib+bin): config `CCTG_BOT_TOKEN`, `CCTG_CHAT_ID` (`-100…`), `CCTG_ALLOWED_USER_IDS` (comma-separated, required), read from `./.env` or `--env-file` into memory WITHOUT `set_var` (process env wins; child processes never inherit the token). All outbound Bot API calls go through the one `Scheduler` actor: permission prompts first across topics but never ahead of an earlier job of their own topic, FIFO within a topic, edit coalescing, a separate unmetered topic-mutation lane, bounded fairness (a ready message after 4 unmetered jobs), ≤20 metered sends per any 60 s, any 429 pauses the whole queue for max(retry_after, 1 s). Updates are parsed per item from `Vec<Value>`; unknown types/fields never stop the poll and the offset always advances.
- TASK-009: `getUpdates` offset persisted in `<CCTG_STATE_DIR|.cctg>/offset` (temp + fsync + rename via `spawn_blocking`), saved before a batch is handled (at most once). `/brief [n] [prefix]` and `/full [n] [prefix]` run on one sequential command worker; `n` = last n prompts (`transcript::last_prompts`, defaults brief 3, full 1); the reply text equals the library output exactly; 400 too-long switches the undelivered tail to one document once; any other delivery failure sends one short notice. Transcript choice goes through `hub::sessions::TranscriptLocator::locate(thread_id, prefix)`; the TASK-009 impl `ProjectsDir` scans `<CCTG_PROJECTS_DIR|~/.claude/projects>/<project>/<uuid>.jsonl` (direct children only, never subagents, 256 MiB read cap). TASK-011 replaces the impl, not the trait.
- TASK-010: wire contracts in `crates/cctg/src/wire.rs` (`VERSION = 1`; every agent-link line carries `v` and `type`; `hello{secret}` (constant-time via `subtle`) then `register` before anything else; `MAX_LINE` 1 MiB). Each connection has one reader task feeding an mpsc (never read inside `select!`), every write capped at 5 s. Hub ingress `hub/ingress.rs`: `serve_agents` (TCP, `CCTG_AGENT_LISTEN`, default `127.0.0.1:47291`) and `serve_hooks` (hand-rolled strict HTTP/1.1, `POST /v1/hook`, Bearer secret, `CCTG_HOOK_LISTEN`, default `127.0.0.1:47292`); non-loopback only by explicit `ip:port` with a warning. Hook events are deduplicated by a hook-minted `event_id` (4096 ids / 10 min), remembered only after a successful hand-off. `agent::spawn` reconnects with equal-jitter backoff 250 ms..30 s and re-registers; `hook::post` is one-shot. `CCTG_HUB_SECRET` (16+ visible ASCII) is required; the hub refuses to start without it. Until TASK-011, `drain_ingress` consumes events.
- TASK-011: `hub/registry.rs` (pure model) + `hub/slots.rs` (the only owner of the registry, an actor that never awaits Telegram or the scheduler queue: jobs go to a dispatch task over an unbounded channel). `registry.json` in `<CCTG_STATE_DIR|.cctg>` (temp + fsync + rename from the latest snapshot); an unparsable, foreign-version or duplicate-topic file stops the hub. Slot identity `(host, folder_key(cwd), ordinal)`; `folder_key` is lexical (strip `\\?\`, `\` -> `/`, drop trailing `/`, case-fold drive-letter and UNC paths). The hub never adopts a session without a SessionStart (agents of unknown sessions wait; unknown Stop/UserPromptSubmit are ignored). Nesting = `SessionStart.parent_claude_pid` looked up in the persisted `pids` map `<host>/<pid> -> session`; any `Some` means nested; a nested start of a known top-level session keeps its kind and slot. `SessionEnd.claude_pid` (optional) that differs from the pid of the session's live run is ignored (the end of a nested `--resume`). The `pids` slot transfer applies only to SessionEnd(reason=clear) -> SessionStart(source=clear) from the same host+pid within 60 s; otherwise first free slot. At most one topic call per slot in flight; the session separator stays in `registry.json` until Telegram accepted it. TOPIC_NOT_MODIFIED = applied; TOPIC_ID_INVALID / thread not found = one replacement topic. Icons (alive ⚡️ 5312016608254762256, dead 🏁 5408906741125490282, waiting ❓ 5377316857231450742, no channel 👀 5357121491508928442) are validated against `getForumTopicIconStickers` at start; a lookup error stops the hub, a missing id is replaced from the offered set. Known limitations: a lost createForumTopic answer can leave an orphan topic; a permanently failing separator blocks name/icon edits of that slot; a session continuing from another folder keeps its old slot alive.
- TASK-021: only `/brief` and `/full` (optionally `@bot`) are commands; every other allowlisted text in a topic, including `/compact` or `/path`, is routed via `Control::Message` to the slots actor, which `try_send`s `HubMsg::Inbound` (meta `chat_id`, `message_id`, `thread_id`, `reply_to_message_id` only for an explicit reply) to the agent of the slot's live top-level current session. `AgentMsg::Reply` is sent only for the live top-level current session of its slot (late replies of ended sessions and stale duplicate connections are dropped), split with `split_for_telegram` (>4 chunks -> one document), handed to the dispatch task; at most 256 sends pending, overflow drops the reply with one warn per episode. A slot gets each fixed notice (offline, text-only) at most once per 60 s; a delivered message re-arms the offline notice. General and non-slot topics are silent. On `/clear`, only the newest connection of the claude pid follows the new session. Unknown slash commands are never logged.
- TASK-014 (`hub/permissions.rs` + slots): a `permission_request` becomes a message in the requesting session's own slot topic with Allow/Deny buttons (`callback_data` = `allow:<id>` / `deny:<id>`); a press is resolved by the Telegram message_id plus the id, so equal 5-letter ids of two sessions never mix. The first press fixes the answer; the verdict carries a `verdict_id` and counts as delivered only after the agent's `permission_ack` (resent on reconnect, retry tick or repeat press; the pid fallback is limited to the prompt's session); later presses get "Уже решено". After the ack the message is edited with the decision and an explicit empty `inline_keyboard` (edit retried, `message is not modified` = applied). Prompts of a known ended or pruned session are never shown and open ones are closed as "Сессия завершилась"; a session's waiting icon is derived from its active prompts. The prompt book holds 256; when full it forgets finished prompts first, else expires the oldest open one visibly. Agent frames are attributed to the session the connection was bound to when the frame was read. Terminal answers are invisible to the hub.
- TASK-022 (slots): a `Stop` hook with a non-blank `last_assistant_message` sends that text to the slot topic when the session is live, top-level and the slot's current session (`current_slot`, the same predicate as `Reply`) and the slot has a topic; no agent connection needed. It shares `send_text` with `Reply` (split_for_telegram, >4 parts as `answer-<short>.txt`, the 256 pending-send cap, dispatch task). Every turn is mirrored, terminal turns included; no dedup, so a user's own blocking Stop hook (`stop_hook_active`) can give several answers per turn, and a nested `claude -p --resume <id>` of a top-level session answers into that session's topic.

## Risk lessons
- 2026-09-22: bot needs admin right `can_manage_topics` for createForumTopic; check via `getChatMember` at hub start. Bot API chat id is `-100` + web-client id. Bot-admin CAN post into a closed topic, users cannot: never close a dead session's topic. Service messages `forum_topic_*` arrive as `message` updates and must be ignored. Text limit is exactly 4096. `icon_custom_emoji_id` is editable, `icon_color` is not. Service messages for rename/icon change are deleted by the hub via `deleteMessage` (message_id from getUpdates); the `forum_topic_created` one cannot be deleted (it is the topic root). See CLAUDE.md "Telegram Bot API".
- 2026-09-23 (TASK-008): `reqwest::Error` Display/Debug include the request URL, which contains the bot token. Every reqwest error leaves `BotApi` through `without_url()`; responses are decoded from bytes by hand, never via `Response::json`/`error_for_status`. A `dotenvy::Error` Display can echo the rest of the env file (token included): map it to a fixed-text error, never wrap it with `anyhow::Context`.
- 2026-09-23 (TASK-008): tests that capture `tracing` output must live in their own integration test binary (parallel tests race on callsite registration: 56/100 flaky before isolation) and negative log assertions must use `.without_time()` (ids like 1001 appeared inside timestamp fractions, ~0.5% flake).

- 2026-09-23 (TASK-009): encoded-cwd project directory names (`C--Users-<name>-...`) are private paths: never log them and never send them to Telegram (ambiguous-prefix candidates show short id, age and ai-title only).
- 2026-09-23 (TASK-009): after a week without updates the next Bot API `update_id` is random (can be below the last offset) and updates live at most 24 h. Next offset = `max(update_id in batch) + 1`, never `max(old, ...)`; a persisted offset older than 24 h is ignored on load (go-telegram-bot-api #156).

- 2026-09-23 (TASK-010): serde_json error texts quote the offending value, which on the agent link or hook endpoint can be the shared secret: map decode errors to fixed-text variants and drop the serde error.
- 2026-09-23 (TASK-010): tokio `read_until`/`read_line` inside a `select!` branch loses the partially read line when another branch wins (silent message loss, reproduced on both ends). Read in a dedicated task per connection and forward frames over an mpsc.
- 2026-09-23 (TASK-010): an early HTTP answer (401) survives only if the server drains the rest of the largest in-contract request (`MAX_HEAD + MAX_HOOK_BODY`, fixed 4 KiB buffer, 250 ms cap) before closing; a 64 KiB drain lost the 401 to a TCP reset on Windows. "Strict HTTP" means the RFC grammar: exactly `HTTP/1.1`, `tchar` field names, no CTL except HTAB in values, OWS = SP/HTAB only (not `str::trim`), one all-digit Content-Length, no Transfer-Encoding, duplicate Authorization = 400; the hook client accepts only a complete `HTTP/1.1 NNN ...\r\n` status line.
- 2026-09-23 (TASK-010 QA): both link ends cap writes at 5 s; if the hub-side consumer of ingress events stalls longer (e.g. awaiting Telegram `retry_after`), the agent's write times out, it reconnects and the message being written is lost. Never do Telegram I/O inline on the ingress event channel (TASK-011+): hand off to the scheduler and keep draining.

- 2026-09-23 (TASK-011 QA): tests that drive `Slots` through the real `Scheduler` need a fast `BucketConfig` (large capacity, `min_gap` 0) or must wait longer than `min_gap`; timing bounds in actor tests should be generous (a stall shows up as a hang anyway).

- 2026-09-23 (TASK-021): in a forum topic Telegram sets `reply_to_message` on every message to the topic root (`message_id == message_thread_id`); only another id is an explicit reply.

- 2026-09-23 (TASK-014): wire compatibility: agents live as long as their Claude Code session and survive a hub upgrade, and `check_version` rejects any other version, so never bump `wire::VERSION` for an additive change: add optional fields (`#[serde(default)]`, skipped when empty) and gate new message types behind a capability announced in `Register` (e.g. `verdict_ack`).
- 2026-09-23 (TASK-014): hub and agent events arrive on independent channels; a queued agent frame can be processed after a hook that ended its session. Every agent-frame handler re-checks the session's state at processing time.
