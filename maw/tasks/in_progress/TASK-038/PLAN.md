## 3. Подход

Один вызов `AskUserQuestion` = один запрос хука = одно сообщение в теме слота сессии.

1. **Хук** `cctg hook PreToolUse` с matcher `AskUserQuestion` (отдельная синхронная группа, `timeout: 330`, `statusMessage`). В `hook::run` вход с `tool_name == AskUserQuestion` уходит в `question`: `build_question` проверяет форму (1-4 вопроса, у каждого непустой уникальный текст, 1-8 вариантов с непустым `label`; не внутри субагента; без готовых `answers`), режет тексты для hub и держит исходный `tool_input`. POST на новый `/v1/question`, ждёт до 310 с. На 200 печатает `{"hookSpecificOutput":{"hookEventName":"PreToolUse","permissionDecision":"allow","permissionDecisionReason":"Answered in Telegram","updatedInput":<исходный tool_input + answers>}}`; ключи `answers` берутся из исходного `tool_input`, hub возвращает ответы по индексу. 204, 404 (старый hub), ошибка, таймаут: пустой stdout, выход 0, терминальный диалог как обычно. В spool не пишется.
2. **Ingress**: `Route::Question` для `QUESTION_PATH = "/v1/question"`; `serve_hooks_and_asks(listener, secret, events, permissions, questions)`; `serve_hooks`/`serve_hooks_and_permissions` без изменений снаружи (на новый путь 404). `question_request` повторяет `permission_request` (семафор тот же, 16 мест на оба вида), общий `select!` вынесен в `wait_for`. Cap 305 с.
3. **Hub**: новый чистый модуль `hub/questions.rs` (как `permissions.rs`): `Ask` (вопросы, текущий шаг, ответы, отметки multiSelect, режим «жду текст», состояние, message_id, версии для правок) и книга `Asks` (≤16). Кнопки `ask:<id>:<вопрос>:<o N|x|d|t>` ≤ 16 байт; id — пять букв как у hook-промптов. Один вопрос на экран; ответ переводит сообщение к следующему вопросу; после последнего сообщение правится в итог без кнопок, ответы уходят хуку. multiSelect: отметки ☐/☑ и «✅ Готово» (пустой выбор не принимается); свой текст: «✏️ Другое» → следующий текст в теме, либо reply на сообщение вопроса в любой момент; для multiSelect свой текст идёт после отмеченных, через `", "`. «⌨ В терминале» отпускает хук сразу.
4. **Slots**: `question_asks()`, ветка `select!`, `check_questions` в `pump` (хук ушёл → `Gone`, время → `Expired`, сессия не живая top-level → `Closed`; закончившийся вопрос отдаёт хуку `Some(answers)` или `None`; вопрос без долгов забывается), `send_questions` на permission-полосе, `send_question_edits` (одна правка в полёте, версия, повтор на retry tick, 5 попыток), нажатия в `press` до `allow:`/`deny:`, перехват текста в начале `on_topic_message` (до консоли, склейки TASK-048 и буфера: ответ в сессию не уходит), иконка «ждёт» = промпты или открытый вопрос, остановка hub = «без решения».
5. **Без двойных кнопок**: канальный `permission_request` и `PermissionRequest`-хук с `tool_name == AskUserQuestion` не получают Allow/Deny (хук даже не ходит в hub: `Skip` в `build_permission`; hub дополнительно отсекает старые хуки и канал). Это безопасно при любом исходе (c): вопрос отвечается либо кнопками вопроса, либо в терминале.
6. **Сроки**: hub 300 с (`slots::QUESTION_WAIT`, `Options::question_wait`), ingress 305, хук 310, settings 330. Выбор длинного ожидания: удалённый пользователь — основной сценарий cctg, после срока вопрос отвечается только в терминале; терминальному пользователю `statusMessage` говорит, что вопрос в Telegram (и Esc, если проба (d) это подтвердит). Окончательное число — открытый вопрос 1.
7. **ExitPlanMode не входит**: одобрение плана — отдельный диалог с другими вариантами (одобрить с авто-правками / с ручными / продолжить планирование с отзывом); как `allow`/`deny` хука ложатся на них и какой режим получается, в доках нет; план часто длиннее 4096 символов; и одобрение плана может уже приходить в канал как `permission_request` (проба (e)). Ничего в этой задаче поведение `ExitPlanMode` не меняет. Предлагается отдельная задача по итогам (e).

Отклонённые варианты (записаны в `log.jsonl`): расширить `/v1/permission` вопросным вариантом; отдельное имя события `cctg hook AskUserQuestion`; короткое ожидание 60-90 с; `ForceReply` для «Другое» (лишнее сообщение и зависимость от клиента; reply и «следующий текст» закрывают то же).

## 7. Риски

- Ждущий хук держит ход до 5 минут, если пользователь у терминала и не видит Telegram: терминал показывает только `statusMessage`. Смягчение: текст `statusMessage`, кнопка «В терминале», срок настраивается (открытый вопрос 1). Если Esc (d) не отпускает хук, человеку у терминала остаётся ждать или ответить в Telegram.
- После срока вопрос отвечается только в терминале; удалённый пользователь остаётся с сессией, ждущей диалога. Ответ кнопкой после `Expired` получает «Вопрос уже закрыт». Ввод ответа клавишами через агента (TASK-044) — возможное продолжение, не здесь.
- Ключи `answers` — точные тексты вопросов из `tool_input`; два одинаковых текста в одном вызове не отвечаются из Telegram (Skip → терминал).
- Хук на `PreToolUse` без matcher у пользователя (свой хук `deny`/`ask`) побеждает наш `allow` по приоритету `deny > defer > ask > allow`: тогда ответ из Telegram пропадает, диалог/отказ как решил чужой хук. Отражать не будем.
- Перехват текста: после «Другое» следующий текст в теме (не пересланный, не файл) уйдёт ответом, даже если пользователь хотел написать сессии. Смягчение: подсказка в сообщении и в ответе на кнопку; вопрос закрыт — перехвата нет. Команды `!`/`/` после «Другое» тоже станут ответом (осознанно: так проще и предсказуемее).
- Hub упал/перезапустился, пока хук ждёт: соединение рвётся → хук без решения → терминальный диалог; сообщение вопроса в Telegram остаётся с кнопками (книга в памяти, как у промптов), нажатие отвечает «Вопрос уже закрыт». Не сохраняем в `registry.json` сознательно.
- Общий семафор 16 мест на permission и question хуки: поток permission-хуков может занять все места, тогда вопрос сразу без решения (терминал). Практически недостижимо.
- `statusMessage` и `timeout` в `install.sh`: русский текст в heredoc (файл уже UTF-8); существующие установки получают хук только после повторного `install.sh` и перезапуска сессии (TASK-040: `--settings` не перечитывается).
- Конфликт слияния с TASK-052 (ветка `fix/install-path-channel-off`, коммит d5e38de ещё не в main: `hub/slots.rs` +212, `hub/mod.rs`, `install.sh` +150, `tests/install_e2e.rs`): наши правки точечные (импорты, поля, `run`, `pump`, `on_topic_message`, `on_permission_*`, тестовый `Rig`, одна строка `PreToolUse` в heredoc `install.sh`). Если TASK-052 сольётся раньше, эталон пересобирается против нового `main` (`build_patch.py <ws> <новый main>`), `verify_hashes.sh` тогда сверяет новые хеши; вручную — обычный merge по этим местам.
- Общий `CARGO_TARGET_DIR`: e2e запускают `cctg.exe` из общего target; параллельная сборка другого дерева может подменить бинарь между сборкой и тестом. При странном падении e2e — пересобрать и повторить.
