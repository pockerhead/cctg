## 0. Изменения задачи по ходу планирования (сообщения оркестратора)

1. **Один `install.sh`, без `install.ps1`** (решение пользователя). На Windows скрипт идёт в Git Bash: `uname -s` = `MINGW*|MSYS*|CYGWIN*`, качается `.exe`, пишутся обе обёртки (sh и `.cmd`), пути в JSON в виде `C:/...` (`cygpath -m`), права файлов не важны. Windows e2e гоняет тот же скрипт в Git Bash. Уточнение по фактам: документация Claude Code (https://code.claude.com/docs/en/setup, раздел «Set up on Windows») называет Git for Windows **необязательным**: без него Claude Code берёт PowerShell. Но cctg без Git Bash не работает всё равно: хуки cctg записаны в shell-форме (`"C:/.../cctg.exe" hook X`), а хук без Git Bash по умолчанию идёт через PowerShell (https://code.claude.com/docs/en/hooks, поле `shell`), где такая строка не вызов программы. Поэтому Git for Windows это требование cctg, README даёт одну строку `winget install Git.Git`.
2. **Установщик ставит Claude Code, если его нет** (решение пользователя). Команды сверены с https://code.claude.com/docs/en/setup (2026-09-25): `curl -fsSL https://claude.ai/install.sh | bash` (macOS, Linux, WSL) и `irm https://claude.ai/install.ps1 | iex` (PowerShell; из Git Bash как `powershell -NoProfile -Command "irm https://claude.ai/install.ps1 | iex"`). Ставит в `~/.local/bin/claude` (Windows `%USERPROFILE%\.local\bin\claude.exe`), PATH пользователь добавляет сам (https://code.claude.com/docs/en/troubleshoot-install, «Verify your PATH»). Скрипт спрашивает (или `--yes`), скрипт Anthropic не копируется и не зеркалируется. Тесты подменяют его заглушкой (`curl` с перехватом только `https://claude.ai/*`, `powershell` на Windows) и ничего не качают.
3. **`install.sh --hub`: hub на сервере** (решение пользователя). Входит в этот план и в эталон (шаг 3.3). `/join` в General и `--hub --local` **предлагаю вынести** (раздел 6, вопрос 1): `/join` с общим секретом переделывается задачей TASK-045 (коды), а `--local` требует автозапуска hub на каждой ОС, это отдельный дизайн. Черновик обоих в разделе 7, чтобы следующий planner начал не с нуля.
4. Диалог development channels отвечает `cctg run` на каждом старте (main 12b9bd4), в установщике для этого ничего нет. Факт по коду: `keys::visible_lines` есть только на Windows (`crates/cctg/src/keys.rs:455-458` на Unix `None`), и в mintty (окно Git Bash) консоли нет; README это говорит.
5. Одноразовые коды и секреты устройств: TASK-045 (уже заведена, `maw/tasks/pending/TASK-045`), в follow-ups.

## 2. Approach

1. **Один POSIX `install.sh` в корне**, тело в функции `main`, вызов последней строкой (обрыв `curl | sh` ничего не выполняет; приём rustup: https://www.arp242.net/curl-to-sh.html). `LC_ALL=C`, `set -eu`. Режимы: клиент (по умолчанию), `--uninstall`, `--hub`, `--hub --uninstall`.
2. **Раскладка клиента** (решение: стабильный путь + файлы cctg отдельно от файлов Claude Code):
   - `~/.cctg/bin/cctg[.exe]`: один стабильный путь во всех конфигах. Обновление кладёт файл на тот же путь: Unix `mv -f` (атомарно, работающие процессы держат старый inode), Windows сначала `cctg.exe` -> `cctg.old.exe` (запущенный exe переименовать можно, как у `cctg deploy`). Работающие сессии получают новую сборку по «⬆️ Обновить» (hand-over shim-а), хуки со следующего события. Отвергнуто: папки версий + symlink (на Windows symlink требует прав, shim и так следит за одним путём).
   - `~/.cctg/claude/{mcp.json,settings.json}`, передаются обёрткой (`--mcp-config`, `--settings`). `~/.claude/settings.json` и `~/.claude.json` не пишутся никогда. Отвергнуто: `claude mcp add --scope user` (пишет в `~/.claude.json`, сервер появляется в каждой сессии, channel.md risk lesson TASK-004) и слияние хуков в настройки пользователя.
   - `~/.local/bin/claude-cctg` (+ `claude-cctg.cmd` на Windows): туда же ставит `claude` официальный установщик, так что папка обычно уже в PATH; если нет, скрипт печатает подсказку и rc-файлы не трогает. Порядок аргументов: `cctg run -- --mcp-config M --dangerously-load-development-channels server:cctg --settings S "$@"`: `--settings` берёт одно значение (`claude --help` 2.1.282: `--settings <file-or-json>`, `--mcp-config <configs...>`), поэтому промпт пользователя остаётся промптом. `--debug-file` как в ручной обёртке не пишется (лог без ротации).
   - `~/.cctg/device.env`: ключи `CCTG_HUB_SECRET`, `CCTG_HUB_AGENT_ADDR`, `CCTG_HUB_HOOK_ADDR`, `CCTG_HUB_CERT_SHA256` (управляемые); прочие строки файла сохраняются; без нового значения старая строка остаётся как была (секрет не надо разбирать). Значения в одинарных кавычках с `'` -> `'\''` (для dotenvy буквально, `$` не раскрывается). Режим 600 (umask 077). На macOS, если `CCTG_HOST` нет, дописывается `CCTG_HOST=<scutil --get LocalHostName | hostname -s>` (иначе тема `[unknown]`, см. Understanding; правка в Rust это TASK-044).
   - Файл пишется, только если байты изменились (`put`: temp + `cmp` + `mv`), иначе mtime `settings.json` меняется и «Обновить» перезапускает claude без причины.
   - Чужой файл на месте обёртки (ручная обёртка этой машины) переносится один раз в `<имя>.before-cctg-install`; `--uninstall` удаляет только файлы с меткой `cctg-install`.
3. **Бинарник**: `curl` (только он: официальный установщик Claude Code требует его же; wget отвергнут, его ветку нечем проверить в CI), `--proto =https --proto-redir =https --tlsv1.2`, `https://github.com/pockerhead/cctg/releases/latest/download/<ассет>` (шаблон GitHub: https://docs.github.com/en/repositories/releasing-projects-on-github/linking-to-releases) или `releases/download/<тег>/` с `--version`. `SHA256SUMS` того же релиза, сверка `sha256sum`/`shasum -a 256`, несовпадение: ничего не ставится. Новый файл проверяется запуском `--version` (ответ начинается с `cctg `). Ассеты `cctg-x86_64-pc-windows-msvc.exe`, `cctg-x86_64-unknown-linux-musl`, `cctg-aarch64-apple-darwin` **без версии в имени**: правка `release.yml` 035 (иначе `latest/download` не работает; отвергнут поиск тега через GitHub API: лимит запросов и JSON в sh). macOS: `uname -m` под Rosetta даёт x86_64, скрипт смотрит `sysctl hw.optional.arm64`; ad-hoc подпись ставит линкер, а curl не ставит quarantine, поэтому Gatekeeper бинарник не останавливает (https://users.rust-lang.org/t/distributing-cli-apps-on-macos/70223). `CCTG_INSTALL_BASE_URL` для зеркала и тестов (http только на loopback, как `CCTG_BOT_API_URL` у hub). `--from-source`: `cargo build --release --locked -p cctg` в клоне (папка скрипта, при `curl | sh` текущая папка), учитывает `CARGO_TARGET_DIR`. Это же путь, пока релизов нет.
4. **Секрет не печатается**: из `CCTG_HUB_SECRET` (сразу `unset`, чтобы ни `cctg doctor`, ни установщик Claude, ни cargo его не унаследовали, и doctor проверял файл, как его прочитают сессии), `--secret-file` или скрытый ввод с `/dev/tty` (`stty -echo`, восстановление в `trap`); флага с самим секретом нет (argv видно в `ps`, https://smallstep.com/blog/command-line-secrets/). Вопросы идут через `/dev/tty` (stdin занят скриптом при `curl | sh`); без терминала или с `--yes` вопросов нет, нужное берётся из флагов и уже записанного `device.env`.
5. **`cctg doctor`** (новый модуль, решение пользователя «doctor остаётся в бинарнике»): грузит `DeviceConfig`, пишет по строке на секрет, pin, агентский канал (TCP/TLS connect) и хуки: новый маршрут hub `POST /v1/ping` (с секретом, без тела, 204, ничего не делает, hub пишет только debug). 401: секрет не тот; 404: hub старше этой задачи (маршрута нет, 404 он отдаёт до проверки секрета), считается «доступен, секрет не проверен». Секрет не печатается. Отвергнуто: слать фейковое событие хука или `hello` в агентский канал (hub пишет warning или действует).
6. **`--hub`**: Docker Engine + compose plugin + openssl. Папка `~/cctg-hub` (`--dir`). `compose.yml`/`compose.host.yml` из клона (`deploy/`) или raw GitHub того же ref (`CCTG_INSTALL_RAW_URL` для тестов). `hub.env` (600): токен (`CCTG_BOT_TOKEN` или скрытый ввод), `--chat-id`, `--users`, `--proxy` -> `HTTPS_PROXY`, секрет генерируется (`od -An -N24 -tx1 /dev/urandom`, 48 hex) и дальше не меняется; уже записанные значения остаются. `.env` рядом: `COMPOSE_FILE=compose.yml[:compose.host.yml]` (второй, если прокси на `127.0.0.1`/`localhost` хоста), так ручные `docker compose pull && up -d` из `docs/remote-hub.md` видят тот же набор. Сертификат (если нет): `openssl ecparam -name prime256v1 -genkey -noout` + `openssl req -x509 -new -days 3650 -subj /CN=cctg-hub` (пара команд работает и в OpenSSL, и в LibreSSL macOS; SEC1-ключ hub читает: тест грузит его `cctg::tls::Acceptor::from_files`). Ключ: root -> `chown 10001` + 600, иначе 644 с предупреждением. Pin из `openssl x509 -fingerprint -sha256`. `docker compose pull hub` + `up -d --force-recreate hub`, потом ждать в `docker compose logs --since <старт> hub` строку `hub started, polling` (значит, токен, группа и права тем проверены самим hub) или `Error: ` (показать 20 строк лога, выйти с ошибкой), до 120 с. В конце одна строка для клиентов: `curl -fsSL https://raw.githubusercontent.com/pockerhead/cctg/main/install.sh | CCTG_HUB_SECRET='<секрет>' sh -s -- --hub-host <адрес> --pin <hex>` (секрет в переменной окружения, не в argv; это единственное место, где скрипт печатает секрет, по решению пользователя; TASK-045 заменит его кодом). `--hub --uninstall`: `docker compose down`, удаляет compose-файлы и `.env`, `hub.env`, `tls/` и том состояния оставляет и говорит об этом.
7. **Тесты**: `crates/cctg/tests/install_e2e.rs`, Rust integration test, который скармливает `install.sh` в `sh -s --` (Windows: Git Bash через `cctg::statusline::git_bash`), как `curl | sh`. Локальный HTTP-сервер релиза (этот же `cctg` под именем ассета ОС + `SHA256SUMS`), настоящий hook endpoint hub (`cctg::hub::ingress::serve_hooks`) для `cctg doctor`, заглушки в начале PATH: `claude`, `curl` (перехват только `https://claude.ai/*`), `powershell`, `docker`, `cargo`. Каждый прогон со своим HOME через `common::isolate` (правило TASK-042). CI: на ubuntu и windows тест идёт в `cargo test --workspace` job-а `test`; новый job `install-macos` (`macos-15`, Apple Silicon) гоняет только этот тест; `shellcheck --shell=sh install.sh` на Linux. Отвергнуто: bats или python-обвязка (второй раннер и нет доступа к настоящему endpoint).

## 3. Steps

Порядок: 3.1 (hub ping) -> 3.2 (doctor) -> 3.3 (install.sh) -> 3.4 (e2e) -> 3.5 (CI, релиз) -> 3.6 (доки). Проверка после 3.1-3.2: `cargo test -p cctg --lib -- ingress::tests::a_ping doctor::`; после 3.4: `cargo test -p cctg --test install_e2e`.

### 3.1 Маршрут `/v1/ping` на hub
- `crates/cctg/src/wire.rs` после `HOOK_PATH` (`:44`): `pub const PING_PATH: &str = "/v1/ping";` с doc (204 с секретом, 401 без, 404 у старого hub). `VERSION` не растёт: это новый маршрут HTTP, не сообщение канала.
- `crates/cctg/src/hub/ingress.rs`: импорт `PING_PATH`; `enum Route` (`:657`) + `Ping`; разбор цели (`:707`) `PING_PATH => Route::Ping`; `hook_request` (`:480`) ветка `Ok(Ok((Route::Ping, _))) => { debug!(%peer, "ping answered"); Status::NoContent }` (204 не пишет warning). Секрет и длину проверяет существующий `read_request`, `Content-Length: 0` обязателен (иначе 411).
- Тест `a_ping_checks_the_secret_and_is_no_event` рядом с тестами хуков: 204 с секретом, 401 с чужим, `hook::ping` даёт `Ok`, событий нет.

### 3.2 `cctg doctor`
- `crates/cctg/src/hook.rs` (`post` `:634-670`): тело запроса выносится в приватный `exchange(addr, path, secret, body, timeout) -> Result<u16, PostError>`; `post` = `exchange(HOOK_PATH, ...)` и `204 => Ok`; новый `pub async fn ping(addr, secret, timeout)` = `exchange(PING_PATH, пустое тело)`. Поведение `post` не меняется (те же заголовки, таймаут, строгий разбор статуса).
- `crates/cctg/src/doctor.rs` (новый, `lib.rs` `pub mod doctor;`): `TIMEOUT` 5 с на проверку; `run() -> i32` печатает строки `check` в stdout, код 0/1; `check(&DeviceConfig, timeout) -> Report { lines, ok }`: версия (`client::LONG_VERSION`), `secret: set` или `ConfigProblem`, pin (нет/есть/ошибка), `agent link <addr>` (`config.hub(addr)` -> connect с таймаутом, `ConfigProblem` как текст), `hooks <addr>` через `hook::ping` (401 -> «the hub rejected the secret», 404 -> «reachable; this hub is older and cannot check the secret», ok=true). ## 5. Risk areas

- **Linux и macOS не прогнаны здесь.** Docker и WSL запрещены, Mac нет. `install.sh` на dash (Ubuntu `sh`) и на bash 3.2 (macOS `sh`) проверит только CI; конструкции только POSIX (`bash --posix -n` чисто), но dash строже (например `local` не используется, `$(( ))` есть в POSIX). ShellCheck в CI.
- **macOS сборка crate ни разу не делалась.** Job `install-macos` и релизный `macos` первыми это увидят; код с `cfg(windows)` и `/proc` должен собираться, но `aws-lc-sys` и прочее на macOS не проверены. Если `install-macos` красный из-за самого cctg (не скрипта), это вопрос TASK-044.
- **Git Bash в разных окнах.** `stty -echo` в mintty и в Windows Terminal (ConPTY) работает, в старом conhost без pty скрипт откажется прятать ввод и попросит `CCTG_HUB_SECRET`/`--secret-file`. Живьём не проверено (здесь нет терминала).
- **Официальный установщик Claude** может поменять адрес или поведение (например, не добавить `~/.local/bin` в PATH): скрипт после него ищет `claude` в PATH и в `~/.local/bin`, а при неудаче только предупреждает.
- **Строка клиента с секретом** (`--hub`) оседает в истории терминала и чата. Смягчение: предупреждение в выводе и README; решение: TASK-045.
- **Приватный пакет GHCR**: `docker compose pull` падает, пока пакет не публичный или нет `docker login ghcr.io` (вопрос 3 плана 035); сообщение об ошибке это называет.
- **`--force-recreate`** перезапускает hub при каждом повторе `--hub`, даже без нового образа: агенты переподключатся, хуки на эти секунды в спул.
- **Ключ hub при запуске не от root** получает режим 644 (контейнер с uid 10001 иначе его не прочтёт); вывод об этом говорит.
- **`cctg.old.exe` на Windows** остаётся, пока работают сессии со старой сборкой; следующая установка или `--uninstall` удаляют его, когда он свободен (MSYS `rm` занятого файла может «удалить» его в корзину, это нормально).
- **Эта машина**: первый запуск установщика здесь перенесёт ручные обёртки в `.before-cctg-install`, заменит `~/.cctg/bin/cctg.exe` (тот же файл запускает supervisor hub) и оставит `~/.cctg/poc` как есть. Делать только после переезда hub на сервер.
- **Разные версии скрипта и бинарника**: `curl .../main/install.sh` + `releases/latest`. Если main добавит событие хука раньше тега, старый бинарник ответит на незнакомое событие `cctg hook: ...` и выйдет с 0 (хуки никогда не падают), вреда нет.
