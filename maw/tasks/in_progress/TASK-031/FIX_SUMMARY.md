# TASK-031 FIX_SUMMARY (fixer)

Code commit `88536e4` on `feature/cctg-install`. Self-checks are in `scratch/fixer/`.

## Preflight: the review claim that would break working code

The orchestrator's minor "TLS key mode 600" follows review nit `install.sh:727-732`. Applied as written (`chmod 600` when not root), it breaks the hub. The image runs as `USER 10001` (Dockerfile) and `compose.yml` mounts `./tls:/tls:ro`. A key that belongs to the host user with mode 600 cannot be read in the container, so the hub never starts. The code as it is (644 plus a printed note, and `chown 10001` + 600 only as root) is correct. I skipped this item (see Skipped).

## 2. Skipped

- **TLS key mode 600 (review nit, orchestrator minor).** Applied as written it makes the hub unable to read its key (uid 10001, read-only mount; see Preflight). The review's root-free alternative is `docker run --user 0 ... chown 10001`. That depends on Docker Desktop and rootless uid mapping, which I cannot test here. It would also make the next non-root re-run's `chmod` fail under `set -e`. The current note printed to the user stays. Logged as a decision.
- **Drop the "(in use?)" branch.** It is not dead code. On Linux and macOS, `rm -f` fails on a file in a directory the user cannot write (for example a root-owned `~/.cctg/bin` after a `sudo` run), and then this branch reports it. Only the MSYS running-exe case never reaches it.
- **Stale `*.tmp` after an interrupted run, `[Y/n]` taking `Yes`, `is_loopback` of `127.0.0.1.nip.io`, the `--strict-mcp-config` note, the `install.ps1` wording, `hub.env.example` from `main`.** These are review nits outside the orchestrator's scope. The orchestrator already decided the last three in OPEN_DECISIONS or they belong to TASK-035 docs.
- **`check_paths` with `$`/`%` test.** It is in the review's list but not in the orchestrator's list of tests to add.
- **A product change for item 8 (`biased;` select, or the actor acking registration itself).** No message is lost in the order it would fix (unit test above). The lost-message path is test-only: a message in a topic whose creation answer the actor has not processed yet. In real use a person cannot post before Telegram shows the topic. I am not certain this is the Linux cause. The log dump on timeout will show it if CI fails again.
