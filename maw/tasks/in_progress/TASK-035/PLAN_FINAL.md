## 1. Summary

Hub становится пригодным для сервера в интернете. Оба существующих слушателя (агенты 47291, хуки 47292) принимают rustls TLS 1.3, если у hub заданы `CCTG_TLS_CERT` и `CCTG_TLS_KEY`; newline-JSON и рукописный HTTP/1.1 идут поверх одного `tls::Stream` без изменений протокола. Устройство включает TLS pin-ом `CCTG_HUB_CERT_SHA256` (sha256 сертификата hub; свой `ServerCertVerifier` сверяет ровно эти байты и штатно проверяет подпись рукопожатия); без pin устройство ходит только на loopback, сломанный pin никогда не откатывается на открытый TCP. До проверки секрета hub держит соединения коротко: одно окно от TCP-accept, включающее рукопожатие TLS (агент 5 с, хук 2 с), не больше 16 неаутентифицированных агентских соединений (лишнее закрывается сразу), первая строка агента до 4 КиБ, заголовки хука до 8 КиБ, пауза 250 мс перед ответом на неверный секрет. Сборка определяется git-коммитом (`build.rs`: `CCTG_BUILD_ID` в CI и Docker, иначе `git rev-parse HEAD`, `-dirty` плюс хеш exe для грязного дерева, без git хеш exe), поэтому Linux-hub в контейнере и клиент того же коммита на Windows или macOS не «устаревшие». Один бинарник остаётся. Образ: статический musl на Alpine, uid 10001, том `/data`, `HEALTHCHECK cctg health`; `deploy/compose.yml` (+ `compose.host.yml` для прокси на `127.0.0.1` хоста). Bot API ходит через `HTTPS_PROXY`, если он задан, иначе напрямую; адрес прокси не логируется. CI (`ci.yml`) гоняет fmt, clippy и все тесты на ubuntu, windows и macos, собирает образ и прогоняет контейнерный smoke (compose с фейковым Bot API, healthcheck, хук и агент по TLS клиентом того же коммита, секреты не в образе и не в логах). `release.yml` публикует образ в GHCR и клиентов (Windows x86_64, Linux musl x86_64, macOS arm64) в Releases только по тегу, только с `GITHUB_TOKEN`, actions закреплены по SHA. Док: `docs/remote-hub.md`.

### Шаг 3. Hub-ingress: `crates/cctg/src/hub/ingress.rs`, `wire.rs`
- `Listener { tcp, incoming }` (`From<TcpListener>` = plain, `Listener::tls`, `Listener::new(tcp, Option<Acceptor>)` c info «listening with TLS» или прежним warning про plain за loopback). `serve_agents`/`serve_hooks`/`serve_hooks_and_permissions` берут `impl Into<Listener>`.
- `open(incoming, tcp, peer, deadline)`: рукопожатие TLS в задаче соединения до `deadline` (ревью: был `Duration`, окно после рукопожатия начиналось заново, до 10 с у агента и 4 с у хука); ошибка и таймаут рукопожатия пишутся debug.
- Защита до секрета (ревью, по требованию orchestrator):
  - `HANDSHAKE_TIMEOUT` 5 с и `REQUEST_TIMEOUT` 2 с считаются от accept (`deadline` в `serve_agents`/`serve`), `agent_session` и `hook_request` используют `timeout_at(deadline)`.
  - `MAX_PENDING_AGENTS = 16`: отдельный семафор, `try_acquire_owned` при accept до `MAX_AGENTS`; нет места = соединение закрывается сразу (debug). Разрешение живёт в `struct Handshake { deadline, unauthenticated }` и отдаётся сразу после успешного handshake (при отказе после паузы и `reject`).
  - `MAX_HELLO_LINE = 4 KiB`: первая строка агента читается через новый `wire::read_line_max(reader, buf, max)`; `wire::read_line` = `read_line_max(.., MAX_LINE)`. Длиннее = `Rejection::Protocol` сразу, а не ожидание до 1 MiB.
  - `AUTH_FAIL_DELAY = 250 ms`: `Rejection::Auth` у агента и `401` у хука отвечаются после паузы (место остаётся занятым). Сравнение секрета уже constant-time (`subtle`, `wire::Secret::matches`). Значение секрета не логируется; событие = одна фиксированная warn-строка с адресом пира («agent rejected reason=Auth», «hook request rejected: bad or missing secret»).
  - Хуки: лимит `MAX_HOOK_REQUESTS = 64` уже закрывает лишнее сразу; заголовки до секрета `MAX_HEAD = 8 KiB`, тело читается только после проверки секрета (было до задачи, не менялось).
- Соединение, закрытое до первого байта (healthcheck, сканер): debug «connection closed before its first byte», без ответа (`read_request` возвращает `Err(None)`, остальные ошибки `Err(Some(status))`).
- `agent_session`, `hook_request`, `respond`, `permission_request`, `gone` работают с `Stream`, `tokio::io::split`, `ReadTask`. `respond` делает `shutdown` (для TLS это close_notify + flush).
- Тесты (ревью добавило 6): `the_tls_handshake_counts_against_the_pre_auth_deadline`, `unauthenticated_agents_beyond_the_cap_are_closed_at_once`, `a_long_first_line_is_refused_before_the_secret_is_read`, `a_wrong_secret_is_answered_after_a_fixed_pause`, `garbage_before_auth_never_panics_or_grows` (2000 входов xorshift по `read_request`, `wire::decode::<AgentMsg>`, `read_line_max`), `garbage_and_foreign_handshakes_never_stop_a_listener` (мусор на plain и TLS порты, TLS ClientHello на plain порты, открытый HTTP на TLS порт, затем настоящие агент и хуки проходят). `tests/ingress_logs.rs`: пустые соединения дают две debug-строки и ни одного WARN.

Counter-example, проверенный первым: «какой-то клиентский путь (hook, permission, spool replay, строка статуса, агент, update/deploy) всё ещё открывает `TcpStream` к hub и шлёт секрет открытым текстом при заданном pin или на удалённый адрес».
