## 1. Summary

The pure `transcript` crate gets three things. (1) The parser keeps `message.stop_reason` in a new field `Turn.stop_reason: Option<String>` and stays tolerant to wrong types. (2) A new private module `render.rs` exposes `render_brief(&[Turn]) -> String` and `render_full(&[Turn]) -> String`. They produce plain text for any slice of turns. Brief shows prompts, one line per tool call and final answers (`end_turn`, or null/other stop reason with no later tool call, as approved by the orchestrator). Full adds intermediate text, compact tool inputs and truncated results. Neither mode can emit thinking. An unfinished tail ends with `в работе…`. Non-meta service records (`<task-notification>` and similar) are hidden in brief and shown in full. (3) A new private module `split.rs` exposes `split_for_telegram(&str, SplitOptions) -> SplitResult`. It cuts the rendered text into consecutive exact slices of at most 4096 UTF-16 code units each. It prefers a blank line, then a line break, then whitespace in the second half of the chunk, then an extended grapheme boundary via `unicode-segmentation`'s `GraphemeCursor`. It drops whitespace-only slices and sets `prefer_file` when there are more than `max_chunks` chunks (default 4). `telegram_len` and `TELEGRAM_TEXT_LIMIT` stay public as the single length definition for the hub. All of this is built and passing in `R` (fmt, clippy `-D warnings`, 52 transcript tests). It was also applied to a clean `git archive HEAD` copy of the workspace, where it passes with 54 workspace tests. The implementer copies the files byte for byte and checks the SHA-256 hashes.

- Per block, in order:

Full adds the next line: compact JSON input cut to 500 chars, indented two spaces. It sets `finished = false`.
  - `ToolResult` renders only in full: `  ← {tool name | "tool" | "error"}: {content trimmed, ≤1500 chars}`, every line indented. It sets `finished = false`.
  - Truncation keeps the first N chars and appends `… [+{dropped} chars]`.
- If anything was shown or counted and `!finished`, the marker line is appended. An empty or fully hidden slice gives `""`.

**`src/split.rs`** (private module):
- `pub const TELEGRAM_TEXT_LIMIT: usize = 4096`. `pub fn telegram_len(&str) -> usize` is the sum of `char::len_utf16`. Its doc comment says the Bot API does not name the unit and that UTF-16 is a conservative project policy.
- `pub struct SplitOptions { pub max_chunks: usize }` with `Default` = 4. `pub struct SplitResult { pub chunks: Vec<String>, pub prefer_file: bool }`. Both derive `Debug, Clone, PartialEq, Eq` (`SplitOptions` also `Copy`).
- `split_for_telegram(text, options)` loops `rest.split_at(cut(rest))`. It pushes a slice only if `!slice.trim().is_empty()`. `prefer_file = chunks.len() > options.max_chunks`.
- `cut(text)` makes one char scan up to the limit and records `fit` (the longest char prefix within 4096 UTF-16 units) plus the byte offsets just after the last `\n\n` (paragraph; `\r` is skipped when tracking the previous char), the last `\n` (line) and the last other whitespace (space). If the whole text fits, it returns `text.len()`. Otherwise it returns the first of paragraph, line, space that is `> fit / 2` (bytes) and is a grapheme boundary. Failing that, the last extended grapheme boundary in `1..=fit` (`GraphemeCursor::is_boundary` / `prev_boundary` over the whole remaining text, `chunk_start = 0`). Failing that (one grapheme longer than the window), `fit`.
- No `unwrap`/`expect`/`panic`. Grapheme errors fall back through `unwrap_or(false)` / `.ok()`. All slicing is at char boundaries.

## 5. Review notes

### Disconfirmation (done before the review)

The counter-example I set out to find: PLAN_V2 requires, for every nonblank input, that "every chunk is nonempty … and `chunks.concat() == input`", and it forbids whitespace-only chunks, which Telegram rejects as an empty message. The input `"a" + "\n"×10000 + "b"` must break one of the two: some 4096-unit window lies wholly inside the newline run. The counter-example **held**. The invariant is contradictory as written. Fix: the splitter emits exact slices and drops whitespace-only ones. The test invariant is now "consecutive slices, only whitespace between them" (`blank_run_longer_than_the_limit_drops_only_whitespace`), and exact `concat == input` is asserted wherever no whitespace run exceeds the limit.

I also re-ran the planner's reference as a control. Its 47 tests pass and the hashes match. Its splitter really does have the bugs PLAN_V2 claimed, plus one more (`T/scratch/reviewer2/probe_old`): `combining_split=true`, a regional-indicator flag split after an odd prefix (`flag_split=true`, not covered by PLAN_V2), and a paragraph `\n\n` rewritten to `\n` (`para_sep_lost=true`).

### What changed from PLAN_V2, and why

1. **Dependency accepted, but used differently.** The orchestrator asked me to accept `unicode-segmentation` only if the grapheme bug is real and no simpler dependency-free rule exists. The bug is real (above). The dependency-free candidate was "walk back without the 16-char cap over the joiner table", i.e. never cut inside a cluster unless the cluster alone exceeds the limit. It fixes the combining and ZWJ cases, but it still splits flags (no joiner between regional indicators; needs pair-parity logic), Indic spacing marks and Hangul jamo. A correct hand rule means copying UAX #29 tables, so the dependency is the simpler correct option. PLAN_V2's `grapheme_indices` over each window was correct, but it made the split about 10× slower in debug (43 ms vs 4 ms per 236 KB) and the render suite 0.6 s → 2.6 s. The final code scans chars and asks `GraphemeCursor` only at the candidate cut points (4 ms, suite 0.7 s). The version is pinned to `1.13.3`, not `1.13`, because 1.13.0 and 1.13.1 are yanked.
2. **`telegram_len` and `TELEGRAM_TEXT_LIMIT` stay public.** PLAN_V2 made them private. The spec asks to count the limit "in the same definition of length that the Telegram layer uses", and TASK-014 must cap hub-built messages at 4096. One exported definition prevents drift. `IN_PROGRESS_MARKER`, `SplitLimits.chunk_len` and `Chunks` are gone, as PLAN_V2 asked.
3. **Soft-boundary rule made precise.** PLAN_V2 applied "the latter half" only to whitespace, and it was unclear about paragraphs and lines. Final rule: every soft boundary (paragraph, line, space) must be past half the chunk in bytes. Otherwise the cut is at the last grapheme boundary. This keeps every chunk at least half full apart from the text end and blank-slice drops, so the chunk count stays bounded.
4. **Blank chunks and exact slices reconciled** (disconfirmation above).
5. **Service-record handling built and tested.** PLAN_V2 described it but had no code. The six prefixes come from the planner's survey of real user records (`T/scratch/planner/survey_user_text.out.txt`): 751 `<task-notification>`, 38 `<command-name>`, 32 `<local-command-stdout>`, 24 `<bash-input>`, 24 `<bash-stdout>`, 5 `<command-message>`, all non-meta. `<pasted_content>` (35) stays a visible prompt. Service records never change the in-progress state and are not prompt boundaries for the null-stop rule. Orchestrator decision 2.
6. **Kept from PLAN_V2 and the planner, verified by build:** the tolerant `stop_reason` parser change, the orchestrator-approved null/other structural fallback (OPEN_DECISIONS 1; 238 of 530 subagent files end on null-stop text), marker `в работе…` (decision 4), `max_chunks` default 4 (decision 3), renderer formatting, O(n) maps, the timing test with its bounds, and the fixture.
