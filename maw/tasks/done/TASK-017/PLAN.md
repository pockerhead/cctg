## 2. Approach

One idea: **every allowlisted text topic message is parked in its slot's buffer, and the buffer is flushed to the slot's live agent whenever there is one.** The live path becomes a buffer of one message that is flushed in the same actor turn, so there is one delivery path, order holds (a new message never overtakes kept ones), and a full link queue keeps the message instead of losing it.

- **Where the buffer lives.** `Slot.buffer: buffer::Buffer` in `registry.json` (`#[serde(default, skip_serializing_if = "Buffer::is_idle")]`): older files load, idle slots are written exactly as before, `registry::VERSION` stays 1. Pure logic in a new `hub/buffer.rs` (types, cap, callback data, texts, unit tests); IO in `slots.rs`. The buffer is per slot, not per session (OPEN_DECISIONS 2026-09-24).
- **What is kept.** `Parked { message_id, thread_id, text, reply_to }`. No user id: `updates::Routed` never carries one (updates.rs:3). `target_agent` is computed at delivery for the delivering session (a new session cannot reach the old session's subagent; `subagent_of_message` checks the parent).
- **Cap.** `MAX_BUFFERED = 50`; the 51st drops the oldest (`VecDeque::pop_front`). One `OVERFLOW_NOTICE` per offline period (`overflow_told`).
- **Offline period.** Starts with the first kept message, ends when a flush empties the buffer (`Buffer::close` resets every mark). Marks: `overflow_told`, `queued_told` (one `QUEUED_NOTICE` for a running session without a bound agent), `resume: Option<ResumeNote>`, `resume_asked`.
- **Revival (amended criterion).** `flush_all()` at the start of every `pump()`: a slot with kept messages whose `live_agent(slot)` exists gets them oldest first. `live_agent` already demands a live top-level current session with a bound, connected agent, so: resume of the same session, a new session taking the free slot, and `/clear` (new session, agent follows the pid) all revive; nested runs (never `current_session`, agent never bound), a nested `-p --resume <id>` of the dead session (session stays ended) and subagents never do; headless top-level runs (`sdk-cli`, no hub link) never do; delivery waits for the agent that registers after SessionStart because nothing flushes until it is bound. Recorded as a decision in `log.jsonl`.
- **Delivery point (exactly-once question).** A message leaves the buffer when the agent link queue accepted it (`try_send` Ok), the same point at which TASK-021 counts a live message as delivered; the pop marks the registry dirty and the next snapshot saves it. This is the outbox pattern: relay then mark, which is at-least-once when the relay crashes between the two ([Microsoft, Idempotent Consumer](https://learn.microsoft.com/en-us/azure/architecture/patterns/idempotent-consumer); [ByteByteGo, delivery semantics](https://blog.bytebytego.com/p/a-detailed-guide-to-idempotency-delivery)). Residuals, documented in code and here: (1) a link that dies between the queue and the socket loses the message (same as the live path today); (2) a hub crash between hand-off and the registry save re-delivers after restart. True exactly-once would need an idempotent consumer (agent-side dedup by meta `message_id`), which is an agent change; open question Q1. Rejected alternative: a TASK-014-style `inbound_ack` capability (wire + agent change, still not exactly-once without dedup).
- **Live session without an agent** (the orchestrator's open choice): buffer too, with one `QUEUED_NOTICE` per period; `OFFLINE_NOTICE` is deleted (no user left). Reason: the reconnect window after every hub restart otherwise loses messages, and the domain rule says buffer on the hub side until an agent takes it. No Resume button there: the session is running.
- **Resume button.** A pump reconciler `offer_resume()`: a slot in state `Dead` with kept messages, a topic and no `ResumeNote` yet gets one message `resume_text(session)` with one button `Возобновить`, `callback_data = "resume:<full session id>"` (43 bytes for a UUID, under the Bot API 1-64 byte limit, [Bot API via n8n/DEV summaries](https://dev.to/serhii_a9c08345ac360cf5c8/handle-telegram-inlinekeyboardmarkup-in-php-callbackquery-answercallbackquery-and-the-64-byte-1c7g)); ids over 64 bytes or outside `[A-Za-z0-9-]` get the message without a button. The note is set before the send, so at most one per period, also across a restart; a lost send is not retried in that period. The message counts against `MAX_QUEUED_MESSAGES` like other sends (`Work::Resume`, `Done::Resume` keeps its Telegram `message_id`). When the period ends, the message is edited to `RESUMED_TEXT` with an explicit empty `inline_keyboard` (one try, `Work::Callback`); if the send answer arrives after the period ended, the button goes then.
- **Press.** `resume:<id>` is checked before the permission parser (the prefixes cannot collide: `permissions::parse_callback` rejects any action but `allow`/`deny`, and `buffer::parse_callback` accepts only `resume`). Resolved by session state, not message id (works when the send answer was lost or after a restart): the id is a live top-level session -> "Сессия уже на связи"; it is the ended current session of its slot -> `resume_asked = true` (persisted), info log, answer `ANSWER_UNAVAILABLE` (under the 200-character toast limit of `answerCallbackQuery`); anything else -> `permissions::ANSWER_EXPIRED`. TASK-019 will act on `resume_asked`.
- **Logs.** Only ordinals, short session ids, counts and fixed text; never the message text, a user id, a path or a title (the buffer holds text but no log line prints it).

## 4. Risk areas

- **Link queue full during a flush.** `flush` stops at the first refused `try_send` and tries again at the next `pump`, which runs on any actor input or the 60 s retry tick, not when the agent's queue drains. 50 kept messages fit `TO_AGENT_QUEUE = 64`, and a streamed session wakes the actor every 300 ms, so in practice the rest goes quickly; a quiet session with a nearly full queue could wait up to a minute. Test helpers with a queue of 4 show the behaviour (`a_full_link_queue_keeps_the_rest_in_order_for_the_next_try`).
- **Duplicate after a hub crash.** Between the hand-off and the next snapshot save (milliseconds) a crash re-sends the kept messages after restart. And the pre-existing `getUpdates` at-most-once gap: a message whose update offset was saved but whose registry save did not happen is lost.
- **A session without the channel flag.** Its agent registers, so the flush hands the kept messages to it and Claude Code drops them silently (known platform fact, same as the live path today). The hub cannot tell (channel domain).
- **Resume message during `/clear`.** Between `SessionEnd(clear)` and the new `SessionStart` the slot is `Dead` for one actor turn; if messages were already kept, `offer_resume` sends a button that the flush right after edits away. Rare (needs kept messages at the moment of `/clear`), harmless.
- **registry.json size and privacy.** Kept texts are written to `<state>/registry.json` (gitignored, local) until delivered: up to 50 x 4096 UTF-16 units per slot, rewritten on every change. Many long-dead slots with full buffers make the file large; slots are never pruned, so a folder that never comes back keeps its 50 messages forever. No user id is stored.
- **Behaviour change for users.** The offline notice is gone; a running session without agent gets one "сохранены" notice per period instead of one per minute, and a dead slot gets the Resume message instead. Tests that encoded the old notice change (section 3 step 7).
- **Unified path cost.** Every live message now marks the registry dirty (push + pop), so each message triggers one snapshot save; with the stream receipts this already happened for streamed sessions.
- **A Resume button with an unknown message id** (send answer lost, or cut by a restart) is never edited away; a press still answers correctly because the press is resolved by session.

## 5. Open questions

- **Q1 (follow-up, not blocking).** True exactly-once across a hub crash needs the agent to drop an inbound whose meta `message_id` it already passed on (bounded FIFO, like its verdict-id cache). Worth a small channel-domain task? This plan keeps at-least-once across a crash.
- **Q2 (decided here, confirm if you disagree).** A running session without a bound agent buffers with one notice per period rather than the old per-minute "не доставлено". Alternative: keep the old notice for `NoChannel` slots and buffer only dead ones.
- **Q3 (TASK-019 interface).** The press records `buffer.resume_asked` on the slot. TASK-019 should read it (and the note's session) and start the headless resume; this task does not start anything.
