# TASK-058: status line numbers through the session agent, not a direct POST

Type: bug
Mode: small-fix
Priority: high
Branch: fix/statusline-via-agent
Domains: hub, hooks

## Description
Найдено вживую 2026-09-26: на Linux-клиенте в закреплённом статусе темы нет модели/контекста/лимитов (только «думает», «ждёт»), хотя строка в терминале их показывает. `cctg statusline` (TASK-029) шлёт `status_line` прямо в hub с бюджетом `POST_TIMEOUT = 80 ms`, чтобы не тормозить строку терминала. С hub на удалённом сервере (TASK-035, TLS) одно установление TLS с той машины 162 мс (`curl time_appconnect`), с Windows-машины 37-45 мс. Цифры молча теряются (ошибка только в `debug!`).

Решение оркестратора: statusline не ходит в hub сам. Он атомарно пишет последние цифры сессии в локальный файл (`<state>/status/<session_id>.json`, 0600, rename поверх), а агент этой сессии (MCP-сервер, у него уже открыто соединение с hub) замечает изменение (дешёвый опрос mtime раз в ~1 с или notify без новых крейтов) и отправляет их по своему соединению новым сообщением wire (additive, без VERSION bump; старый hub игнорирует). Hub принимает его как тот же `StatusLine` этой сессии. Прямой POST оставить как запасной путь, только если агента нет (сессия без канала) и hub на loopback; иначе не слать.
Файлы мёртвых сессий чистить (агент удаляет свой при выходе; старше суток при старте).

## Acceptance criteria
- [ ] Цифры доходят до статуса hub при задержке до hub больше 80 мс (e2e: фейковый hub с искусственной задержкой handshake/ответа, настоящий `cctg statusline` + агент)
- [ ] `cctg statusline` не делает сетевых запросов к удалённому hub и укладывается в прежнее время
- [ ] Старый hub на новое сообщение агента не ломается; старый агент со новым statusline не теряет больше, чем сейчас
- [ ] email/секреты в файл и в wire не попадают
- [ ] Existing tests pass
