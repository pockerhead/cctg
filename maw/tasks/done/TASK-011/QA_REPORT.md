## Disconfirmation

Самый конкретный контрпример, записанный до проверки: "Пусть интерактивная сессия B живёт в теме папки F2. Из Bash другой сессии A запускается `claude -p --resume B` (parent pid = A). Фикс I2 не даёт вложенному старту переписать `kind`/`slot` B, но вложенный запуск закончится своим `SessionEnd(B)`. Если SessionEnd помечает B `ended`, слот B становится свободным, и следующая сессия в F2 займёт тему живой B."

Проверка по коду: `apply_hook(SessionEnd)` (`registry.rs:662-690`) ставит `entry.ended = true` по одному session id. В wire у `SessionEnd` нет `claude_pid` (`wire.rs:371-374`), поэтому hub не может отличить конец вложенного запуска от конца настоящей сессии. Тесты `s5b` и `s5c` (ниже) падают в каждом прогоне: s5b 9 из 9, s5c 8 из 8. **Контрпример подтвердился.**

## 4. Bugs found

### B1 — medium — конец вложенного запуска с id живой top-level сессии отдаёт её тему другой сессии
Где: `registry.rs:662-690` (`SessionEnd`) при ранних возвратах в `session_started` (`registry.rs:561-584`). Корень: у `HookEvent::SessionEnd` в wire нет `claude_pid`, и SessionEnd вложенного `claude -p --resume <id>` неотличим от SessionEnd самой сессии.

Воспроизведение (`scratch/qa/tests/e2e.rs`, s5b и s5c, падают в каждом прогоне):
1. A top-level (pid 10) в F, агент подключён.
2. `SessionStart(A, source=resume, claude_pid=30, parent_claude_pid=10)`: это вложенный `claude -p --resume A` из Bash самой A. Для случая `--resume B` из A то же самое делает s5b.
3. `SessionEnd(A, reason=other)` вложенного запуска, затем `Stop(A)`: A продолжает работать.
4. `SessionStart(C, startup, pid 50)` в F.

Ожидалось: A остаётся ⚡️, C получает `#2` (вторую тему).
Получено: теме A ставится 🏁, хотя A жива. `Stop` её не оживляет, `ended` снимает только следующий SessionStart. C занимает тему 100 и пишет туда разделитель `cccccccc · new`, так что в одной теме оказываются две живые сессии. `/brief` в этой теме и будущий inbound (TASK-013) уйдут в C. В PLAN_FINAL §4 для resume id родителя записано только «иконка станет мёртвой до следующего события родителя». Это неверно: обычные события иконку не возвращают. То, что слот уходит другой сессии, там вообще не упомянуто.

Варианты фикса (выбирает оркестратор):
- (a) Добавить `claude_pid: Option<u32>` в `HookEvent::SessionEnd` (`#[serde(default)]`, совместимо; хук TASK-012 его ещё не заполняет). Hub игнорирует SessionEnd, если pid есть и не равен `entry.claude_pid` top-level записи.
- (b) Без изменения wire: при раннем возврате `Parent(..)` в `session_started` запомнить «у сессии X идёт вложенный запуск» и проглотить ровно один следующий SessionEnd(X). Хрупко, если настоящий конец придёт раньше.
- (c) Записать как known limitation и перенести в TASK-012. Сейчас хуков, которые шлют `parent_claude_pid`, ещё нет, поэтому баг латентный.

### B2 — low — обычный startup с повторным pid наследует слот сессии, чей SessionEnd потерян
Где: правило `pids` в `allocate` (`registry.rs:474-488`). Оно не ограничено `source == "clear"`.

Воспроизведение (s4b): A в `#1`, B в `#2` (pid 2). A завершается. B падает без SessionEnd (краш, kill, хаб был выключен). Новая несвязанная сессия C стартует с `source=startup` и тем же pid 2 (Windows переиспользует pid, особенно после перезагрузки).
Ожидалось (явное требование оркестратора): C получает первый свободный слот `#1`.
Получено: C попадает в `#2` (разделитель в thread 101), B помечается `ended`. Лишней темы нет, нарушен только порядок «первый свободный слот».
Фикс: применять правило `pids` только при `source == Some("clear")`. Для других источников при устаревшей записи `pids` помечать прежнюю сессию `ended` (повтор pid доказывает, что её процесс мёртв), но слот выбирать обычным путём. s3b (обратный порядок `/clear`) должен остаться зелёным.
