## 1. Summary

Hub принимает из темы `document`/`photo` (самый большой размер)/`video`/`voice`/`audio`/`animation` от allowlisted-пользователя и паркует сообщение в буфере слота ссылкой (`Parked.file`: `kind`, `file_id`, `name?`, `size?`, без байтов, в `registry.json`). Когда у слота есть живой агент с capability `Register.files`, одна задача hub (`hub/fetch.rs`) делает `getFile` + скачивание (≤ 20 MiB, мимо планировщика, до 3 попыток на 429/сеть/5xx) и отдаёт файл агенту по agent-линку как `file_start` + base64 `file_chunk` по 256 KiB, держа в очереди линка не больше 4 строк; файл держит следующие сообщения слота, пока все его чанки не в очереди линка. Агент собирает файл в памяти, сохраняет в `<cwd сессии>/.cctg/inbox/<UTC-дата>-<очищенное имя>` (без перезаписи, `.gitignore` = `*` внутри самого inbox; запасная папка `<temp>/cctg-inbox`) и шлёт Claude обычное channel-сообщение с путём, размером, видом и подписью (meta `file_path`, `file_kind`, `file_size`). Обратно: MCP-инструмент `send_file(path, caption?)` читает обычный файл 1..=50 MiB, шлёт `file_offer` только hub, объявившему `registered{files:true}`, после `accepted` чанки, hub собирает файл (не больше одного файла максимального размера за раз на весь hub, простаивающая передача освобождается через 60 с) и шлёт его через единый планировщик тихо как `sendPhoto` (JPEG/PNG/WebP по сигнатуре, ≤ 10 MiB; на 400 тот же job уходит `sendDocument`) или `sendDocument`, а агенту отвечает `sent`/`failed`. `wire::VERSION` не меняется; старый агент получает в тему `OLD_AGENT_NOTICE`, а подпись текстом; стикеры и кружки получают короткое `UNSUPPORTED_NOTICE`. Логи несут только вид, размер, ордер слота, conn и короткий id сессии.

## 4. Rollout notes

- Миграций нет. `registry.json` получает необязательное поле `file` у ждущих сообщений; текстовые записи не меняются. Откат hub на сборку до TASK-032 с ждущим файлом в `registry.json`: старый hub поле не знает и отдаст сессии только подпись (возможно пустой текст). Перед откатом дать буферам опустеть.
- Новых env, флагов и настроек нет. `wire::VERSION` = 1: старые агенты живут с новым hub (получают `OLD_AGENT_NOTICE` на файлы, подпись текстом), новые агенты со старым hub не предлагают файлы (`send_file` отвечает ошибкой «hub недоступен или старше агента»).
- После merge (orchestrator, не implementer): `cctg deploy` и перезапуск hub supervisor-ом; живые сессии со старым агентом получают `OLD_AGENT_NOTICE`, пока пользователь не нажмёт ⬆️ Обновить. Живой hub и supervisor в `~/.cctg`, запущенные claude и `~/.cctg` implementer не трогает; интерактивных claude и окон не открывает; настоящий Telegram API не вызывает.
- Inbox создаётся в рабочей папке сессии (`.cctg/inbox/` с собственным `.gitignore`); `.gitignore` пользователя не меняется. Уборки inbox нет (follow-up ниже).
- Известные пределы (задокументированы, не баги этой задачи):
  - Отправка файла идёт через единый последовательный планировщик (закон hub: все отправки через одну очередь): загрузка 50 MB держит остальные отправки, включая permission-промпты, до `DOCUMENT_TIMEOUT` 120 с; на медленном uplink такой файл может не уложиться и получить `failed`.
  - Скачивания последовательны на весь hub; повторы (до ~34 с ожидания на 429) задерживают файлы других слотов.
  - Ответ `send_file`, ждущий в момент подмены воркера (TASK-040), теряется: hub шлёт `update` только вне хода, а `send_file` всегда внутри хода и локально отвечает не дольше ~100 с. Совпадение возможно только для вызова, ушедшего в фон через 2 минуты (удалённый медленный линк) и нажатия ⬆️ Обновить в это же время; такой вызов останется фоновой задачей до `MCP_TOOL_TIMEOUT` (~28 ч по докам Claude Code).
  - Файл из темы, чьи чанки все попали в очередь линка уходящего при подмене воркера, но пришли после `released`, теряется с 👀 (как текст TASK-017 в том же окне).
  - Крах hub между передачей чанков и сохранением `registry.json` даёт повторную доставку (агент сохранит `-2`), как текст TASK-017.
  - `send_file` читает любой обычный файл, доступный процессу, в том числе вне рабочей папки (решение ниже).
- Follow-ups (не в этой задаче): уборка старых файлов inbox (например, старше 7 дней); ответ ждущих `send_file` ошибкой перед `Ended::Handover`; отдельная полоса планировщика для больших файлов, если файлы станут частыми (потребует правки закона hub).

## 5. Review notes

Проверенный контрпример (disconfirmation): «`send_file`, у которого рвётся линк посреди передачи или чьи чанки после `accepted` не приходят, отвечает сразу и ничего не держит на обеих сторонах» (план: «оборванный линк — ошибка», «отключение линка выбрасывает недособранный файл»). Не выдержал: агент при потере линка висел в `files::room`, пока линк не вернётся (очередь линка при переподключении никто не читает; `interrupted` проверялся только между чанками), а hub держал байты принятого, но заброшенного offer до следующего offer того же conn или его отключения. Оба случая воспроизведены падающими тестами на коде планировщика (`R/red_unit.txt`) и исправлены.

Изменения относительно плана и эталона планировщика (каждое с падающим тестом до правки, `R/red_unit.txt`):
1. `agent.rs`: `interrupted` заменён на `room_or_heard` (`select!` с приоритетом событий воркера над ожиданием места). Причина: send_file висел всё время отсутствия hub и мог уйти в фон Claude Code. Тест `a_link_lost_while_chunks_wait_for_room_ends_the_upload_at_once`.
2. `slots.rs`: `Upload.touched` + `UPLOAD_IDLE` 60 с, простаивающие загрузки выбрасываются при следующем offer, их агенту `failed`. Причина: offer, дошедший после таймаута агента (`OFFER_WAIT`) или повторно отправленный из очереди линка после переподключения, навсегда занимал бюджет, и все сессии получали `busy`. Тест `an_accepted_file_whose_bytes_never_come_does_not_hold_the_budget`.
3. `slots.rs`: `MAX_FILE_BYTES` 100 MiB -> `files::MAX_UPLOAD` (50 MiB). Причина: граница памяти «50 MiB out» от orchestrator; с клоном multipart в `send_file` пик был ~150 MiB, стал ~100 MiB. Второй большой файл в это время получает `busy` («попробуйте через минуту»). Тест `at_most_one_file_of_the_largest_size_waits_at_a_time`.
4. `files.rs`: `.gitignore` = `*` пишется в сам inbox, а не в `.cctg`. Причина: вариант планировщика прятал от git всё новое в `.cctg` проекта (`R/gitignore_probe.out.txt`). Тест `the_inbox_ignores_only_itself`; `agent` тест считает в inbox два файла (сохранённый и `.gitignore`).
5. `fetch.rs`: `download` с 3 попытками на 429 (`retry_after`, не больше 30 с), сетевые ошибки и 5xx (2 с). Причина: план выбрасывал файл пользователя с «пришлите ещё раз» на временной ошибке; отказ (4xx, `file is too big`) остаётся финальным, как решил планировщик. Тест `a_flood_wait_or_a_telegram_outage_is_tried_again`.
6. `updates.rs`: `width.saturating_mul(height)`. Причина: переполнение на внешних данных паниковало в debug. Тест `a_photo_of_any_announced_dimensions_is_taken`.

Проверено и оставлено как в плане (с причиной):
- Capability в обе стороны: `Register.files` (hub шлёт файлы только такому агенту) и `registered{files}` (агент предлагает только такому hub); без VERSION bump, старые пиры читают новые строки (тест на HEAD `unknown_fields_are_ignored` и новый `files_stay_compatible...`).
- Порядок и размер чанков: строго `offset == принято`, не больше объявленного, иначе передача выбрасывается на обеих сторонах; hub->agent размер берётся из фактически скачанных байтов, не из анонса Telegram.
- Голодание текста и relay: файл держит только следующие сообщения своего слота; permission-вердикты, ответы и `update` идут `try_send` мимо буфера и ждут за ≤ 4 строками чанков в очереди линка (64); агентская очередь линка (256) так же держит ≤ 4 строки чанков.
- `sendPhoto` против `sendDocument`: по сигнатуре байтов и ≤ 10 MiB, никогда по имени или MIME; 400 на `sendPhoto` -> тот же job `sendDocument`. Фото сжимается Telegram, это требование задачи («картинку как фото»).
- Путь `send_file` вне cwd разрешён: адресат всегда только своя приватная тема, Claude и так читает любой файл и может переслать его текст, вызов MCP-инструмента по умолчанию проходит permission prompt Claude Code (он релеится в Telegram), а ограничение cwd сломало бы законные случаи (скриншот в `%TEMP%`, артефакт сборки вне проекта). Относительный путь считается от рабочей папки агента. Каталоги, устройства и отсутствующие пути -> «not a regular file»; ссылка на обычный файл допустима; 0 байт и > 50 MiB -> ошибка без offer.
- Inbox в рабочей папке, а не во временной: Claude читает его без запроса разрешения. Две сессии одной папки не перезаписывают друг друга (`create_new` + номер). Папка только для чтения или `.cctg`-файл -> `<temp>/cctg-inbox`.
- Мёртвый слот: ничего не скачивается, ссылка ждёт в `registry.json`, при оживлении качается заново; протухший `file_id` -> `FETCH_FAILED_NOTICE`.
- Логи: проверены все новые `info!/warn!/debug!` — только вид, размер, ордер, conn, исход; `ApiError` при скачивании без URL (`without_url()`), описание ошибки Telegram не содержит имён.
- Shim не меняется; `tools/list` согласован после подмены (update_e2e). Ответы orchestrator на открытые вопросы: 1) list_changed оставлен, проверка живьём после rollout; 2) файлы из сессии тихие (`notify: false`); 3) кружки и стикеры получают короткое уведомление, без скачивания; 4) уборка inbox в follow-ups.
- Размер: +~4.2k строк в основном тесты (files_e2e ~630, тесты slots/agent/fetch/files/wire); в коде лишним оказался только `mime_type`. `Dirs` нужен (clippy `too_many_arguments` на `serve_channel`), `FileKind::Other`/`FileOutcome::Other` — две строки прямой совместимости.
