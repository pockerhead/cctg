## 3. Issues

### 1. major: файл, скачиваемый в момент конца сессии, теряется с 👀
- **Где:** `crates/cctg/src/hub/slots.rs:1867-1922` (`on_fetched`, ветка `Fetched::Handed`); захват линка в `slots.rs:1841-1848`; `crates/cctg/src/hub/fetch.rs:112-154`.
- **Сценарий.** Пользователь шлёт фото и сразу `/exit` (или сессия кончается сама, или TASK-040 перезапускает claude). Hub уже начал `getFile`/скачивание (секунды на 20 MB, до ~34 с с повторами). Приходит `SessionEnd`, и `registry.rs:1020` делает `entry.agent = None` именно затем, чтобы «the old link, still open for a moment, must not take the slot's kept messages (TASK-017)». Но задача скачивания держит клон `to_agent` старого линка и закидывает в него `file_start` и чанки. `on_fetched(Handed)` снимает сообщение из буфера и ставит 👀. Умирающий агент сохранит файл в inbox и отправит channel-сообщение в закрывающийся Claude Code. Следующая сессия слота (resume) этот файл не получит, а пользователь видит 👀 «принято».
- **Доказательство:** падающий тест выше (`repro_out.txt`: `got ["file photo.jpg look"]; reacted [2]; buffered [3]`).
- **Правка.** Хранить conn задачи в `fetching` (`(transfer_id, message_id, conn)`). В `on_fetched` на `Handed` снимать сообщение и ставить 👀 только если `self.live_agent(slot).map(|(_, c)| c) == Some(conn)`, иначе вести себя как при `LinkClosed`: сообщение ждёт в слоте. Для `/clear` это даст в худшем случае повтор, то есть at-least-once, как у текста TASK-017. Можно ещё научить `fetch::hand` останавливаться между чанками по флагу, но это не обязательно. Репро добавить тестом.

### 2. minor: переполнение буфера во время загрузки выкидывает файл с фронта, текст обгоняет его
- **Где:** `slots.rs:1667-1708` (`park` → `buffer.push` дропает старейшее), `slots.rs:1885-1893` (ранний `return` в `on_fetched`), `slots.rs:1806` (`hand_file` проверяет `fetching` только для файлов).
- **Сценарий (трасса).** Живой агент, файл на фронте скачивается (`fetching[slot]` стоит), за ним копятся тексты. 51-е сообщение вытесняет файл, тема получает `OVERFLOW_NOTICE` («старое удалено»). Следующий `flush` видит на фронте текст (не файл), ему `fetching` не мешает, и все тексты уходят агенту раньше файла. Потом задача дожимает файл (`Handed`), `on_fetched` не находит его на фронте и выходит без 👀. Итог: файл, о потере которого тема уже сообщила, всё-таки приходит, но после 50 более поздних сообщений и без реакции. Условие редкое: 50 сообщений за одну загрузку.
- **Правка.** В `park` при полном буфере не вытеснять сообщение, которое сейчас в `fetching` (вытеснять второе по старшинству). Либо в `flush` держать слот, пока `fetching` содержит слот, для любого фронта.

### 3. minor: строки чанков по ~350 KB при лимите записи 5 с на медленном линке дают бесконечный цикл
- **Где:** `files.rs:32` (`CHUNK` 256 KiB → строка ~350 KB), `hub/ingress.rs:29` и `agent.rs:78` (`WRITE_TIMEOUT` 5 с на строку), `slots.rs:1878-1883` (`LinkClosed` оставляет файл без счётчика попыток).
- **Сценарий (трасса, не воспроизводилось).** Удалённое устройство (шаг 5, Tailscale) с линком медленнее ~70 KB/s. Одна строка чанка не пишется за 5 с, hub рвёт соединение, `fetch::hand` возвращает `LinkClosed`, файл остаётся. После переподключения его снова скачивают из Telegram и снова шлют, соединение снова рвётся, и так без предела. Каждый разрыв теряет всё, что уже лежало в очереди линка (текст TASK-017 снимается из буфера на `try_send`). Строки транскрипта (TASK-016) ограничены ~128 KB текста, так что файлы делают такие разрывы заметно вероятнее.
- **Правка.** `CHUNK` 64 KiB (строка ~90 KB, те же 4 строки впереди). Плюс/или счётчик `LinkClosed` на сообщение: после N подряд `FETCH_FAILED_NOTICE`.

### 4. minor: фолбэк `sendPhoto` → `sendDocument` на любой 400 удваивает простой планировщика
- **Где:** `crates/cctg/src/hub/scheduler.rs:224-238`.
- **Сценарий.** Любой 400 (`message thread not found`, `chat not found`, ошибка подписи) запускает второй полный multipart-аплоад в том же job. Планировщик последовательный: до 2×`DOCUMENT_TIMEOUT`, то есть 240 с, стоят все отправки, включая permission-промпты. Метрится это как одна отправка, а вызовов два. Для фото ≤ 10 MB на нормальном линке это мелочь, но фолбэк на «topic not found» заведомо бессмыслен.
- **Правка.** Фолбэк только когда в описании 400 есть `PHOTO`/`IMAGE` (как `PHOTO_INVALID_DIMENSIONS` в e2e). Либо принять как есть и записать в known limits.

### 5. minor: сохранение входящего файла блокирует MCP-цикл агента
- **Где:** `crates/cctg/src/agent.rs:837`, `agent.rs:847` (`deliver(incoming, &dirs).await` внутри `select!`-цикла).
- **Сценарий.** Запись 20 MiB в `spawn_blocking` ожидается прямо в цикле. Пока идёт запись, не обрабатываются stdin-кадры Claude Code, вердикты и события hub. На обычном SSD это десятки мс. На сетевой папке или под антивирусом, который сканирует новый файл, это секунды.
- **Правка.** Запускать сохранение отдельной задачей и возвращать готовый `HubMsg::Inbound` в цикл через канал. Порядок относительно следующих inbound сохранится, если держать их за незавершённым файлом.
