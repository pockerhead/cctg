## 0. Исследование (что решает дизайн)

- **Bot API** (https://core.telegram.org/bots/api, выгрузка в `P/research/botapi.txt`): `getFile` «bots can download files of up to 20MB», ссылка `https://api.telegram.org/file/bot<token>/<file_path>` живёт «at least 1 hour», `file_id` можно использовать снова (поэтому буфер мёртвого слота держит `file_id`, а не байты, и скачивает при доставке). В исходнике telegram-bot-api `MAX_DOWNLOAD_FILE_SIZE = 20 << 20`, ответ сверх него `400 Bad Request: file is too big` (`P/research/client_cpp_excerpt.txt`: `Client.h:72`, `Client.cpp:9383,17043`). Multipart: «10 MB max size for photos, 50 MB for other files»; `sendPhoto`: «width and height must not exceed 10000 in total. Width and height ratio must be at most 20». Caption 0–1024 символа. `Message.photo` это «available sizes of the photo» (массив); `animation` «for backward compatibility... the document field will also be set»; `live_photo` так же заполняет `photo`. `getFile` «may not preserve the original file name»: имя берётся из сообщения (`file_name`), для фото/голоса строится из вида и расширения `file_path`.
- **Claude Code MCP** (https://code.claude.com/docs/en/mcp): «Claude Code supports MCP `list_changed` notifications... automatically refreshes the available capabilities»; вызов главного разговора дольше двух минут «moves to a background task»; idle timeout stdio-серверов 30 минут. Отсюда: воркер после подмены шлёт `notifications/tools/list_changed`, а `send_file` ждёт ответа Telegram не дольше 90 с.
- **Имена файлов**: Microsoft Learn «Naming Files, Paths, and Namespaces» (запрещённые `<>:"/\|?*`, коды 0–31, CON/PRN/AUX/NUL/COM¹²³/LPT¹²³ «also... followed immediately by an extension», не заканчивать пробелом или точкой). OWASP File Upload Cheat Sheet: не доверять имени и Content-Type от клиента, ограничивать размер, хранить вне публичных мест. Поэтому: имя чистится, тип фото определяется по сигнатуре байтов, размеры ограничены на обеих сторонах, файл кладётся только в свой inbox и никогда не перезаписывает существующий.

## 2. Approach

1. **Wire без смены VERSION.** `Register.files` (агент принимает файлы), `HubMsg::Registered { files }` (hub принимает `file_offer`; `#[serde(default)]`, пропускается при `false`, строка старого hub читается как `false`, старый агент игнорирует поле). Hub -> агент: `file_start{transfer_id, name, size, kind, content, meta}` и `file_chunk{transfer_id, offset, data}` только агенту с `files`. Агент -> hub: `file_offer{transfer_id, name, size, caption?}`, ответ `file_answer{accepted|no_topic|busy|failed}`, после `accepted` чанки, затем `file_answer{sent|failed}`. `FileKind` и `FileOutcome` с `#[serde(other)] Other`. Чанк 256 KiB сырых байт, base64 (`base64 = "0.23"`, уже в lock через reqwest), строка ~350 KB. Приём строго по порядку (`offset` = принятое), не больше объявленного размера, иначе передача выбрасывается.
2. **Общий модуль `src/files.rs`**: `chunks`, `Assembly`, `room` (отправитель держит в очереди линка не больше 4 строк, остальные сообщения не ждут за файлом), `is_photo` (JPEG/PNG/WebP по байтам), `default_name`, `clean_name`, `date`, `save` (inbox `<cwd>/.cctg/inbox`, свой `.cctg/.gitignore` = `*`, запасной `<temp>/cctg-inbox`, `create_new`, `-2`, `-3`...), `read_upload` (обычный файл 1..=50 MiB). Лимиты `MAX_DOWNLOAD` 20 MiB, `MAX_UPLOAD` 50 MiB, `MAX_PHOTO` 10 MiB.
3. **Тема -> сессия.** `updates` извлекает `Media { file: Attachment, caption }` (animation раньше document, самый большой размер фото), `text` остаётся `None`, поэтому подпись никогда не команда. `slots::on_topic_message`: `file_size` > 20 MiB — уведомление сразу; другое медиа (стикер, кружок) — «такие сообщения не доходят» (старая заглушка «только текст» удалена); файл паркуется в буфер слота как `Parked.file` (ссылка `file_id`, в `registry.json`). `flush` на файле: агент без `files` — уведомление в тему и подпись текстом; иначе задание в `hub::fetch` (одна задача на hub, по одному файлу: `getFile` + скачивание мимо планировщика, это чтение, не сообщение в чат), файл держит следующие сообщения слота, пока все его чанки не в очереди линка; тогда уходит из буфера и получает 👀 (`Done::Fetched`). `too big`/отказ Telegram — уведомление, сообщение уходит; закрытый линк — остаётся для следующего агента. Мёртвый слот ничего не скачивает, файл ждёт ссылкой и уходит при оживлении, как текст TASK-017.
4. **Агент принимает файл**: один файл за раз в памяти (`Incoming` + `Assembly`, ≤ 20 MiB), по завершении `spawn_blocking(files::save)`, затем обычное `notifications/claude/channel`: content «A photo from the Telegram topic is saved at <путь> (<N> bytes).» + подпись (с цитатой/пересылкой), meta как у текста + `file_path`, `file_kind`, `file_size`. Не сохранилось — content говорит об этом. `LinkEvent::Down` выбрасывает недоделанный файл.
5. **Сессия -> тема.** Инструмент `send_file(path, caption?)`: `channel::Server` проверяет аргументы и откладывает вызов (`take_file_calls`), цикл отдаёт его воркеру-отправителю (одна передача за раз, очередь 4). Отправитель: путь (относительный от cwd сессии), `read_upload`, `file_offer` (только если hub объявил `files`), ждёт `accepted` 10 с, шлёт чанки с `room`, ждёт `sent`/`failed` до 90 с; ответ инструмента по исходу, оборванный линк — ошибка. Hub (`slots`): offer принимается от агента живой текущей сессии слота с темой (`live_reply_slot`, как `reply`), размер 1..=50 MiB, не больше 100 MiB файлов в ожидании (`MAX_FILE_BYTES`) и не при полном `MAX_QUEUED_MESSAGES`; собранный файл (слот перепроверяется) уходит `Op::SendPhoto` (картинка по байтам ≤ 10 MiB) или `Op::SendDocument`, тихо, через планировщик; 400 на `sendPhoto` — тот же job сразу `sendDocument` в `Transport`. `Done::File` возвращает агенту `sent`/`failed`. Отключение линка выбрасывает недособранный файл.
6. **Shim и подмена воркера (TASK-040).** Shim не меняется. `initialize` объявляет `tools.listChanged`; воркер с `CCTG_WORKER_RESUMED` первым делом пишет `notifications/tools/list_changed`, Claude Code перечитывает список и видит `send_file`. `update` hub шлёт только вне хода (TASK-040), а `send_file` всегда внутри хода и короче 2 минут, поэтому подмена посреди передачи на практике не случается; если случится, передача обрывается как при потере линка.
7. **Логи.** Только вид, размер, ордер слота, conn, короткий id сессии; никаких имён, путей, подписей и байтов (проверено e2e с маркерами).

## 4. Risk areas

- **`list_changed` не проверен живьём** (интерактивный claude агентам запрещён). По докам Claude Code перечитывает инструменты; если нет, после ⬆️ Обновить `send_file` появится только после перезапуска claude, приём файлов из темы работает в любом случае (он не зависит от списка инструментов).
- **Память.** Hub держит до 100 MiB файлов из сессий (сборка + очередь планировщика) и до 20 MiB скачивания; `send_document`/`send_photo` клонируют байты на запрос (существующий приём `send_document`), пик ~2x файла. Агент держит один файл из темы (≤ 20 MiB) и один исходящий (≤ 50 MiB).
- **Очередь планировщика.** Файл это одна метеринговая отправка (как документ `/brief`), 50 MB загрузка держит однопоточный планировщик до 120 с (`DOCUMENT_TIMEOUT`); сообщения других тем ждут. Так было и с документами; для частых больших файлов понадобится отдельная полоса.
- **Скачивания последовательны на весь hub**; медленный агент (очередь линка полна) держит задачу, пока линк не закроется (запись в ingress ограничена 5 с). 429 на `getFile` не повторяется: файл получает FETCH_FAILED_NOTICE.
- **Порядок и at-least-once.** Крах hub после передачи чанков, но до сохранения `registry.json`, даст повторную доставку файла (агент сохранит `-2`), как с текстом TASK-017. Переполнение буфера во время скачивания выбрасывает старейший (скачиваемый) файл: `on_fetched` сверяет `message_id` и ничего не удаляет лишнего.
- **Откат hub на старую сборку** с `registry.json`, где лежит файл: старый hub не знает `file` и отдаст сессии только подпись (возможно, пустой текст).
- **Inbox в рабочей папке.** Если в проекте `.cctg` — ссылка или папка пользователя, файл ляжет туда же; `.gitignore` создаётся только при отсутствии. Заполнение диска не ограничено (файлы от одного allowlisted пользователя, ≤ 20 MiB каждый).
- **`send_file` читает любой файл, доступный процессу** (вызов делает Claude; адресат всегда только своя приватная тема; сам вызов MCP-инструмента Claude Code по умолчанию спрашивает разрешение, и этот запрос уходит в Telegram через relay).
- **Имена в Telegram**: `file_name` multipart чистится `clean_name`; подпись режется до 1024 UTF-16 единиц (`registry::cut`), Telegram считает после разбора сущностей, мы шлём без `parse_mode`.
- **Flake-риск e2e**: `files_e2e` ждёт события с таймаутом 30 с, паузы 200–300 мс только там, где hook и control идут разными каналами (как `buffer_e2e`).
