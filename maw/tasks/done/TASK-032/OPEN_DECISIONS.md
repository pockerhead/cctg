# TASK-032 — решения планировщика (полная автономия, каждое с отвергнутой альтернативой)

1. **Куда агент кладёт файл из темы.** `<cwd сессии>/.cctg/inbox/<UTC-дата>-<имя>`, при ошибке (папка только для чтения, `.cctg` это файл) `<temp>/cctg-inbox/`. Claude читает файлы внутри рабочей папки без запроса разрешения; в `.cctg/` агент кладёт свой `.gitignore` с `*` (только если его там нет), так что `git status` чист, а `.gitignore` пользователя не трогается. Отвергнуто: только temp (чтение вне рабочей папки спрашивает разрешение, каждое фото давало бы prompt); `~/.cctg/inbox` (то же плюс смешивает сессии); правка `.gitignore` пользователя (запрещено задачей).
2. **Имя файла.** Последний компонент пути; `<>:"/\|?*`, управляющие и bidi-символы (U+200E/F, U+202A–202E, U+2066–2069) заменяются на `_`; точки и пробелы с краёв срезаются (нет скрытых файлов и `..`); зарезервированные имена Windows (CON, PRN, AUX, NUL, COM0-9, LPT0-9, с ¹²³, с любым расширением) получают `_` в начале; не длиннее 120 байт с сохранением расширения до 16 байт. Без имени (фото, голос): `<kind>.<расширение file_path Telegram>`. Отвергнуто: сгенерированный UUID вместо имени (OWASP советует для веб-загрузок, но здесь имя нужно Claude и пользователю, а путь приватен); проверка только `..`.
3. **Без перезаписи.** `OpenOptions::create_new`; занято — `-2`, `-3`, ... перед расширением (до 1000). Отвергнуто: перезапись и атомарный rename (rename заменяет существующий файл).
4. **Размер чанка на линке.** 256 KiB сырых байт, base64 (крейт `base64 0.23`, уже в lock через reqwest), строка ~350 KB при `MAX_LINE` 1 MiB. Отправитель держит в очереди линка не больше 4 строк (`files::room`), чтобы разрешения и ответы не ждали за файлом. Отвергнуто: hex (x2), JSON-массив байтов (до x4), 512 KiB (строка ~700 KB ближе к пределу), отдельный канал в link-таске (меняет сигнатуру `agent::spawn`).
5. **Протокол.** Hub -> agent: `file_start{transfer_id, name, size, kind, content, meta}` + `file_chunk{transfer_id, offset, data}`, только агенту с `Register.files`. Agent -> hub: `file_offer{transfer_id, name, size, caption?}`, hub отвечает `file_answer{accepted|no_topic|busy|failed}`, после `accepted` чанки, потом `file_answer{sent|failed}`. Hub объявляет приём в `registered{files: true}` (новое опциональное поле, старый агент его не видит), агент шлёт offer только такому hub. VERSION = 1. Отвергнуто: отправлять offer без объявления (старый hub выдаёт warn на каждый чанк; нарушает правило wire.rs); отдельное сообщение-возможность от hub (лишний тип).
6. **Что видит Claude.** Обычное `notifications/claude/channel`: content `A photo from the Telegram topic is saved at <путь> (<N> bytes).` + пустая строка + подпись (с цитатой/пересылкой, как у текста); meta как у текста плюс `file_path`, `file_kind`, `file_size`. Не сохранилось: content говорит об этом, `file_path` нет. Отвергнуто: только meta (Claude может не заметить атрибуты), содержимое файла inline (размер, бинарные данные).
7. **Файл в памяти, не на диске, пока не пришёл целиком** (агент ≤ 20 MiB, hub ≤ 50 MiB на соединение, всего ≤ 100 MiB `MAX_FILE_BYTES`). Оборванная передача просто выбрасывается на обеих сторонах. Отвергнуто: запись `.part` на диск (нужна уборка обрывков).
8. **Скачивание мимо планировщика.** Одна задача `hub::fetch` на hub, файлы по одному, `getFile` + `https://api.telegram.org/file/bot<token>/<file_path>` прямо через `BotApi`. Это чтение, не сообщение в чат: лимит группы 20/мин его не касается. Отвергнуто: `Op::GetFile` в планировщике (однопоточный планировщик ждал бы 20 MB загрузку, задерживая все сообщения).
9. **Порядок.** Файл в буфере слота держит сообщения после себя, пока все его чанки не в очереди линка (тогда уходит из буфера, как текст по TASK-017). Отвергнуто: текст обгоняет файл (фраза «что на скриншоте?» пришла бы раньше скриншота).
10. **Ошибки скачивания.** `file_size` > 20 MiB известен сразу: уведомление, в буфер не кладётся. Telegram сказал `file is too big` или отказал иначе: уведомление, сообщение уходит из буфера (без повторов). Закрытый линк: сообщение остаётся для следующего агента (at-least-once). Отвергнуто: повторы при ошибке Telegram (перезапрос того же file_id обычно даёт ту же ошибку, а петля держит слот).
11. **Старый агент без `files`.** Файл не передаётся, в тему одно уведомление («клиент cctg устарел... ⬆️ Обновить»), подпись (если есть) уходит сессии обычным текстом. Отвергнуто: молча выбросить подпись; держать файл до обновления (буфер забивается, порядок стоит).
12. **Фото или документ.** Hub решает по байтам (JPEG/PNG/WebP сигнатуры) и размеру ≤ 10 MiB; иначе `sendDocument`. Отказ Telegram 400 на `sendPhoto` (размеры, формат) — тот же job сразу уходит `sendDocument` внутри `Transport` (одна попытка). Отвергнуто: по расширению имени (не доверяем), по MIME от агента.
13. **Когда `send_file` отвечает.** После ответа Telegram (`sent`/`failed`), не дольше 90 с (у Claude Code вызов дольше 2 минут уходит в фон), по таймауту `isError: false` «файл у hub, Telegram ещё не подтвердил». Offer без ответа 10 с — ошибка «hub не ответил». Отвергнуто: отвечать сразу после постановки в очередь (Claude не узнал бы об отказе).
14. **Файлы из сессии тихие** (`notify: false`), как `reply` (правило TASK-041: громко только ответы, промпты и итоги субагентов).
15. **Инструменты после подмены воркера.** Воркер объявляет `tools: {listChanged: true}`; воркер, запущенный после подмены (`CCTG_WORKER_RESUMED`), первым делом пишет `notifications/tools/list_changed`. Shim ничего не кэширует (строки как есть), Claude Code по докам перечитывает список. Отвергнуто: требовать перезапуск claude при появлении нового инструмента (TASK-040 restart тяжелее, а доки обещают refresh).
16. **Типы медиа.** document, photo (самый большой размер по `width*height`, затем `file_size`), video, voice, audio, animation (раньше `document`: Telegram заполняет оба). Стикеры, кружки, геометки и прочее — уведомление «такие сообщения не доходят». Media group приходит несколькими сообщениями, каждое отдельно.
