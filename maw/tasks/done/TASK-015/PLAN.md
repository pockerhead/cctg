**Registry (`hub/registry.rs`).**

Nested runs never get a slot or topic, and `agent_connected` refuses them (788-796). Nothing is posted for them: no `⇣ nested` block exists.
- Topic work pattern to copy: desired state in the registry (`pending_separator`, `applied_title`), `busy` (serde skip) per slot, `failed` until `retry_failed` (1020-1024), and at most one call per slot in flight.

**Slot actor (`hub/slots.rs`).**

So a nested run's Stop is never sent, and `SubagentStop` is a different enum variant that never reaches `on_turn_answer`. Nothing handles `SubagentStart/Stop/Handback` beyond the registry.
- `on_topic_message` (557-608) builds the meta `chat_id`, `message_id`, `thread_id` and `reply_to_message_id` (only for an explicit reply, `updates.rs:118-121`) and `try_send`s to the agent of the slot's live current session (`live_agent`, 611-620).

**Transcript crate.** `Subagent::new(SubagentInput)` (`src/subagent.rs`) already applies the whole body order: report > finished transcript brief (only when its final answer equals `last_assistant_message`) > `last_assistant_message` > in-progress brief > empty. That covers "a lagging transcript file" (test `body_source_order_is_fixed`). The header takes type from the meta or `input.agent_type`, and description **from the meta only**. `agent_header` is `pub(crate)`. `Block::ToolResult.agent_id` comes from `toolUseResult.agentId` (`lib.rs:169-173`).

**Premise.** 65/65 real `Agent` calls have a result with `toolUseResult.agentId` (`PREMISE_CHALLENGE.md`), and every parent result is `async_launched`, so the result is written at launch. The parent jsonl is written asynchronously and lags the hooks (hooks.md, transcript.md).

## 2. Approach

1. **Correlation decides what is a subagent.** A typed `SubagentStart` or `SubagentStop` of a known **top-level** session with a slot becomes an in-memory *candidate* in the slot actor. It does not go into the registry. The actor reads the parent transcript (the session's `transcript_path`) incrementally off the actor: per session offset, complete lines only, one read in flight per session. It collects `Agent` tool uses (`tool_use_id -> subagent_type, description`) and results (`agentId -> tool_use_id`). When both sides exist for the candidate's id, the subagent is **confirmed**: `registry.confirm_subagent` records it and opens its block. Internal agents and the `--agent` main agent never have such a call, so they never get a block (acceptance 2).
2. **Lagging transcript: a bounded deferred re-check.** A lookup happens at once, then after 1, 2, 4, 8, 16, 16... s, never later than `correlate_for` = 60 s after the candidate was seen. A `SubagentStop` stores its data in the candidate, re-opens the 60 s window and asks for a lookup now. So a stop that arrives before the correlation is visible is neither a ghost nor lost: the block opens when the line appears and is finished at once with the stored stop. After the window the candidate is dropped with one debug line. Candidates are capped at 256 and reports at 256. The scheme is capped exponential backoff with a deadline; jitter is not needed because each session has one reader.
3. **Blocks.** A confirmed subagent gets one message in the topic of the parent's slot: `↳ <type> <id>: <description>` plus `в работе…`. It is posted at once, so there is something to reply to while the subagent runs. On `SubagentStop` the actor reads `agent-<id>.jsonl` and `.meta.json` off the actor and edits the block to `Subagent::render()`, whose body order is report > transcript brief > `last_assistant_message` (the library's order; the hub passes the stop's `last_assistant_message`, so a lagging file cannot look finished). A report comes from the `SubagentHandback` hook (kept per agent id until the stop). Text over 4096 UTF-16 units is cut, with a note, and the whole text goes once as `subagent-<short>.txt`.
4. **Nested runs.** A nested `claude -p` with a known parent (`Nested { parent: Some }` and the parent's slot) gets one block `⇣ nested <short id>` + `в работе…` in the parent's topic. It is created in `session_started` and reused by any later start of the same id. Its own Stop answer is not sent as a turn answer (unchanged gate) but kept. At its SessionEnd the block is edited to `⇣ nested <id>\n<answer>`, or `⇣ nested <id> · завершён` when there was none. It gets no slot, topic or channel route; that was already true and stays so. Subagents of nested runs get no block (decision logged).
5. **Persistence and restart.** Block state lives in `registry.json`: `SubagentEntry.block` and `SessionEntry.block` (nested) hold `header`, `thread_id`, `message_id`, `pending` (text Telegram should show next, cleared once accepted, like `pending_separator`), `running`, and `sending`. `busy`, `failed` and `attempts` are not persisted. `confirm_subagent` refuses a known id, so repeated hooks after a restart only edit. A first send that had no answer when the hub stopped (`sending` persisted) is never sent again: at most once, so no duplicates (acceptance 6). Deterministic end of unfinished blocks: when their session ends (SessionEnd, `/clear`, pid reuse, prune), and at hub start for sessions already ended, every block still running in it becomes `<header>\nитог не получен`. This covers subagents, the nested run itself, and nested runs whose parent ended. A result that still comes replaces the mark.
6. **Reply to a block.** In `on_topic_message`, an explicit reply (`reply_to`) to a subagent block whose `parent_session` is the slot's live current session, in the same thread, adds `target_agent=<agent_id>` to the same `Inbound` meta. It goes only to that session's agent (acceptance 5). Agent ids are accepted only as `[A-Za-z0-9_-]{1,64}` when the candidate is created, so the value is safe as an XML attribute. Replies to nested blocks, to other messages or to blocks of an older session of the slot carry no `target_agent`.
7. **Delivery.** Block sends and edits go through `hand_off` as a new `Work::Block(BlockJob)`: Send on the message lane (metered), Edit on the edit lane. There is at most one in flight per block. They are not counted against `MAX_QUEUED_MESSAGES` (like topic jobs); the overflow document is. On failure a block waits for the retry tick and is given up after 5 attempts. An edit answered `message is not modified` / `message to edit not found` / `message can't be edited` counts as done.

Research notes: the re-check is plain capped exponential backoff with a hard deadline for polling a source that catches up late. Jitter is left out on purpose: it matters when many clients compete, and here there is one reader per session. The hooks reference (https://code.claude.com/docs/en/hooks) confirms that `agent_type` is also set for `--agent` sessions, so hook fields alone cannot filter them. The Telegram Bot API `editMessageText` limit is 4096 like `sendMessage` (CLAUDE.md, verified).

Rejected: correlating by `.meta.json` `toolUseId` alone (needs the subagent file, and still has to find the parent call to prove the subagent is explicit); posting blocks only at stop (nothing to reply to while the subagent runs); keeping every typed hook in `registry.subagents` (ghost records in `registry.json`); blocks for nested runs' subagents; re-sending an unanswered first send after a restart (duplicate).

## 4. Risk areas

- **Remote devices get no subagent blocks.** Correlation and bodies read files by the hook's paths on the hub's machine. A session on another device has no readable parent transcript: its candidates expire silently and no block appears (no ghost, but no block either). Nested blocks do not need files and work everywhere. Step 5 of the dev order must bring files through the agent. Proposal filed in `PCTX_PROPOSALS.md`.
- **Correlation latency.** A block appears when the parent jsonl line is flushed, usually within seconds. If the parent writes it more than 60 s after the last hook of the subagent, the subagent gets no block (logged at debug). Large parent transcripts are read incrementally from the saved offset, so re-checks cost only new bytes. The first read of a long-running session reads up to 256 MiB once, on a blocking thread.
- **Flood budget.** Each subagent costs one metered send (+ one unmetered edit). A burst of subagents shares the group's ~20 messages/min with answers and replies. Block sends are not under `MAX_QUEUED_MESSAGES`: at most one in flight per block, but many blocks can queue in the scheduler.
- **At-most-once first send.** `sending` is saved asynchronously (save_loop), so a crash in the few ms between hand-off and save can still re-send once. The opposite case, a crash after the save with the send never delivered, loses that block. Both are rarer than the existing orphan-topic limitation (TASK-011 I3) and documented in code.
- **Memory-only pieces.** Candidates, reports, nested answers and the Agent index are lost on restart. A report handed back just before a restart is lost; the block then shows the transcript brief or the last message (library order). A candidate whose start came before the restart is created again by its stop.
- **`SubagentStop` while the parent's block is lost.** A stop after `итог не получен` replaces the text (by design); a user who already read "lost" sees the block change.
- **`registry.json` size.** Every confirmed subagent keeps its header (and, until accepted, pending text up to 4096) in the file until its parent session is pruned (`MAX_SESSIONS` 1024). Heavy subagent use grows the file, and `pump` scans all blocks on each event (O(blocks), cheap at the expected thousands).
- **Old registry files.** Entries written by TASK-011 code (`subagents` without `block`) load with an empty default block and are never posted. Unconfirmed ghosts in old files stay harmless until pruned.

## 5. Open questions

1. **Subagents of nested runs.** The plan shows none. A nested run is one `⇣ nested` block, and SendMessage from the top-level parent cannot reach its subagents. If the user wants them visible (maw runners spawn many), they would need their own blocks without `target_agent`. Default: not shown.
2. **`target_agent` for finished subagents.** The plan adds it for any block of the live session, since SendMessage continues a previously spawned agent. If only running subagents should be targetable, one filter on `block.running` in `subagent_of_message` does it.
3. **Nested run's final text.** The plan shows the nested run's last Stop answer in its block (cut to 4096, whole text as a file). If only a status is wanted (`· завершён`), drop `nested_answers`.
4. **Window length.** 60 s after the last hook of the subagent (`Options.correlate_for`). A longer window costs nothing but a timer; shorter hides slow flushes.
