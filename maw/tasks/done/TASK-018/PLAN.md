## 1. Understanding

Line numbers are HEAD `114e786`.

**The gap (premise challenge, accepted).** `hook::run` (`crates/cctg/src/hook.rs:51-75`) builds one `HookPost` and calls `post` (290-326) once; on failure it only logs "hook event not delivered". The hub never adopts a session without a SessionStart: an agent of an unknown session waits in `Slots::pending` (`hub/slots.rs:497-534`), and only `on_hook` for a known session binds it (660-670); `Registry::apply_hook` ignores `UserPromptSubmit`/`Stop` of unknown sessions (`hub/registry.rs:906-925`). So a session that started while the hub was down stays invisible for its whole life.

**What the hub already does right for a late start.** `session_started` (`registry.rs:697-830`) + `allocate` (590-659): a new top-level session takes the first free slot of its folder (`is_free`: no current session or it ended), `occupy` (661-671) writes one pending separator when the slot had another session. A `startup` start streams its transcript from byte 0 (797-805), so lines written while the hub was down still show. Hook events are deduplicated by the hook-minted `event_id` in `ingress::accept_hook` (`hub/ingress.rs:439-469`): contains + `try_send` + insert under one mutex, 4096 ids / 10 min, so concurrent copies of one event reach the actor once. No hub change is needed for "the hub takes a late SessionStart as a normal one".

**Device config.** `DeviceConfig` (`device.rs:55-98`) knows secret, hook/agent address and host, not a state dir. The hub's `CCTG_STATE_DIR` (`hub/config.rs:17-19`, default relative `.cctg`) is a hub setting read from its `.env`; hooks and agents never see it.

**Agent link.** `agent::run` (`agent.rs:113-156`) reconnects with backoff (250 ms..30 s) and re-registers; `run_stdio` (301-335) builds `LinkConfig` from `DeviceConfig`. `Register.claude_pid` is the nearest claude ancestor (`proctree::current_lineage(None, None, "")`).

**Nesting (TASK-012).** `proctree::lineage` (`proctree.rs:119-160`): the session's own claude is the nearest ancestor named `claude(.exe)` (Desktop images excluded), the parent is the next older one. Consequence for any simulation: a hook spawned from a test that itself runs under Claude Code sees the orchestrator's real `claude.exe`; all simulated sessions would get the same `claude_pid` and the reused-pid rule (`registry.rs:738-749`) would end them. The soak must build its own process tree.

**Scheduler (TASK-008).** `hub/scheduler.rs:476-551`: permission prompt first (never ahead of an older message of its own topic, stream lines excepted), edits, topic lane, messages; token bucket; any 429 pauses the whole queue `max(retry_after, 1 s)` and puts the job back at the head of its lane. Consecutive tool lines of a topic merge when more messages wait than tokens (574-618), prompts and assistant text never merge.

**Existing e2e patterns.** `tests/stream_e2e.rs` (real `cctg agent` over TCP + real `Slots`/`Scheduler` + fake `Transport`), `tests/buffer_e2e.rs`, `tests/hook_cli.rs` (real `cctg hook` with a temp home). The soak reuses their pieces: `Transport` fake, `start_hub` shape, temp `CLAUDE_CONFIG_DIR`, agent stdio init lines.

## 2. Approach

Two deliverables, in this order.

**A. Hook spool (feature).** New module `crates/cctg/src/spool.rs`, used by `cctg hook` and `cctg agent`.
- *What is kept:* only `SessionStart` and `SessionEnd`. They carry ids, pids, folder and transcript path; never prompt or answer text, never the secret (not part of `HookPost`). `Stop` answers, prompts and subagent events of a hub-less period stay lost as today (open question Q1). Decision logged.
- *Layout:* `<state>/spool/<session id>/<nanos:020>-<event id>.json`, one `HookPost` per file exactly as it was to be sent (same `event_id`, so the hub's dedup drops a copy), written as `.tmp` and renamed: the maildir scheme, a reader never sees half a file and concurrent replays never lose an event, they only send it twice ([Maildir](https://en.wikipedia.org/wiki/Maildir), [atomic file mailboxes](https://munderdiffl.in/blog/atomic-file-mailboxes-for-agents/)). Delivery is at-least-once; the hub's `event_id` dedup is the idempotency key. Session ids that are not `[A-Za-z0-9_-]{1,128}` are never written.
- *Bounds:* 16 files per session (a later event of a full session is dropped, the start stays), 256 in all, 16 KiB per file, 24 h age (expired files deleted unsent on every save and read).
- *Where:* `DeviceConfig.state_dir` = absolute `CCTG_STATE_DIR` (process env or `device.env`), else `<home>/.cctg`. A relative value is ignored: a hook runs in the session's folder.
- *Replay by hooks:* every hook of the session first sends that session's kept events in order, then its own. It stops at the first failure and then does not send its own event (it would overtake the kept start); the own event is kept if it is a start/end. Replay and the own POST share the existing POST timeout as one deadline, so a down hub costs a hook exactly what it cost before (SessionEnd stays inside its 1.5 s); a slow hub pushes the own start/end into the spool instead of losing it.
- *Replay by the agent:* after every successful registration the agent spawns one replay of its session's spool (5 s budget) to the hub's hook endpoint. The fifth session then becomes known within the agent's reconnect backoff after the hub returns, without waiting for the user's next prompt. A hook replaying at the same moment only sends duplicates; the hub keeps one. Decision logged (alternatives: hook only; device-wide replay).
- *Why this is safe for the registry:* a late SessionStart is replayed only by its own session's hook or agent, both alive only while that claude process lives, so its pid cannot have been reused yet (the reused-pid rule would otherwise end another session). A duplicate SessionStart of a live session is idempotent (`allocate` returns its own slot, `occupy` writes no separator).

**B. Soak harness (chore).** `crates/cctg/tests/soak.rs` as a `harness = false` test target (`[[test]]` in `crates/cctg/Cargo.toml`): it runs only with `-- --ignored` and otherwise prints `soak: skipped`, so `cargo test --workspace` stays fast. The same binary re-executes itself by env role:
- *Claude Code stand-in:* the test copies itself to `<tmp>/bin/claude.exe` and starts each session through a *launcher* (role `launch`) that starts the stand-in (role `claude`) with inherited stdio and exits at once. The stand-in's parent is gone before any hook runs, so the process tree above a top-level session ends at the stand-in even when the test runs inside Claude Code. The stand-in runs `cctg hook <Event>` and `cctg agent` as its children with the env Claude Code sets (`CLAUDE_PID` = own pid, `CLAUDE_CODE_SESSION_ID`, `CLAUDE_CODE_ENTRYPOINT`, `CLAUDECODE=1`), relays the agent's JSON-RPC output as `@@<json>` lines and forwards `rpc` lines to the agent's stdin. The nested `claude -p` is a script-mode stand-in started by the A1 stand-in, so the real hook's tree walk finds A1 as parent (verified: `registry.json` shows `{"kind":"nested","parent":A1}`, mutation M13 proves the check matters). The agent's `Register.claude_pid` equals the hook's `claude_pid`, as in reality.
- *Hub:* the real `serve_hooks`, `serve_agents`, `Slots`, `Scheduler` and `updates::poll` on fixed loopback ports with a temp state dir; stop = abort the tasks, restart = rebind the same ports and load `registry.json`.
- *Telegram:* one `Tg` transport records every call (time, hub run, kind, topic, text, message id, outcome). Fake mode numbers topics (100..) and messages, answers `editForumTopic` with a `forum_topic_edited` update that goes through the real `updates::poll` and `route`, and answers 429 (`retry_after` 1 s) on the 3rd and 12th stream send after the burst starts. User messages and button presses are fake `getUpdates` items from an allowlisted user. Live mode (`CCTG_SOAK_LIVE=1`) wraps the real `BotApi` (which implements `Transport` and `UpdateSource`), reads `.env` itself through `Config::load` (values never printed), takes icons from `getForumTopicIconStickers`, uses the real bucket, forwards only service messages from `getUpdates` and injects user messages/presses as `Control` with ids that name no real message; waits are 10x longer.
- *Scenario:* A1, A2 (folder A), B1 (folder B) start in order with the hub up; routing both ways (topic message -> only its agent; `reply`, `Stop` answer, transcript lines -> own topic); nested run inside A1; burst (A #2: 30 typed prompts + 30 tool calls, B: 12 prompts; typed prompts because tool lines merge and would not build a queue, logged as dead end) with two 429s and two permission requests (A: other topic, A #2: own topic behind its stream), presses Allow/Deny reach only their agents; A1 ends, hub stops, A5 starts (its SessionStart is spooled, 1 file), A5's agent starts and retries, transcript lines written while down, hub returns, A5's `UserPromptSubmit` replays (or the agent does, whichever is first); A5 takes slot 0 (`[host] A`) with one separator, all agents bound again, routing after restart.
- *Checks:* exactly 3 `createForumTopic`; exactly one separator in all topics; every text that names a session is in that session's topic (nested and A5 belong to topic A); every agent got only its own inbound; every `forum_topic_edited` was deleted; each 429 is followed by no call for `retry_after` and exactly one successful retry of the same op; metered sends per hub run within `capacity + window/refill + 1` for any 1/3/60 s window and never closer than `min_gap`; FIFO of the burst within its topic; the prompt of A #2 overtook stream lines of its own topic queued before it; `registry.json` field by field (3 slots with host, folder key/name, ordinal, topic id, current session, applied title and alive icon, no pending separator, no buffer; 5 sessions with kind, slot, ended and `claude_pid` = stand-in pid; nested entry with parent A1 and A's slot; `pids` = exactly A2, B1, A5).
- *Report:* markdown printed to stdout (and to `CCTG_SOAK_REPORT`): accepted calls per Bot API method (send / permission / stream / document / edit / react / callback / createForumTopic / editForumTopic / deleteMessage), topics, separators, service messages shown/deleted/left, 429 count, permission latencies (marked when a 429 pause was running), stream lines vs messages, bucket peak; edits are explicitly not compared with the 20/min message limit (no published number; [grammY flood limits](https://grammy.dev/advanced/flood) and the TASK-008 rule: pause everything on 429, [grammY auto-retry](https://grammy.dev/plugins/auto-retry)). `docs/soak.md` (Russian, like `docs/poc.md`) documents both modes, the live checklist and the report template.

## 4. Risk areas

- **Spool privacy.** Files hold the folder and transcript path of a session under `~/.cctg` (same data as `registry.json` on the hub). Never logged; stderr lines are fixed text (checked in `spool_e2e`).
- **Duplicates after a hub restart.** Dedup lives in hub memory for 10 min. A file whose delivery was not recorded (crash between the 204 and the delete) is sent again after a hub restart: harmless for a start of a live session (idempotent), and an end is only replayed by hooks of a session that ended, which do not come. A late start replayed after its own end cannot happen through the session's own hooks.
- **Lost `SessionEnd` of a session that ended while the hub was down** is kept but never replayed (no later hook of that session): its slot looks busy until pid reuse. Pre-existing behaviour, now at least on disk; Q2.
- **Hook latency.** With the hub up, each kept event is one more loopback POST inside `UserPromptSubmit`'s 300 ms; at most 16 per session.
- **Concurrent replays** (hook + agent) send duplicates; `accept_hook` dedups atomically. Two processes deleting the same file: `NotFound` ignored.
- **Windows file quirks.** An AV lock can fail the rename; the event is then logged as "not kept" (lost as before).
- **Soak process tree.** The launcher trick depends on the stand-in's parent being gone before a hook's ToolHelp snapshot (the harness waits for the launcher to exit first). A reused launcher pid fails the creation-time check. On Linux orphans move to init. If the trick ever stopped working, top-level stand-ins would look nested with an unknown parent and the soak would fail loudly (no topics), not pass silently.
- **Soak leftovers.** A failing run leaves `%TEMP%/cctg-soak-<pid>` (the stand-ins exit on stdin EOF when the test process dies; the folder stays). A passing run removes it. No process leaks observed (checked with `Get-Process claude,cctg` after the runs).
- **Live pass side effects.** It consumes real `getUpdates` (a running hub would get 409 and user messages sent meanwhile are acknowledged by the test), creates three `[soakbox]` topics that must be deleted by hand, and its synthetic reactions/callback answers get 400s. Never run by the implementer.
- **Big test file.** `soak.rs` is ~1600 lines after rustfmt, `scenario` alone ~560; a reviewer may ask to split phases into functions. Kept linear because the phases share many locals.
