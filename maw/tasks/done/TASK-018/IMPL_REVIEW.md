- `Drop` повторяет удаление до 50 x 20 мс. Каталог никто не пересоздаёт: `RegistryStore::save` делает `File::create(&temp)` без `create_dir_all` (`hub/registry.rs` около строки 1574).

Итог: контрпример не подтвердился. После полного `cargo test -p cctg --lib` (407 passed) в `%TEMP%` 0 каталогов `cctg-test-*`.

Мои прогоны: один `CARGO_TARGET_DIR` в `%TEMP%`, `DEBUG=0`, `-j 1`, `--offline`, каталог потом удалён.
- `cargo test -p cctg --lib -- spool hook:: agent:: device:: testdir`: 50 passed. Полный `--lib`: 407 passed, 1 ignored.
- `--test spool_e2e`: 4 passed.
- `--test soak -- --ignored` (fake): `soak: ok`, 15.4 с, 102 вызова, 3 createForumTopic, 1 разделитель, 13 из 13 service messages удалены, 2 x 429.
- `cargo clippy -p cctg --all-targets -D warnings`: чисто. `cargo fmt --all --check`: чисто. Полный workspace смотрел по `scratch/implementer/workspace_test.txt`: все цели зелёные.

По коду:
- Спул (`crates/cctg/src/spool.rs`). Хранятся только `SessionStart`/`SessionEnd` (`keeps`, стр. 69). Секрета нет в `HookPost`; тест `the_spool_holds_no_text_and_is_bounded` сверяет точный набор ключей файла. Id сессии проходит только если это `[A-Za-z0-9_-]{1,128}`: `..` и разделители путей не пройдут (стр. 76-83). Запись идёт так: `.tmp` через `create_new`, потом `write_all`, `sync_all`, `rename`; если что-то упало, `.tmp` удаляется (стр. 190-206). Мёртвый `.tmp` старше `TMP_GRACE` удаляется, свежий не трогается (стр. 134-148). Порядок задаёт имя `<nanos:020>-<event_id>`. Replay удаляет файл только после 2xx и на первой ошибке останавливается (стр. 236-259). Перебор границ при гонке описан в module doc и проверен тестом `concurrent_saves_overshoot_a_bound_by_at_most_one_file_each`.
- Идемпотентность. Hub дедуплицирует по `event_id`. Проверка и вставка идут под одним `Mutex` (`hub/ingress.rs`, `accept_hook`), поэтому два одновременных replay одного файла дают одну доставку. E2e подкладывает доставленный файл обратно и проверяет, что второй копии нет.
- Хук (`hook.rs`, `deliver`). Один deadline на replay и своё событие. Если сохранённое событие не ушло, своё не отправляется (`?` на стр. 124), а 503 проверен с честными `\r\n`. Wall-clock при молчащем hub измерен на настоящем `cctg hook SessionEnd` с 15 файлами: меньше 1.5 с, одно соединение. Stdout пуст, stderr состоит из фиксированных строк без id и пути.
- Агент (`agent.rs`, `spawn_replay`). Replay запускается после каждой регистрации и только один за раз (`is_finished`, тест `one_replay_runs_at_a_time`). Wire не меняется. Hub привязывает агента из `pending` к сессии на позднем `SessionStart` (`hub/slots.rs:667`).
- `CCTG_STATE_DIR` (`device.rs`): берётся только абсолютный путь, иначе `<home>/.cctg`. Тест `the_state_dir_is_absolute_or_under_home`.
- Soak (`tests/soak.rs`). Дублёры `claude.exe` стартуют через launcher, который сразу выходит, поэтому цепочка над top-level обрывается. Вложенный дублёр это ребёнок A1, и `nested{parent: A1}` находит сам `cctg hook`. Вызовов планировщика нет в `synthetic`: в live на реальный транспорт уходят только операции над своими темами (удаление service messages hub делает только по `slot_by_topic`). Токен не печатается: ошибки `delete_topics` отбрасываются непрочитанными. Cleanup при панике есть: сценарий идёт в отдельной задаче, есть `Drop for Hub`/`Sim`, потом удаление тем и `resume_unwind`. Реестр проверяется с точными наборами ключей.
- Каждое утверждение закрывает свою строку приёмки. Три темы: `create_topic == 3` до и после фазы 5. Разделитель один, только в `t_a`. Перепутанных маршрутов нет: сессия видна только в своей теме, а входящее каждого агента содержит его id. После 429 вся очередь молчит не меньше `retry_after`, повтор ровно один. Permission обгоняет свои строки: `behind_a2 > 0`, задержки попадают в отчёт. Отчёт считает операции раздельно и без сравнения с 20/мин. `forum_topic_edited` не остаётся ни одного.
- Продуктовый код тронут по минимуму: `device.rs`, `hook.rs`, `agent.rs`, новый `spool.rs`, строка в `lib.rs`. Всё это нужно для спула из дополнения к задаче. `hub` не менялся, `testdir.rs` существует только под `#[cfg(test)]`. Новых крейтов нет.

## 3. Issues

1. **minor**, `crates/cctg/tests/soak.rs:745` (`OffsetStore::open(&self.state)` на свежем state) и `docs/soak.md`, шаг 1. В живом режиме `updates::poll` стартует без offset. Он читает и подтверждает весь хвост непрочитанных апдейтов за 24 ч, а не только апдейты времени прогона. Пропадают и сообщения, которые пользователь написал в свои темы, пока штатный hub стоял до прогона. Штатный hub их уже не увидит и не положит в буфер слота. Документ говорит только "во время прогона". Что сделать: написать в docs точно ("все непрочитанные апдейты, включая написанные, пока hub был остановлен") и советовать запускать soak сразу после остановки hub. Второй вариант: брать стартовый offset из `offset` штатного hub.
2. **minor**, `crates/cctg/tests/soak.rs:1308` (`tg.arm_flood(&[3, 12])`). Первый запланированный 429 попадает почти в момент записи permission-запросов. В моём прогоне задержки вышли A 1007 мс и A #2 1053 мс ("includes a 429 pause"), у исполнителя 15/61 мс. Записанная задержка в основном измеряет паузу 429, а не приоритет permission. Строка приёмки "задержка измерена и записана" формально выполнена, но число почти ничего не говорит. Что сделать: поставить 429 после отправки обоих prompt (arm после `wait_for("both permission prompts")`) или сдвинуть смещения так, чтобы окно `t0..p_a2` не попадало на паузу.
3. **minor**, `crates/cctg/tests/soak.rs:945-1079`. Защищённая от паники часть начинается только с `tokio::spawn(scenario)`. Если упадёт подготовка (`copy the stand-in`, в live `Config::load`/`getMe`/`getChatMember`/проверка прав), в `%TEMP%/cctg-soak-<pid>` останется каталог с копией бинарника. Тем в этот момент ещё нет, так что это только мусор на диске. Что сделать: RAII-guard на `root`, созданный сразу после `create_dir_all`.

## 4. Missing coverage

- Нет теста на "hub вернулся, пока `SessionStart`-хук ещё ждал свой timeout". Агент мог зарегистрироваться и сделать replay до того, как хук сохранил файл. Тогда сессия остаётся невидимой до своего следующего хука: агент повторяет replay только после новой регистрации. Окно не больше 500 мс. Достаточно записать это в известные ограничения рядом с остальными.
- Живой режим не запускался (так и задумано). Пункты приёмки про настоящий Telegram (реальные 429, реальные `forum_topic_edited`) пока подтверждены только фейком.
- Нет теста, что `SessionEnd` прошлого запуска, сохранённый в спуле, при `claude --resume` той же сессии уходит раньше нового `SessionStart(resume)` и не гасит новый запуск. По коду это так: порядок replay плюс проверка `claude_pid` в hub. Но пути это ни один тест не проходит.

## 5. Nits

- `hook.rs:90-93`: без `state_dir` для `Stop`/`UserPromptSubmit` пишется "not delivered and not kept: spool write failed: NotFound", хотя такие события вообще не хранятся. Лучше сначала проверить `spool::keeps` и выдать `NotKept`.
- `spool.rs:218-220`: `pending` читает файл целиком и только потом сравнивает размер с `MAX_FILE`. Лучше проверить `metadata().len()` до чтения.
- `spool.rs:248`: `PostError::Timeout(Duration::ZERO)` печатается как "within 0ns". Лучше передавать исходный бюджет.
- `CCTG_STATE_DIR`: hub принимает относительный путь (от своей cwd), устройство его игнорирует. Одна переменная ведёт себя по-разному, это записано только в doc `DeviceConfig.state_dir`.
- `spool.rs:113`: порядок и возраст считаются по `SystemTime`, поэтому если часы уйдут назад, порядок replay сломается. Практически не важно, но в module doc можно одной строкой упомянуть.
