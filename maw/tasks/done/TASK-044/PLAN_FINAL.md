## 1. Summary

На Linux, WSL и macOS `cctg run` (родитель claude, TASK-040), когда его stdin и stdout это терминал, держит claude в собственном псевдотерминале: терминал пользователя в raw-режиме, байты идут насквозь в обе стороны (Ctrl+C, Esc, Ctrl+Z доходят до claude байтами), размер окна повторяется по SIGWINCH, копия экрана ведётся эмулятором `vt100`. На каждый запуск claude новый pty (`openpty` с режимом и размером терминала пользователя, `setsid` + `TIOCSCTTY` в `pre_exec`, оба конца `FD_CLOEXEC`). Агент получает копию экрана и пишет ввод через локальный сокет `<state>/run/<pid cctg run>.sock` (папка 0700, сокет 0600) замороженным протоколом из двух запросов (`"screen"`, `{"keys": "..."}`); вся логика «что на экране и что набирать» остаётся в агенте (`keys.rs`, общий код с Windows через трейт `Terminal`), `cctg run` остаётся тупым. Агент объявляет `console_keys/console_commands`, только если его claude запустил именно этот `cctg run` (`launched_by`) и сокет отвечает; иначе hub отвечает как сейчас (новый текст `NO_CONSOLE_NOTICE`). macOS получает обход процессов (`proc_pidinfo`, `proc_pidpath`, `proc_listallpids`), нативный claude под именем-версией распознаётся по пути `.../claude/versions/<v>`. Вариант tmux не делается (решение orchestrator). Windows-путь не меняется; без терминала (`-p | jq`, тесты) `cctg run` работает как раньше.

## 4. Rollout notes

- Миграций, флагов, новых env нет. Протокол hub <-> agent не меняется (`wire::VERSION` тот же), hub можно обновлять независимо.
- Новый файл состояния: `<CCTG_STATE_DIR|~/.cctg>/run/<pid>.sock` (папка `run/` 0700). После SIGKILL `cctg run` файл остаётся; следующий `cctg run` с тем же pid его заменяет, чужой агент к нему не подключается (агент берёт только сокет своего `CCTG_RUN`, прошедшего `launched_by`).
- Обновление: уже запущенные `claude-cctg` работают на старом `cctg run` без pty и сокета; агент нового бинарника у такой сессии консоль не объявляет (как сейчас на Linux). Консоль появится после перезапуска `claude-cctg` новым бинарником. «Обновить» на Linux/macOS в такой старой сессии по-прежнему недоступен (restartable = false), это не регресс.
- Формат сокета заморожен (`the_ask_format_is_frozen`): `cctg run` не обновляется на лету, агент обновляется. Новый запрос в будущем добавляется только как новый вариант, и агент обязан считать отсутствие ответа «старый `cctg run`, не умеет».
- Зависимости: `vt100 0.16.2` (MIT, чистый Rust, тянет `vte 0.15`, `arrayvec`, `unicode-width`), `libc` уже в lock. Сборка релиза: linux-musl (Docker, `openpty` есть в musl), aarch64-apple-darwin, windows-msvc.
- Совместимость с TASK-050: слит в `main` (239dbcf) до этого плана; эталон собран против 239dbcf, патч применяется без конфликтов. Относительно патча планировщика изменились только хеши `agent.rs`, `lib.rs`, `docs/remote-hub.md` (контекст TASK-050) плюс файлы правок ревьюера.
- Известные ограничения (не чинить в этой задаче):
  - `cctg run`, убитый SIGKILL (или SIGQUIT), оставляет терминал в raw-режиме (лечится `reset`), как любая TUI; если он убит, пока claude остановлен Ctrl+Z, claude остаётся остановленным.
  - Клавиши, набранные до старта первого claude (type-ahead), и между выходом claude и перезапуском, пропадают.
  - Процесс, унаследовавший slave pty и переживший claude (фоновая задача вне группы claude), продолжает печатать в окно через старый поток реле до своего выхода (на Linux; macOS отзывает терминал).
  - Если терминал пользователя остался с `O_NONBLOCK` от чужой программы, реле ввода завершится на `EAGAIN` (консольные кнопки и клавиатура перестанут доходить до claude до перезапуска `claude-cctg`).
  - Claude Code, установленный через npm на macOS, идёт как `node`: `claude_pid` не находится, консоль, перепривязка и распознавание вложенных запусков для него не работают (нативная установка работает).
  - Длинный `CCTG_STATE_DIR` (`sun_path` 104 байта на macOS, 108 на Linux) = строка «no terminal socket» и работа без консольных кнопок; диалог каналов всё равно отвечается.

Проверено и оставлено как есть (с доказательством):
- `pre_exec`: в std замыкания выполняются после `dup2` stdio и после сброса маски сигналов и SIGPIPE, поэтому `ioctl(0, TIOCSCTTY)` действует на slave; в замыкании только `setsid`/`ioctl`. Копии slave в родителе закрываются при выходе из замыкания `spawn`. `try_clone` = `F_DUPFD_CLOEXEC`, сокеты std = CLOEXEC.
- Claude Code на Ctrl+Z шлёт себе именно SIGSTOP (стек `handleSuspend -> process.kill(..., 'SIGSTOP')`, anthropics/claude-code#4035), поэтому осиротевшая группа claude его не теряет; SIGTSTP ядро бы выбросило.
- Linux: запись в master без открытого slave даёт EIO (`n_tty_write`: `tty->link->count == 0`), `Host::write` не виснет с замком между запусками; macOS `ptcwrite` без `TS_CONNECTED` тоже EIO. Замки `master` и `screen` никогда не берутся вложенно.
- Выход лидера сессии: Linux для pty не делает hangup (`disassociate_ctty` пропускает PTY), macOS отзывает терминал, но сперва ждёт слива вывода (`ttywait`), поэтому последний вывод claude не теряется, пока `relay_output` читает. Новый pty на каждый запуск нужен и правилен.
- UTF-8 через границу чтений: `vte 0.15` держит незаконченный символ между `process`; агент режет текст по символам.
- `clippy::print_with_newline` на `eprint!("{text}\r\n")` не срабатывает (два символа перевода строки); `as _` у `TIOC*` не даёт `unnecessary_cast` (проверено unixcheck).
- Размер `MAX_ASK`: самый длинный запрос это 200 символов BMP (до 600 байт UTF-8) или 200 DEL, влезает с запасом.
- Windows: `Attached` повторяет прежний порядок Win32-вызовов и тайминги; ответ на диалог и `run_e2e` без изменений (тесты на Windows зелёные).
