## 2. Approach

**Статус.** Одно сообщение на слот, `Slot.status: Option<StatusMessage { message_id, pinned }>` в `registry.json` (пропускается, когда пусто). Создаётся только для живой текущей сессии слота и после её разделителя, закрепляется один раз (`pinChatMessage`, `disable_notification`), служебное `pinned_message` удаляется только если оно про наше сообщение. Первая строка — эмодзи и пара слов: `🏁 Сессия завершена` / `❓ Ждёт разрешения` / `⚙️ <brief-строка идущего вызова> (+N)` / `💭 Думает` / `💤 Ждёт вас`. Вторая строка — цифры statusline: `Opus 5.5 (1M context) · medium · ctx 50% · 5h 3% · 7d 92%` (только известные части). Правки идут `Op::Edit` не чаще `Options::status_every` (в hub 5 с; по умолчанию `None` = статус выключен, чтобы существующие тесты actor-а не менялись), кроме правки сразу после нажатия кнопки. Удалённое в Telegram сообщение (`message to edit not found`) отправляется и закрепляется заново; сменённая тема сбрасывает `status`.

**Откуда «что делает сессия».** `UserPromptSubmit` → ход идёт; `Stop` → ход закончен; новый хук `cctg hook ToolStatus` на `PreToolUse`/`PostToolUse`/`PostToolUseFailure` с `"async": true` → какие вызовы главного разговора идут сейчас (транскрипт это сказать не может: в интерактивной сессии `tool_use` пишется только после конца инструмента, TASK-016); permission prompts → `SessionEntry.waiting`; конец сессии → registry. Ход после Esc заканчивается по ответу агента (`console_key_done ok`) или по заметке `[Request interrupted by user` в потоке (Esc в терминале), заметка учитывается один раз на байт транскрипта, так что перечитывание после rewind не гасит новый ход. Async-хук может прийти после своего конца: `Activity` помнит 64 закончившихся id. Вызовы внутри субагентов (`agent_id` в input) хук отбрасывает до POST.

**Цифры.** `cctg statusline` — `statusLine.command` cctg-сессий. Берёт поля из stdin (терпимо к `null`, отсутствию и чужим типам), шлёт одно событие `status_line` через существующий hook endpoint (тот же секрет и `device.env`, бюджет 150 мс), параллельно запускает `statusLine.command` из пользовательских настроек (`$CLAUDE_CONFIG_DIR/settings.json`, иначе `~/.claude/settings.json`, читается на каждом вызове) с тем же stdin через тот shell, что и Claude Code (`CLAUDE_CODE_GIT_BASH_PATH`, затем `SHELL`, если это файл `bash.exe`, затем `EXEPATH\bash.exe`, затем `bash.exe` рядом с `git.exe` из PATH, иначе `powershell -NoProfile -Command`; не на Windows `sh -c`) и печатает его вывод. Без своей команды печатает `model · ctx N% · 5h N% · 7d N%`. Рекурсия закрыта `CCTG_STATUSLINE=1` в env дочерней команды. Клиентского троттлинга нет: Claude Code сам дебаунсит вызов (300 мс) и зовёт его раз на сообщение ассистента, темп правок держит hub.

**Кнопки.** ⏹ `status:stop` → кнопка превращается в «⏹ Точно прервать?» (`status:confirm`) на 10 с; второе нажатие шлёт агенту `HubMsg::ConsoleKey { key_id, key: Interrupt }`. ⏬ `status:bg` (только при `background_button`) шлёт `Background` сразу. Нажатие действует только на слот своего сообщения (поиск по `message_id` нажатого сообщения), только на его живую текущую сессию и только через её привязанного агента, объявившего `Register.console_keys`. Allowlist уже проверен в `updates::classify`. Агент отвечает `AgentMsg::ConsoleKeyDone { key_id, ok }`; `ok` для Esc сразу заканчивает ход в статусе, `!ok` даёт одно уведомление в тему (через `notify`, не чаще раза в минуту). Мёртвая сессия, чужое сообщение, агент без ключей, «нечего прерывать» получают только текст ответа на кнопку.

**Агент.** `keys.rs`: `FreeConsole` + `AttachConsole(claude_pid)` + `CreateFileW("CONIN$")` + `WriteConsoleInputW` (down+up) + `FreeConsole`, под глобальным mutex (консоль одна на процесс), `SetConsoleCtrlHandler(None, TRUE)` чтобы Ctrl+C пользователя в момент attach не убил агента. Только Windows (`keys::SUPPORTED`), только при известном `claude_pid`; иначе `console_keys: false` и кнопок нет. Не на Windows поддержки нет (TIOCSTI в современных ядрах закрыт; задокументировано).

Почему так: всё новое на проводе за capability или новыми видами hook-событий (старый hub ответит 400 на новый вид, хук `ToolStatus` асинхронный, statusline не ждёт ответа); статус живёт в actor-е без новых задач и блокировок; сообщение одно и закрепляется один раз (минимум metered-отправок, лимит 20/мин на группу); edit-ы коалесцируются scheduler-ом и дополнительно ограничены темпом на слот.

## 4. Risk areas

- **Esc в неудачный момент.** Esc при открытом диалоге закрывает диалог, на permission prompt равен «No» (дока interactive-mode). ⏹ показывается только когда сессия занята (ход, вызов или ждущий prompt); при «❓ Ждёт разрешения» ⏹ = отказ в разрешении, это ожидаемо, но стоит сказать пользователю. Если hub пропустил `Stop` (hub лежал), статус может считать сессию занятой, и Esc уйдёт в простаивающий claude: одиночный Esc при пустом вводе ничего не делает, при набранном тексте в терминале его не стирает (стирает двойной).
- **Терминалы.** Проба шла в классической скрытой консоли conhost. В Windows Terminal / VS Code claude сидит в ConPTY; `WriteConsoleInputW` пишет в тот же входной буфер conhost, ожидается то же поведение, но живьём не проверено. Git Bash через mintty без ConPTY консоли не даёт вовсе: там `AttachConsole` упадёт, агент ответит `ok: false`, в тему уйдёт уведомление.
- **Attach консоли процессо-глобален.** Во время нажатия агент прицеплен к консоли claude (миллисекунды); Ctrl+C игнорируется (`SetConsoleCtrlHandler`). Своя консоль агента после `FreeConsole` не возвращается: stdio агента — пайпы, консоль ему не нужна.
- **Ctrl+B не проверен** (раздел 0). Флаг выключен; включение = `background_button: true` в `hub/mod.rs` после пробы. С 2.1.198 субагенты по умолчанию фоновые, поэтому ⏬ осмысленна в основном для Bash.
- **Async-хуки.** Порядок `Pre`/`Post` не гарантирован (закрыто памятью закончившихся id); поздний `ToolStart` после `Stop` покажет «⚙️» до следующего события; `PostToolUse` при отмене инструмента Esc может не прийти (дока: отмена не стреляет `PostToolUseFailure`) — после ⏹ список вызовов чистится по ответу агента. Цена: по 2 процесса на вызов инструмента в фоне, ~10 мс с живым hub, ~313 мс с лежащим, Claude Code их не ждёт (`P/hook_cost.out.txt`).
- **statusline медленнее при лежащем hub.** Своя строка: ~10 мс с hub, ~170 мс без (POST ждёт 150 мс, процесс выходит после него). С командой пользователя время почти целиком её (замер с `echo`: ~35 мс). Если окажется заметно, снизить `POST_TIMEOUT` до 100 мс. Отменённый Claude Code запуск statusline может оставить дочернюю команду пользователя доработать (на Windows убийство родителя детей не убивает); команда пользователя короткая, риск принят.
- **`pinned_message` от бота в `getUpdates`.** Предполагается, что приходит так же, как `forum_topic_edited` (проверено для него в CLAUDE.md), с `message_thread_id` темы; удаление ищет наш статус по id закреплённого сообщения, тему не требует. Нужна живая проверка; если не приходит, уведомление о закреплении просто останется (одно на слот).
- **Потерянный ответ на `sendMessage` статуса** (без ответа или 5xx) через `retry_every` даёт второе сообщение; первое останется незакреплённым. Как в известном ограничении TASK-011 для тем.
- **Restart hub.** Метрики и «что делает» живут в памяти: после рестарта первая правка покажет «💤 Ждёт вас» без цифр до следующего события/statusline. Закрепление и id сообщения переживают рестарт.
- **Нагрузка.** `pump_status` рендерит статус каждого слота на каждом событии actor-а: десятки слотов, строки короткие, без IO. Правки одного слота не чаще раза в 5 с.
