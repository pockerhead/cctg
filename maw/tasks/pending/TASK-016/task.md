# TASK-016: hub — live turn streaming into the slot topic

Type: feature
Mode: full
Priority: high
Branch: feature/hub-turn-streaming
Domains: hub, transcript

## Description
Закрыть решение пользователя «push every turn через outbound queue»: hub следит за локальным транскриптом сессии по `transcript_path` (tail по смещению, только целые строки), скармливает новые записи в `transcript` и отправляет каждый завершённый turn в brief-виде в тему слота через планировщик. Финальный текст ассистента на `Stop` берётся из полей хука, а jsonl используется как история и может отставать. Смещение хранится в реестре, чтобы рестарт hub не переотправлял уже отправленное. Удалённые устройства (агент отдаёт файл) — вне этой задачи, это шаг 5 плана.


UX-решение пользователя (2026-09-23, после живого PoC), дополняет описание выше:
- Отметка прочтения: когда hub отдал сообщение пользователя агенту сессии, бот ставит на это сообщение реакцию 👀 (`setMessageReaction`); на `UserPromptSubmit` этой сессии реакция меняется на ✍️. Отдельных сообщений не шлётся.
- Каждый завершённый вызов инструмента (есть `tool_use` и его `tool_result` в транскрипте) уходит в тему отдельным сообщением в одну строку в brief-виде (`Bash: описание ✓`, `Edit: файл ✗ ошибка`), в порядке вызовов. Промежуточный текст ассистента и финальный ответ хода тоже отдельными сообщениями. Стриминга токенов нет.
- Лимит 20 сообщений/мин на группу: пока очередь не упирается в лимит, каждый вызов отдельным сообщением; при упоре накопившиеся строки вызовов одной темы склеиваются в одно сообщение (порядок сохраняется, ничего не теряется).

- Архитектурное решение (2026-09-23): tail транскрипта делает агент сессии (он всегда на том же устройстве, что и jsonl) и шлёт новые записи или готовые строки в hub по существующему agent-линку; hub рендерит и отправляет. Так второе устройство работает без чтения файлов по сети. Финальный ответ хода уже отправляется из хука `Stop` (TASK-022), поэтому поток из транскрипта не дублирует его.

- Развилка источника строк вызовов (решить в плане по замеру, 2026-09-23): (a) tail транскрипта агентом — грубый замер на живой сессии дал задержку появления записи в jsonl около 4–7 с после её timestamp (Claude Code пишет пачками); (b) хуки `PreToolUse`/`PostToolUse` — мгновенно, несут `tool_name` и `tool_input`/`tool_response`, но это процесс `cctg hook` на каждый вызов инструмента (~20–40 мс с живым hub, ~300 мс при выключенном hub, влияет на скорость работы агента). Planner замеряет лаг транскрипта на живом прогоне и выбирает источник (возможна комбинация: хук для мгновенной строки, транскрипт для истории/бэкфилла), решение записывается в OPEN_DECISIONS.

## Acceptance criteria
- [ ] дописывание строк в тестовый jsonl приводит к отправке соответствующих turns в тему нужного слота в правильном порядке
- [ ] частично записанная последняя строка никогда не отправляется и не теряется: она уходит следующей итерацией целиком
- [ ] рестарт hub не переотправляет уже отправленные turns (смещение персистится) и не теряет дописанное во время простоя
- [ ] поток turns подчиняется планировщику (20/мин на группу, FIFO в теме) и уступает permission-трафику
- [ ] ротация сессии в слоте начинает новый поток с новым смещением и пишет разделитель ровно один раз
- [ ] отсутствующий или удалённый файл транскрипта не ломает hub: одно предупреждение, поллинг продолжается
- [ ] сообщение пользователя, переданное агенту, получает реакцию 👀, а при старте хода сессии ✍️; ошибка реакции (нет права, старое сообщение) не ломает маршрутизацию
- [ ] каждый завершённый вызов инструмента приходит отдельным сообщением одной строкой в порядке вызовов; при упоре в лимит строки склеиваются без потерь и без нарушения порядка
- [ ] замер лага транскрипта на живом прогоне записан, выбор источника строк вызовов (транскрипт / хуки Pre/PostToolUse / комбинация) обоснован этим замером
