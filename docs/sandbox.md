# Сэндбокс папки

Режим клиента cctg: сессия, запущенная через `claude-cctg` в помеченной папке, не читает и не пишет ничего вне этой папки. Работает на Linux (включая WSL2), macOS и Windows. На Linux и macOS граница держится на сэндбоксе команд Claude Code (bubblewrap / `sandbox-exec`); на Windows у Claude Code своего сэндбокса команд нет, поэтому cctg строит границу сам через отдельные скрытые учётные записи (TASK-089, ниже раздел «Windows»).

Статус проверки: пробы с настоящим Claude Code прошли на Linux в WSL2 (Ubuntu 22.04, ядро 5.15, Claude Code 2.1.285, bubblewrap 0.6.1, 2026-09-30). На macOS проб не было: всё про macOS ниже не проверено. На Windows e2e с настоящими учётками идёт в CI (`windows-latest`, администратор без UAC); живую проверку через Telegram пользователь делает один раз после `cctg sandbox-install`.

## Как включить

В папке проекта:

```sh
~/.cctg/bin/cctg sandbox on        # или --folder <путь>
```

Метка действует на папку и на всё внутри неё. Новые сессии `claude-cctg` в ней стартуют в сэндбоксе. Уже запущенные переходят после «⬆️ Обновить» в меню бота или после перезапуска.

```sh
~/.cctg/bin/cctg sandbox status    # включён ли и готово ли устройство
~/.cctg/bin/cctg sandbox off       # выключить (только там, где включали)
```

`cctg doctor` показывает число помеченных папок и готово ли устройство.

В Telegram режим не виден: ни в заголовке, ни в иконке, ни в статусе темы. Кнопка в меню появится позже (часть B).

Нужна обёртка `claude-cctg` не старее этой версии (переустановите клиент через `install.sh`): старая обёртка запустила бы claude без сэндбокса, поэтому `sandbox on` с ней отказывает.

## Windows

На Windows у Claude Code нет своего сэндбокса команд, поэтому cctg запускает каждую команду Bash под отдельной скрытой локальной учётной записью.

Один раз на устройстве (один запрос UAC):

```sh
~/.cctg/bin/cctg sandbox-install            # или --slots N (по умолчанию 8, максимум 32)
```

Это создаёт группу `cctg-sandbox` и пул скрытых учёток `cctg-sandbox-1..N` — по одной на помеченную папку. Пароли лежат DPAPI-блобами в `~/.cctg/sandbox/win`, доступ только вашей учётке Windows. Одна учётка на папку нужна, чтобы команда одной помеченной папки не могла читать и писать другую.

Помечать можно только папки **внутри `%USERPROFILE%`**: папки под корнем диска (`C:\dev\x`) и на других дисках Windows по умолчанию открывает любой учётной записи на чтение и запись. Вложенные метки запрещены — одна метка на дерево.

```sh
cctg sandbox on        # выдаёт учётке слота права на папку (на больших деревьях это минуты)
cctg sandbox status    # номер слота и готовность устройства
cctg sandbox off       # отзывает права, выводит слот из оборота
```

Нужен Git Bash (Git for Windows) вне профиля пользователя (или каталог с ним в `~/.cctg/sandbox/read-dirs`); инструмент PowerShell в сэндбоксе выключен, команды идут через Git Bash.

Как устроено: профиль сэндбокса ставит `CLAUDE_CODE_SHELL_PREFIX` на шим `~/.cctg/bin/cctg-sandbox-exec`, тот вызывает `cctg sandbox-exec "$1"`. Broker (ваша учётка, без прав администратора) пропускает напрямую только свои два вызова — stdio MCP `cctg agent` и `cctg statusline`; свои хуки cctg пишет в exec-форме, и Claude Code запускает их без префикса. Всё остальное broker запускает под учёткой слота: `CreateProcessWithLogonW` поднимает runner на приватном рабочем столе в job с kill-on-close, runner строит restricted token (Admins и logon SID только deny, привилегии сняты кроме `SeChangeNotifyPrivilege`, без restricting SIDs — они ломают Schannel) и запускает Git Bash. Изоляция держится на ACE учётки слота: `cctg sandbox on` выдаёт SID слота modify на дерево папки и запрещает запись `.git`, `.claude`, `.mcp.json`, конфигам shell и IDE. Окружение команды — профиль учётки слота плюс явный whitelist (PATH, HOME остаётся ваш, кэши и temp в папке, git-переменные), без `CCTG_*` кроме `CCTG_SANDBOX`, без токенов.

`read-dirs` даёт группе `cctg-sandbox` чтение и запуск на перечисленные каталоги программ (например `~/.cargo/bin`, `~/.rustup`).

### Что пропадает на Windows

- Хуки из `~/.claude/settings.json` в shell-форме и плагинные идут через префикс в сэндбокс и без доступа к профилю обычно падают.
- `git push` и Git Credential Manager внутри сэндбокса не работают (учётных данных у слота нет).
- Файлы с несколькими жёсткими ссылками (например store pnpm) в папке становятся только для чтения — иначе через общий дескриптор изменились бы и ссылки вне папки.
- `.git`, созданный командой в папке без репозитория, принадлежит учётке слота; git вне сэндбокса откажет («dubious ownership»). Не добавляйте его в `safe.directory`: с `safe.directory = *` ваш git выполнит его config, о чём предупреждает `cctg doctor`. `.git/config` и `.git/hooks` после первой команды только для чтения, как на Linux.

### Честные пределы Windows

- Чтение и запись каталогов, открытых Users/Authenticated Users: папки прямо под корнями дисков, другие диски, `C:\Users\Public`, `C:\ProgramData`, на части машин `C:\Windows\Temp`. Ambient deny при установке закрывает запись только в стандартном списке таких каталогов.
- Сеть и loopback открыты: служба без аутентификации на localhost (например Docker API по TCP без TLS) даёт полный выход.
- Команда может показать запрос UAC с вводом пароля администратора — не вводите пароль в запрос, который вы не вызывали.
- Неверные пароли слота при политике блокировки учёток могут заблокировать учётку слота.
- Побег из job через системных посредников (WMI, COM) не закрыт; токен при этом остаётся ограниченным.
- С включённым Developer Mode команды создают симлинки; наружу они не ведут (у цели свой ACL), но процессы вашей учётки, читающие temp в папке, их видят.
- `!`, набранный в терминале, на Windows тоже идёт в сэндбокс.

### Как удалить (Windows)

```sh
cctg sandbox-uninstall     # один UAC: снимает учётки, группу, ключ HKLM
install.sh --uninstall     # затем удаляет бинарь, шим и обёртки
```

Метки папок остаются; снимите их через `cctg sandbox off`. `install.sh --uninstall` останавливается с подсказкой, пока сэндбокс не удалён (иначе учётки остались бы, а `cctg sandbox-uninstall` было бы уже нечем запустить).

## Что нужно на машине

- Claude Code 2.1.284 или новее.
- Linux: `bubblewrap` и `socat` (`apt install bubblewrap socat`), разрешённые user namespaces. На Ubuntu 24.04 их запрещает AppArmor для непривилегированных процессов; нужен профиль для `bwrap` или `sysctl kernel.apparmor_restrict_unprivileged_userns=0` (решение за вами, это системная настройка). Рекомендуется seccomp-фильтр Claude Code (`npm install -g @anthropic-ai/sandbox-runtime`): без него командам доступны Unix-сокеты вне закрытых путей.
- WSL2: cctg не требует выключать запуск программ Windows (interop), но здесь граница держится на самом сэндбоксе ОС. Если программа Windows запустится из сэндбокса, она будет работать в Windows вне всякого сэндбокса. Проба с включённым interop (оба обработчика, `WSLInterop` и `WSLInterop-late`) показала, что `cmd.exe` из сэндбокса не запускается ни по имени, ни по полному пути, хотя `/mnt/c` читается. Проверено в одной конфигурации (выше). После крупного обновления WSL, bubblewrap или Claude Code это стоит проверить заново. Кому нужна уверенность без этой оговорки: выключите interop (`[interop] enabled=false` в `/etc/wsl.conf`, затем `wsl --shutdown`).
- macOS: `/usr/bin/sandbox-exec` (есть в системе).
- В `~/.claude/settings.json` не должно быть ключей, которые расширяют сэндбокс: `permissions.additionalDirectories`, `sandbox.filesystem.allowWrite`, `sandbox.filesystem.allowRead`, `sandbox.excludedCommands`, `sandbox.network.allowUnixSockets`, `sandbox.network.allowMachLookup` (macOS) и правил `Edit(путь)`, `Write(путь)`, `NotebookEdit(путь)` в `permissions.allow`. Массивы из пользовательских настроек складываются с профилем, и отменить их нельзя, поэтому cctg с ними отказывает и называет ключи. Флаги, которые ослабляют сэндбокс (`allowAppleEvents`, `enableWeakerNetworkIsolation`, `enableWeakerNestedSandbox`, `autoAllowBashIfSandboxed`, `network.allowLocalBinding`, `network.allowAllUnixSockets`, `filesystem.disabled`, `allowUnsandboxedCommands`), профиль ставит сам, и его значение сильнее пользовательского: с ними cctg не отказывает, они просто не действуют.
- `CLAUDE_CONFIG_DIR` не задан.

Каждый старт помеченной папки проверяет это заново. Если что-то сломалось, `claude-cctg` не запускается и пишет причину (без сэндбокса он в помеченной папке не стартует никогда).

## Как это устроено

Перед стартом обёртка спрашивает `cctg sandbox-check`. Для помеченной папки cctg пишет профиль `~/.cctg/claude/sandbox/<hash>.json`: ваш `~/.cctg/claude/settings.json` плюс:

- строгий сэндбокс Claude Code для Bash и всех его дочерних процессов (`failIfUnavailable`, без выхода из сэндбокса);
- запрет чтения вне рабочей папки для файловых инструментов (`blockReadsOutsideWorkingDirectories`);
- запрет инструментов, которые выводят за папку: `/cd`, `Artifact`, `SendUserFile`, `SendMessage`, `ListAgents`, `RemoteTrigger`, computer-use, Chrome, `DesignSync`, коннекторы claude.ai (чужие транскрипты и `~/.claude/history.jsonl` инструмент Read не прочтёт: их закрывает блок чтения);
- хук `cctg sandbox-gate`: Write, Edit, NotebookEdit и EnterWorktree только внутри папки и не в `.claude`, `.git`, `.vscode`, `.idea`, `.mcp.json`, конфиги shell; план plan mode в `~/.claude/plans` разрешён;
- очистка учётных данных из окружения команд, хуков и MCP (`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`), запрет `CCTG_*`, `GH_TOKEN`, `GITHUB_TOKEN`, `SSH_AUTH_SOCK`;
- копия gitconfig только с `user.name` и `user.email`; глобальный `~/.gitconfig` командам не виден;
- git-переменные (`GIT_CONFIG_GLOBAL` на копию, `GIT_CONFIG_NOSYSTEM`, `GIT_TERMINAL_PROMPT=0`) cctg передаёт Bash через `CLAUDE_ENV_FILE`: из `env` профиля Claude Code переменные `GIT_*` не пропускает.

claude запускается с `--strict-mcp-config --setting-sources user --no-chrome`: MCP-серверы, хуки и настройки проекта не грузятся (они работали бы вне сэндбокса).

Свои пути наружу cctg закрывает сам:

- `!` и слеш-команды из Telegram: строка с `!` в любом месте не набирается никогда. Из слеш-команд проходят только безопасные встроенные (`/compact`, `/clear`, `/model`, `/cost`, ...), встроенные скиллы, которые работают одними инструментами, и ваши скиллы из `~/.claude/skills`, `~/.claude/commands` и плагинов. `/add-dir`, `/cd`, `/config`, `/permissions`, `/mcp` и всё незнакомое отказаны, `@` в строке тоже. `/loop` отказан целиком: он потом сам запускает промпт или команду (`/loop 1m /add-dir ~`) мимо этой проверки. Строка проверяется вся, не только начало: `/слово` где угодно, похожее на опасную команду, отказывает всю строку. Ваш скилл не набирается, если опасная встроенная команда или слово в ней начинаются с его имени (скилл `add` или `dir`: меню подсветило бы `/add-dir`, и Enter запустил бы её). Ответ в теме нейтральный: «в этой папке такие команды отключены настройками папки».
- `send_file` отдаёт только файлы папки, ссылки наружу не проходят.
- Файлы из темы сохраняются только в `<папка>/.cctg/inbox/`, не во временный каталог, и не через ссылки.

Кэши инструментов для Bash лежат в `<папка>/.cctg/sandbox/` (`CARGO_HOME`, `XDG_*`, npm, Go), `CARGO_TARGET_DIR` это `<папка>/target`. `HOME` не меняется. Внутри `<папка>/.cctg/sandbox/` есть `.gitignore` со `*`.

## Если файл меток повреждён

Метки лежат в `~/.cctg/sandbox/folders.json`, каждое сохранение пишет и копию `folders.json.bak`. Нет файла или он пустой: меток нет, всё как раньше. Если файл испорчен (правка руками, диск), cctg решает по каждой папке отдельно:

- папка, которую называет испорченный файл или его копия `.bak` (или папка внутри неё), остаётся в сэндбоксе;
- папка, которую не называет ни то ни другое, стартует как обычно, если в файле ничего не могло пропасть: он кончается как целый JSON (`}`) или копия `.bak` читается. `claude-cctg` при этом пишет предупреждение;
- если файл обрезан и копии нет, если обрез пришёлся на путь, с которого начинается путь этой папки, или файл не читается совсем, решить нельзя: `claude-cctg` в такой папке не стартует, а `send_file` и консольные команды агента считаются в сэндбоксе.

`cctg doctor` и `cctg sandbox status` показывают, что с файлом. Починить: поправьте JSON или удалите файл и включите нужные папки заново (`cctg sandbox on`).

## Каталоги программ

По умолчанию командам не видны каталоги вне папки, кроме системных. Если программе нужен каталог в домашнем (например rustup и cargo), перечислите его в `~/.cctg/sandbox/read-dirs`, по одному на строку:

```
# программы, которые сэндбокс может читать
~/.rustup
~/.cargo/bin
```

Только каталоги программ. Домашний каталог целиком, каталог над ним, `~/.cctg`, `~/.claude` и всё внутри них, сама папка сессии и каталоги над ней отказаны с номером строки: через них открылись бы соседние проекты и ваши данные.

## Что пропадает в сэндбоксе

- MCP-серверы из `~/.claude.json`, `.mcp.json` проекта и коннекторы claude.ai.
- Хуки, настройки и скиллы проекта (`.claude/` папки не грузится).
- Память проекта (`autoMemoryEnabled` выключен).
- Пересылка сообщения субагенту из Telegram (`target_agent`): без `SendMessage` модель выполнит его сама.
- Авто-разрешение команд сэндбокса и режимы разрешений: очистка окружения (`CLAUDE_CODE_SUBPROCESS_ENV_SCRUB`) переводит сессию в режим `default`, так что plan mode, auto и acceptEdits недоступны, а запросы разрешений идут в Telegram.
- Worktree: `EnterWorktree` в сэндбоксе не создаёт worktree, потому что `.git` там только для чтения.
- Составные команды с `cd` (`cd sub && cargo build`) Claude Code иногда не может проверить блоком чтения и спрашивает разрешение. Команды с путём внутри папки (`cargo build --manifest-path sub/Cargo.toml`) идут без вопроса.
- Выполнение `` !`команда` `` в пользовательских скиллах (выключено: проба, закрывает ли его сэндбокс, не делалась).

## Честные пределы

- `!` и `/add-dir`, набранные вами в терминале, работают вне сэндбокса.
- Хуки и плагины из `~/.claude` (ваш конфиг) работают вне сэндбокса.
- Системные каталоги (`/usr`, `/etc`) читаются.
- Linux: без seccomp-фильтра командам доступны Unix-сокеты вне закрытых путей. `/run/user`, сокеты docker, containerd и podman закрыты.
- Temp: граница конфиденциальности на `/tmp` не распространяется. Команды сэндбокса читают и пишут `/tmp` и `/var/tmp` целиком. Закрыть их нельзя: Claude Code держит temp сессии в `/tmp/claude-<uid>`, и `CLAUDE_CODE_TMPDIR` из профиля его не переносит. Что из этого следует (Linux, пробы 2026-09-30):
  - `/tmp/claude-<uid>` общий для всех проектов пользователя: там scratchpad и вывод фоновых задач каждой сессии, в папке `/tmp/claude-<uid>/<имя проекта>/`. Запрет на весь `/tmp/claude-<uid>` Claude Code перекрывает, открывая temp сессии. Поэтому cctg при старте закрывает каждую папку других проектов, которая там уже есть. Остаются открытыми папки проектов, впервые запущенных после старта этой сессии, и отдельные файлы в корне `/tmp/claude-<uid>` (например `tmp.*` от `mktemp` других сессий).
  - Всё остальное в `/tmp` читается: загрузки и temp других программ. Запрет пути прямо в `/tmp` не действует (проба: `/tmp` открыт на запись целиком), это ограничение Claude Code. Поэтому файлы из тем Telegram, которые сессия cctg не смогла положить в свою папку, больше не лежат в temp: все сессии кладут их в `~/.cctg/inbox/<сессия>/` (или `<CCTG_STATE_DIR>/inbox/<сессия>/`), доступ только владельцу (0700/0600), а сэндбоксу этот каталог не виден.
  - Список закрытых папок других проектов записывается в профиль при старте. Если потом появится новый проект, профиль перепишется при следующем старте в этой папке, но из-за этого «⬆️ Обновить» уже запущенные сессии не перезапускает. Перезапуск будет, только если изменилось что-то ещё: сам профиль (allowlist, метка) или `~/.cctg/claude/settings.json`.
- Claude Code сам кладёт в папку пустые файлы-заглушки для точек монтирования сэндбокса (`.env*`, `.npmrc`, `.yarnrc*`, `.gitmodules`), и внутри сэндбокса на месте `.bashrc`, `.gitconfig`, `.mcp.json` и подобных видны устройства. Поэтому `git add -A` в сэндбоксе падает («can only add regular files»): добавляйте файлы явно. Заглушки после сессии можно удалить.
- `GH_TOKEN` доходит до хуков и MCP-серверов (они работают вне сэндбокса), но не до команд Bash.
- macOS: `/tmp` читается; список процессов виден (не проверено пробой).
- Сеть открыта.
- Общий `.git` связанного worktree пишется через worktree.
- Код папки, который вы сами запускаете вне сэндбокса (`build.rs`, `Makefile`, кэш cargo из `.cctg/sandbox`), выполняется без ограничений.
- Если удалить бинарник cctg, хук gate не запустится, и Claude Code пропустит запись файловым инструментом (сам сэндбокс команд остаётся).
- Подмена каталога inbox в короткий момент между проверкой и записью файла из темы.
- Правило «все сборки в общем target» проекта cctg в сэндбокс-папках не действует: target там свой.
- Хук gate стоит на `Write`, `Edit`, `MultiEdit`, `NotebookEdit` и `EnterWorktree`. Новый инструмент записи файлов в будущей версии Claude Code он не поймает, пока его не добавят в список.

## Как всё удалить

`install.sh --uninstall` удаляет сгенерированные профили (`~/.cctg/claude/sandbox/`). Метки, allowlist и копии gitconfig остаются в `~/.cctg/sandbox/`, их удалите руками:

```sh
rm -rf ~/.cctg/sandbox
```

В каждой помеченной папке остаётся `.cctg/sandbox/` с кэшами; его тоже можно удалить. Файлы из тем, которые не поместились в папку сессии, лежат в `~/.cctg/inbox/` (это относится ко всем сессиям, не только к сэндбоксу).
