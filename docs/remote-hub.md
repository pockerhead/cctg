# Hub на удалённом сервере

Hub (`cctg hub`) может жить не на рабочей машине, а на сервере в Docker. Устройства с сессиями Claude Code (Windows, Linux, macOS) ходят к нему по TLS: агент держит соединение с `CCTG_HUB_AGENT_ADDR`, хуки шлют POST на `CCTG_HUB_HOOK_ADDR`. Секрет hub идёт только внутри TLS. Локальная схема (hub и сессии на одной машине, `127.0.0.1` без TLS) работает как раньше, для неё ничего настраивать не нужно.

```
устройство (cctg agent, cctg hook) --TLS 1.3, pin сертификата--> сервер: docker, cctg hub --HTTPS (через прокси или напрямую)--> Telegram
```

Hub не читает файлов устройств (TASK-034): транскрипты и файлы сессий отдаёт агент по запросу. Поэтому hub на другой машине видит то же, что локальный.

## Что где лежит

- Образ `ghcr.io/pockerhead/cctg`: статический Linux-бинарник `cctg` (x86_64) на Alpine, пользователь uid 10001, состояние (`registry.json`, `offset`) в томе `/data`. Секретов в образе нет: `.dockerignore` пускает в сборку только исходники. Пакет публичный, сервер тянет образ без логина.
- Теги образа: `latest` и `<версия>` для релизов (git-тег `v*`), `main` и `sha-<коммит>` для каждого пуша в main.
- GitHub Releases (на тег `v*`): `cctg-<тег>-x86_64-pc-windows-msvc.exe`, `cctg-<тег>-x86_64-unknown-linux-musl`, `cctg-<тег>-aarch64-apple-darwin`, `SHA256SUMS`.
- `deploy/compose.yml`, `deploy/compose.host.yml` и `deploy/hub.env.example` в репозитории: всё, что нужно серверу.

## Один раз в GitHub

После первой публикации образа (первый пуш в main после TASK-035) пакет `cctg` в GHCR приватный. Один раз: GitHub, профиль, Packages, `cctg`, Package settings, Change visibility, Public. Репозиторий публичный, в образе нет секретов.

Тег `latest` появляется только с первым релизом (git-тег `v*`, раздел «Обновление»). Пуш в main публикует `main` и `sha-<полный коммит>`. Пока релиза нет, `docker compose up -d` с `compose.yml` как есть падает с `manifest unknown`. Два выхода: поставить первый тег `v0.1.0` на коммит main с зелёным `ci` и дождаться `release`, или до первого релиза написать в `.env` рядом с `compose.yml` `CCTG_IMAGE_TAG=main` (и убрать после релиза: watchtower следит за тегом, с которым запущен контейнер).

## Один раз на сервере

Всё, что ниже, делает одна команда (TASK-031, `<тег>` это релиз, например `v0.1.0`):

```sh
curl -fsSL https://raw.githubusercontent.com/pockerhead/cctg/<тег>/install.sh | sh -s -- --hub
```

Папка `~/cctg-hub` (другая: `--dir`). Команда спрашивает токен бота (скрытый ввод), id группы, id пользователей, прокси и адрес сервера (или берёт `CCTG_BOT_TOKEN`, `--chat-id`, `--users`, `--proxy`, `--public-host`), делает секрет и сертификат, пишет `hub.env` (600) и `.env` с `COMPOSE_FILE` (с `compose.host.yml`, если прокси на `127.0.0.1` хоста), `CCTG_IMAGE_TAG` (образ того же релиза, что и скрипт) и адресом сервера, запускает hub, ждёт в логе `hub started, polling` (бот, группа и права проверены) и печатает строку установки клиента с адресом, портами из `compose.yml`, pin и одноразовым кодом (раздел «Устройства и коды»); секрет hub она не печатает. Без терминала адрес сервера обязателен (`--public-host`). Повторный запуск оставляет записанные значения, секрет и сертификат; `compose.yml` в том виде, в каком его записал скрипт, обновляется до версии релиза, а изменённый руками (порты) не перезаписывается, новая версия ложится рядом как `compose.yml.new`. `--hub --uninstall` делает `docker compose down` и убирает compose-файлы, `hub.env`, `tls/` и том остаются. Руками то же самое:

Нужны Docker Engine с плагином compose (2.24 или новее, если нужен `compose.host.yml`) и два открытых наружу TCP-порта (по умолчанию 47291 для агентов и 47292 для хуков, другие номера в разделе «Порты»).

1. Папка и файлы:

   ```sh
   mkdir -p /opt/cctg/tls && cd /opt/cctg
   curl -fsSLO https://raw.githubusercontent.com/pockerhead/cctg/main/deploy/compose.yml
   curl -fsSLO https://raw.githubusercontent.com/pockerhead/cctg/main/deploy/compose.host.yml
   curl -fsSL -o hub.env https://raw.githubusercontent.com/pockerhead/cctg/main/deploy/hub.env.example
   chmod 600 hub.env
   ```

   Заполнить `hub.env`: `CCTG_BOT_TOKEN`, `CCTG_CHAT_ID` (`-100<id>`), `CCTG_ALLOWED_USER_IDS`, `CCTG_HUB_SECRET` (16+ видимых ASCII, длинный случайный, например `openssl rand -hex 32`). Файл остаётся только на сервере.

2. Сертификат. Самоподписанный, на 10 лет, ключ EC P-256:

   ```sh
   openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 -nodes \
     -days 3650 -subj "/CN=cctg-hub" -keyout tls/key.pem -out tls/cert.pem
   chown 10001 tls/key.pem && chmod 600 tls/key.pem
   openssl x509 -in tls/cert.pem -noout -fingerprint -sha256
   ```

   Ключ читает только uid 10001 (пользователь hub в образе); без `chown` hub не стартует с ошибкой «CCTG_TLS_KEY cannot be read as a PEM private key». Последняя команда печатает `sha256 Fingerprint=AB:CD:...`: это pin для устройств, не секрет. Имя в сертификате роли не играет: устройства проверяют ровно эти байты сертификата и подпись рукопожатия его ключом, а не имя и не центр сертификации.

3. Запуск (если Telegram с сервера доступен только через прокси, сначала раздел «Прокси»):

   ```sh
   docker compose up -d
   docker compose ps          # STATUS: healthy
   docker compose logs hub    # "TLS certificate loaded sha256=AB:CD:...", "hub started, polling"
   ```

   Hub пишет pin своего сертификата при каждом старте, его можно сверить с шагом 2.

Healthcheck (`cctg health`) проверяет, что оба порта hub принимают соединения. Он не ходит в Telegram и не отправляет ни байта; hub пишет о таких соединениях только на уровне debug. Порты открываются до первого `getMe`, поэтому «healthy» значит «процесс жив и слушает», а не «Telegram доступен»: это видно по строке «hub started, polling» в логе.

## Порты

Порты hub видны всему интернету, поэтому лучше взять не стандартные номера (меньше шума от сканеров; безопасность держат TLS и секрет, не номер). Пример с 52191 и 52192:

- обычная сеть: в `compose.yml` поменять только левые номера, `"52191:47291"` и `"52192:47292"`; внутри контейнера hub слушает те же 47291/47292, healthcheck не меняется;
- сеть хоста (`compose.host.yml`): в `hub.env` `CCTG_AGENT_LISTEN=0.0.0.0:52191` и `CCTG_HOOK_LISTEN=0.0.0.0:52192` (healthcheck читает те же переменные).

На устройствах те же номера в `CCTG_HUB_AGENT_ADDR` и `CCTG_HUB_HOOK_ADDR`. Если адреса устройств постоянные, firewall сервера может пускать на эти порты только их.

## Прокси

Прокси нужен, только если сервер не достаёт до Bot API напрямую (решение 2 TASK-035: адрес, который отдаёт DNS сервера, не отвечает). Тогда hub ходит в Telegram через HTTP-прокси из своего окружения: `HTTPS_PROXY` (и `HTTP_PROXY`, `ALL_PROXY`, `NO_PROXY`) читает сам клиент Bot API. Без этих переменных hub ходит напрямую. Hub пишет при старте одну строку «Bot API requests go through the proxy of the environment», адрес прокси не пишет никогда (в нём бывают логин и пароль). Агенты и хуки прокси не используют: это входящие соединения к hub, `NO_PROXY` для них не нужен.

- Переменная кладётся в `hub.env`: compose передаёт его в окружение процесса. Файл `.env`, который `cctg hub` читает сам (`--env-file`), для прокси не годится: hub не переносит его значения в окружение.
- Прокси слушает только `127.0.0.1` хоста (так у многих локальных прокси по умолчанию): контейнер в сети хоста, `docker compose -f compose.yml -f compose.host.yml up -d`, в `hub.env` `HTTPS_PROXY=http://127.0.0.1:10809`. Порты hub тогда открываются прямо на хосте. Все команды `docker compose` дальше с теми же двумя `-f`.
- Прокси слушает и адрес моста Docker (обычно `172.17.0.1`): остаётся обычная сеть, в `hub.env` `HTTPS_PROXY=http://host.docker.internal:10809` (`host.docker.internal` в `compose.yml` уже есть).
- Образы из GHCR тянет демон Docker, а не hub: если и `ghcr.io` недоступен напрямую, прокси задаётся демону (systemd drop-in с `HTTPS_PROXY` для `docker.service`, документация Docker «Daemon proxy configuration»).

## Устройство

`~/.cctg/device.env` каждой машины с сессиями:

```
CCTG_HUB_SECRET=<свой секрет устройства от cctg join, или общий секрет из hub.env>
CCTG_HUB_AGENT_ADDR=hub.example.org:47291
CCTG_HUB_HOOK_ADDR=hub.example.org:47292
CCTG_HUB_CERT_SHA256=AB:CD:...
```

- `CCTG_HUB_CERT_SHA256` включает TLS на обоих каналах. Значение это 64 шестнадцатеричные цифры, с двоеточиями или без, в любом регистре: то, что openssl печатает после `Fingerprint=`. Целую строку openssl тоже можно вставить, но только в кавычках (пробел без кавычек ломает файл, и тогда устройство не видит и секрет). Сломанный pin не откатывается на открытый TCP: хук и агент просто молчат и пишут причину в stderr (у агента это debug-лог claude).
- Без pin устройство говорит открытым TCP и только с loopback (`127.x`, `[::1]`, `localhost`). Адрес другой машины без pin не используется вовсе, секрет в открытом виде по сети не уходит. Имя `localhost` разрешает система, поэтому после соединения устройство ещё раз проверяет, что на том конце loopback, и иначе закрывает соединение, ничего не отправив.
- Адрес может быть именем или IP.
- Хуки над TLS ждут дольше: 900 мс (600 мс для `UserPromptSubmit` и тулов) вместо 500/300. Строка статуса в удалённый hub не ходит вовсе: цифры контекста и лимитов она оставляет в `~/.cctg/status/`, а в hub их отправляет агент сессии по уже открытому соединению (TASK-058), так что задержка до сервера на строку не влияет. У сессии без канала цифр в сообщении статуса не будет. Поэтому сначала обновите hub, потом устройства: агент новее TASK-058 с hub старше него цифры не отправляет, а строка статуса в удалённый hub их тоже не шлёт, и в сообщении статуса цифр не будет, пока hub не обновлён.
- Устройство ставит `install.sh` (README, шаг 3): бинарник своего тега из GitHub Releases, этот `device.env`, `~/.cctg/claude/{mcp.json,settings.json}` и обёртку `claude-cctg`. `~/.cctg/bin/cctg doctor` проверяет оба канала, pin и секрет. Руками: бинарник из GitHub Releases того же тега, что образ на сервере (про версии ниже); на Linux и macOS файл из Releases скачивается без права на запуск: `chmod +x` после каждого скачивания, иначе агент и хуки не стартуют (`Permission denied`); регистрация агента и хуков как в `docs/poc.md`: `cctg agent-install`, `docs/hook-settings.json`.
- macOS (Apple Silicon): файл `cctg-<тег>-aarch64-apple-darwin` не подписан. После скачивания `chmod +x` и `xattr -d com.apple.quarantine <файл>`. Управление консолью claude (⏹, `!`-команды, панели, перезапуск по «Обновить») на Linux и macOS работает, когда claude запущен через `claude-cctg` в терминале (TASK-044, `docs/poc.md`); вложенные `claude -p`, перепривязка агента после `/clear` и уборка сессий на macOS работают по обходу родителей процесса, как на Linux.

## Устройства и коды

С TASK-045 у каждой машины свой секрет, а общий `CCTG_HUB_SECRET` из `hub.env` на устройства больше не раздаётся.

- Код: 16 знаков Crockford base32 (80 случайных бит), вид `XXXX-XXXX-XXXX-XXXX`, работает один раз и 10 минут. Регистр, дефисы и пробелы не важны, `O` читается как `0`, `I` и `L` как `1`. Код даёт `cctg hub code` рядом с запущенным hub: в Docker `cd ~/cctg-hub && docker compose exec hub cctg hub code`, у hub без Docker `cctg hub --env-file <тот же .env> code` в той же папке, что и hub (ему нужен только `CCTG_STATE_DIR`). Если в этом каталоге ещё не запускался hub (нет `join/`, его создаёт hub при старте), `cctg hub code` отказывает и называет каталог, а не печатает код, который hub не увидит. Запускать от того же пользователя, что и hub (в Docker `docker compose exec` без `-u`, без Docker без `sudo`): файл кода другого пользователя hub не прочитает, и код будет отвергнут. `install.sh --hub` печатает один код в строке клиента. В каталоге состояния (`/data/join/`) лежит только sha256 кода и срок, не сам код. Неиспользованных кодов не больше 32 одновременно.
- Обмен: `install.sh --join КОД` (или `CCTG_JOIN_CODE`) пишет адрес и pin, потом запускает `~/.cctg/bin/cctg join`. `cctg join [КОД]` можно запустить и руками на уже настроенной машине: он берёт адрес и pin из `device.env`, по TLS с pin (или по loopback без pin) шлёт `POST /v1/join` с кодом и именем машины (`CCTG_HOST` или имя системы) и заменяет строку `CCTG_HUB_SECRET` в `device.env` полученным секретом (файл 600 на Linux и macOS). Ни код, ни секрет он не печатает. Отказ один на все случаи: код неверный, уже использован или истёк.
- Секрет устройства `cctgd_<id>_<64 hex>`: `<id>` (8 hex) публичный и виден в `/devices`, остальное 256 случайных бит. Hub хранит только sha256 секрета в `/data/devices.json` (имя, id, дата). Медленный хеш не нужен: подбирать 256 случайных бит бессмысленно. Устройств не больше 32.
- `/join` в теме General (только из allowlist, TASK-046): hub делает новый код и отвечает строкой установки клиента: `curl -fsSL https://raw.githubusercontent.com/pockerhead/cctg/<релиз hub>/install.sh | sh -s -- --hub-host <адрес> --pin <sha256> --join <код>` (`--agent-addr`/`--hook-addr`, если порты не 47291/47292). Адрес hub берёт из `CCTG_PUBLIC_AGENT_ADDR` и `CCTG_PUBLIC_HOOK_ADDR` в `hub.env` (оба `host:port`, пишет `install.sh --hub` по `--public-host` и портам `compose.yml`; руками тоже можно), pin считает сам по своему сертификату. Без этих строк или без TLS строка годится только для машины hub (`127.0.0.1`), об этом сказано в ответе. Секрета в строке нет; код одноразовый и живёт 10 минут. Когда код взяло устройство, сообщение правится на «использован: подключено устройство «имя» (id)», иначе через 10 минут на «код истёк». Правки помнит только запущенный hub: после его рестарта ожидающие сообщения так и остаются со строкой (код при этом всё равно истекает). Сообщение видят все участники группы: кто успел выполнить строку первым, тот и получил устройство, поэтому новые устройства проверяйте в `/devices`. Hub, собранный не из релиза, даёт ссылку на `main`.
- `/devices` в теме General (только из allowlist): список устройств с датой и последним входом с запуска hub, состояние общего секрета (когда с ним входили последний раз) и по кнопке «Отозвать» на устройство. Отзыв спрашивает подтверждение. После «Да, отозвать» линки агентов этого устройства закрываются сразу, ждущие хуки разрешений и вопросов обрываются без ответа, следующий хук получает 401, `cctg doctor` пишет «rejected the secret». Отозванное устройство возвращается только с новым кодом. Сессии отозванного устройства в темах остаются «живыми без агента», пока hub не уберёт их по обычным правилам: `SessionEnd` от них больше не принимается.
- Агент перечитывает `device.env` только при старте: после `cctg join` уже запущенные сессии ходят со старым секретом (общим, пока он включён), новые сессии и все хуки берут новый.
- До секрета `/v1/join` защищён как остальные запросы хуков (раздел «Защита до секрета»): 2 с на весь запрос, тело не больше 1 КиБ, 16 недочитанных запросов с одного IP, 64 всего, неверный код отвечается через 250 мс. Этого хватает с запасом: за 10 минут жизни кода получается порядка 10^5 попыток против 2^80 вариантов.

### Миграция

1. Hub этой версии поднимается как раньше: общий секрет принимается (`CCTG_SHARED_SECRET` по умолчанию `on`), уже настроенные машины ничего не замечают.
2. На каждой машине по очереди: код (`docker compose exec hub cctg hub code`), потом `~/.cctg/bin/cctg join КОД` или та же строка `install.sh ... --join КОД`. `cctg doctor` покажет «secret: set, this device's own». Запущенные сессии claude перезапускать не обязательно, но до перезапуска их агенты ходят с общим секретом.
3. `/devices` показывает все машины и строку «последний вход с общим секретом». Строка обновляется только при новом входе (подключение агента или хук), а уже подключённый агент старой сессии её не двигает, поэтому перед `off` перезапустите сессии claude, начатые до `cctg join` (иначе они потеряют hub до перезапуска). Когда строка долго не меняется, в `hub.env` дописать `CCTG_SHARED_SECRET=off` и `docker compose up -d`. С этого момента общий секрет не пускает никого; hub с `off` запускается и без `CCTG_HUB_SECRET`.

Откат: `CCTG_SHARED_SECRET=on` (или убрать строку) и перезапуск hub; секреты устройств продолжают работать.

Откат образа hub на релиз до TASK-045 не знает `devices.json`: машины со своим секретом получат отказ, общего секрета у них уже нет. Им снова нужен общий секрет: `install.sh` с `CCTG_HUB_SECRET` или `--secret-file` на каждой такой машине.

## Обновление

Выпуск это git-тег `vX.Y.Z` на main, поставленный на коммит с зелёным `ci`, в котором `install.sh` уже говорит `RELEASE=vX.Y.Z` (иначе `release.yml` ничего не публикует; строки установки в README тоже на новый тег). GitHub Actions (`.github/workflows/release.yml`) собирает образ и бинарники одного коммита, с одним и тем же `CCTG_BUILD_ID`, кладёт образ в GHCR (`latest` и `X.Y.Z`) и создаёт релиз с бинарниками. Никаких секретов, кроме встроенного `GITHUB_TOKEN`, workflow не использует. Серверу ssh от оркестратора не нужен.

На сервере одно из двух:

- автоматически: `docker compose --profile autoupdate up -d` поднимает рядом `nickfedor/watchtower` (поддерживаемый форк заархивированного `containrrr/watchtower`). Он раз в 10 минут проверяет `latest`, трогает только контейнер с меткой `com.centurylinklabs.watchtower.enable=true` (это hub), перезапускает его на новом образе и удаляет старый. Ему нужен `/var/run/docker.sock`, то есть права root на хосте: если это неприемлемо, второй вариант;
- руками или по cron: `docker compose pull && docker compose up -d`.

Hub, поставленный `install.sh --hub`, закреплён на образе своего релиза (`CCTG_IMAGE_TAG` в `.env`): его обновляет команда `--hub` нового тега, `pull` и watchtower тянут только тот же релиз.

Hub останавливается по SIGTERM: дописывает `registry.json` в том и выходит (`stop_grace_period: 30s`). Агенты переподключаются сами, хуки на эти секунды складывают `SessionStart`/`SessionEnd` в спул.

`registry.json` версии 2 (TASK-061, после v0.1.12): тема слота, её имя, иконка, разделитель и статус переехали в «вид» слота в группе, у сохранённых id сообщений появился чат. Новый hub читает файл v0.1.12 и старше (версия 1), сначала кладёт его байт в байт рядом как `registry.v1.json` (не вышло, значит hub не стартует и `registry.json` не трогает: `cannot keep the version 1 registry.json as registry.v1.json`) и при первом же сохранении переписывает `registry.json` как версию 2. Hub v0.1.12 и старше на файле версии 2 не стартует (`registry.json has version 2, this hub reads version 1` или `registry.json is not a valid registry`) и темы не плодит.

Откат на v0.1.12 (или старше) после плохого релиза: остановить hub, вернуть копию, запустить старый образ.

```sh
docker compose stop hub
docker compose run --rm --no-deps --entrypoint cp hub /data/registry.v1.json /data/registry.json
# в .env рядом с compose.yml: CCTG_IMAGE_TAG=0.1.12 (так же закрепляет образ от watchtower)
docker compose up -d
```

Hub без Docker (`cctg supervise`): остановить его, в папке состояния (`CCTG_STATE_DIR`, по умолчанию `.cctg`) скопировать `registry.v1.json` поверх `registry.json`, запустить старый бинарник. Копия это реестр на момент обновления: слоты и темы, появившиеся после него, старый hub не знает и для таких папок создаст темы заново; `offset` остаётся как есть. Следующее обновление снова мигрирует файл и перезапишет `registry.v1.json` его новой копией.

`registry.json` версии 3 (TASK-069, после v0.1.22): у каждого сохранённого чата группы появился её id (`"chat": {"group": -100…}` вместо `"chat": "group"`), и появился список известных групп `groups`. Новый hub читает файл версии 2 (и 1, через версию 2), все группы старого файла становятся группой из `CCTG_CHAT_ID` этого старта. Сначала он кладёт файл байт в байт рядом как `registry.v2.json` (не вышло, значит hub не стартует и `registry.json` не трогает: `cannot keep the version 2 registry.json as registry.v2.json`) и при первом же сохранении переписывает `registry.json` как версию 3. Hub v0.1.22 и старше на файле версии 3 не стартует (`registry.json has version 3, this hub reads version 2`) и тем не плодит.

Не меняйте `CCTG_CHAT_ID` в том же рестарте, что и обновление: старые темы мигрируют в группу из `.env` этого старта. Сменить группу по умолчанию позже можно: старая остаётся подключённой группой, новая становится основной.

Откат на v0.1.22 так же, как выше, только копия другая: остановить hub, скопировать `registry.v2.json` поверх `registry.json`, запустить старый образ или бинарник.

```sh
docker compose stop hub
docker compose run --rm --no-deps --entrypoint cp hub /data/registry.v2.json /data/registry.json
# в .env рядом с compose.yml: CCTG_IMAGE_TAG=0.1.22
docker compose up -d
```

Копия это реестр на момент обновления: слоты, темы и группы, появившиеся после него, старый hub не знает (темы в других группах остаются, но не обновляются; удалите их в Telegram руками). `cctg deploy` откатывает бинарник сам, если новый hub упал в первые 10 с; если он успел записать версию 3, старый hub не стартует, и нужно то же копирование `registry.v2.json`. Hub пишет `registry.json` только после проверок старта, поэтому это редкий случай.

Откат с версии с личкой (TASK-063) на v0.1.15 и старше. Версия реестра та же, файл старый hub читает без копии и без миграции. Что вы увидите:

- слоты, созданные новой версией (новые папки, вторые сессии папки), живут только в личке. Старый hub пишет туда и дальше, но личку не читает: сообщения из этих тем в сессию не идут, кнопки там не отвечают (крутится индикатор), запросы разрешения таких сессий решаются только в терминале. Новая сессия в той же папке займёт тот же слот, то есть тоже останется в личке;
- слоты, у которых есть тема и в группе, работают в группе как раньше; в их теме лички остаётся последний статус, он больше не обновляется;
- при первом сохранении старый hub выбрасывает из `registry.json` связи двойников (`twins`): если потом снова обновиться, блоки субагентов в группе, начатые до отката, остаются «в работе…». В команде старый hub при `/join` или отзыве устройства перезаписывает `devices.json` без владельцев, и после нового обновления такие устройства принадлежат первому id `CCTG_ALLOWED_USER_IDS`, пока их не переподключат через `/join`.

Как вернуть слоты «только в личке» в группу: остановить hub и в `registry.json` поставить таким слотам первым видом группу без темы, старый hub создаст им темы в группе. С `jq` на машине, где лежит файл (для Docker это том `/data`):

```sh
jq '.slots |= map(if .views[0].chat == "group" then . else .views = [{"chat": "group"}] + .views end)' registry.json > registry.new && mv registry.new registry.json
```

После этого запустить старый hub. Тема лички у таких слотов остаётся, но не обновляется: её можно удалить в Telegram.

Откат с версии с общим доступом (TASK-064) на v0.1.16. Реестр тот же: общий слот для старого hub это слот с темой и в личке, и в группе, слот «только в личке» тоже понятен. Теряется:

- строка общего доступа темы, которую ещё не создали: тема появится без неё;
- незаконченное удаление тем группы после `/unshare` (`unshared` в `registry.json`): старый hub его не делает, такие темы удалить в Telegram руками;
- кнопки «👥 В группу» и «🙈 Убрать из группы» на старых статусах отвечают пустым ответом, а `/share` и `/unshare` старый hub набирает в консоль claude как обычную команду.

Если hub упал между `/unshare` и сохранением `registry.json`, после рестарта слот снова общий: повторите `/unshare`.

Откат с версии с меню в личке (TASK-073) на v0.1.17. Версия реестра та же. Старый hub не знает поле `people` (меню и настройки каждого человека), читает файл без него и теряет его при первом сохранении. Что вы увидите:

- `/start` в личке снова отвечает текстом, `/menu` получает ответ «пишите в тему сессии», кнопки меню отвечают пустым ответом;
- закреплённое меню остаётся в General лички: открепить и удалить его руками;
- подробность и звук снова как по умолчанию (всё видно, звук у ответов и запросов).

При возврате на новую версию меню придёт заново сразу после запуска (если в личке есть темы сессий), настройки придётся выбрать ещё раз.

Откат с версии с показом группы (TASK-078) на v0.1.19. Реестр тот же. Старый hub не знает `settings.group` (показ группы каждого человека), читает файл без него и теряет его при первом сохранении: после нового обновления группа снова «Всё». Общий слот снова показан полностью и в личке, и в группе. Кнопки «👤 Личка / 👥 Группа» и настройки группы в старом меню отвечают пустым ответом (↻ рисует меню старого вида).


## Смена сертификата

Pin это хеш сертификата, поэтому новый сертификат (истёк срок, утёк ключ) это новый pin на всех устройствах:

1. На сервере шаг 2 заново (новые `tls/cert.pem` и `tls/key.pem`), `docker compose restart hub`, pin из лога или из openssl.
2. На каждом устройстве новый `CCTG_HUB_CERT_SHA256` в `device.env`. Хуки берут его со следующего события. Агенты читают `device.env` только при старте, поэтому уже запущенные сессии claude до hub не достучатся, пока их не перезапустить (`/exit`, потом `claude-cctg --resume <id>`).

До правки устройства молчат (хуки пишут в stderr, что событие не доставлено), небезопасного отката на открытый TCP нет.

## Версии клиента и hub

Сборка определяется коммитом, из которого она собрана, а не байтами файла: `cctg --version` печатает `cctg 0.1.0 (<коммит>)`. Hub в Linux-контейнере и клиент одного коммита на любой ОС считаются одной сборкой. Клиент другого коммита получает в теме одно предупреждение «устарел» с кнопкой «Обновить» (номера обеих сборок в тексте).

- Коммит в сборку кладёт `build.rs`: `CCTG_BUILD_ID` из окружения сборки (CI и Docker передают полный коммит), иначе `git rev-parse HEAD`. Если в `crates/`, `Cargo.toml` или `Cargo.lock` есть незакоммиченные изменения, к коммиту добавляется `-dirty` и хеш исполняемого файла: две разные грязные сборки одного коммита не равны. Без git и без переменной сборкой остаётся sha256 файла, как до TASK-035.
- «Обновить» при hub из релиза (образ тега, TASK-050): агент устаревшей сессии сам скачивает `cctg-<тег hub>-<платформа>` и `SHA256SUMS` того же релиза (`https://github.com/pockerhead/cctg/releases/download/<тег>/`, другая база в `CCTG_RELEASE_BASE_URL` окружения claude, прокси из `HTTPS_PROXY`), сверяет sha256 и ставит файл на место своего так же, как `install.sh` (Windows: работающий `cctg.exe` в `cctg.old.exe`), потом подхватывает его. Если файл на диске уже этот, ничего не качается. Ошибка сети, несовпадение суммы или нет сборки для платформы дают ответ в теме, старая сборка остаётся; если скачать не вышло (сеть, нет файла), а на месте файла уже лежит другая сборка (поставленная руками или `install.sh`), агент берёт её. Прокси только из переменных окружения claude (`HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`): системный прокси Windows и macOS не читается. «Обновить» ставит ровно сборку hub, а не самую новую: клиент более новой сборки (dev-сборка с main, `--from-source`) при hub из релиза тоже считается устаревшим и по кнопке вернётся на сборку hub. Hub без тега (локальная сборка, образ `:main`) ничего не предлагает скачать: агент берёт новый файл, только если он лежит на месте старого. Порядок тогда: команда установки нового тега (`.../<новый тег>/install.sh`) кладёт бинарник на место старого (работающий `cctg.exe` в Windows переименовывается в `cctg.old.exe`, в Linux и macOS файл получает `chmod` и заменяет старый через `mv`), потом «Обновить» в теме. Руками: скачать бинарник нужного тега из Releases; на Windows переименовать работающий `cctg.exe` (Windows разрешает переименовать запущенный exe) и положить новый под старым именем, на Linux и macOS `chmod +x` новому файлу и заменить им старый (`mv` поверх старого); нажать «Обновить». Если нового файла нет, тема получает подсказку, что делать.
- После первой выкатки TASK-035 старые клиенты (сборка = хеш файла) один раз получат «устарел»: это ожидаемо.
- Порядок обновления: сначала hub, потом устройства. Новый hub понимает старых агентов, а новый агент со старым удалённым hub остаётся без цифр контекста и лимитов в сообщении статуса (TASK-058).

## Hub на своей машине с TLS

Тот же hub без Docker тоже умеет TLS: `CCTG_TLS_CERT` и `CCTG_TLS_KEY` в `.env` (оба или ни одного), `CCTG_AGENT_LISTEN`/`CCTG_HOOK_LISTEN` на нужном адресе. Открытый TCP на не-loopback адресе hub по-прежнему разрешает с предупреждением в логе, но устройства туда без pin не пойдут.

`install.sh --hub --local` (TASK-046) ставит такой hub сам: бинарник в `~/.cctg/bin`, `~/.cctg/hub/hub.env` (600; `CCTG_STATE_DIR` на `~/.cctg/hub/state`), лог `~/.cctg/hub/hub.log` (больше 5 МиБ уходит в `hub.log.prev` при старте) и автозапуск `cctg supervise --env-file ... --log-file ...` при входе в систему без окон:

- Windows: значение `cctg-hub` в `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` запускает `wscript.exe //B //Nologo ~/.cctg/hub/start-hub.js`; пути к бинарнику, `hub.env` и логу записаны в самом скрипте (значение `Run` не длиннее 260 символов, установщик проверяет это и с длинным `--dir` отказывает). Скрипт берёт переменные `CCTG_*` и прокси из реестра, как при входе (из окна Git Bash, где запущен установщик, они не доходят до hub), и запускает supervisor скрыто (`WshShell.Run(..., 0)`); первый запуск идёт той же командой. Прав администратора не нужно, запись видна в «Параметры, Приложения, Автозагрузка». Задача планировщика с триггером входа без прав администратора не создаётся (`schtasks /SC ONLOGON` отказывает), а её консольное окно всё равно было бы видно.
- Linux: `~/.config/systemd/user/cctg-hub.service` (`systemctl --user enable`, `Restart=on-failure`). Без `loginctl enable-linger` hub работает, пока пользователь в системе.
- macOS: `~/Library/LaunchAgents/io.github.pockerhead.cctg-hub.plist` (`launchctl bootstrap gui/<uid>`, `RunAtLoad`, перезапуск только после сбоя).

Без `--public-host` hub слушает только loopback без TLS. С `--public-host ХОСТ` (имя, IPv4 или `[IPv6]` в скобках; голый IPv6 установщик не примет) установщик делает сертификат (нужен `openssl`), пишет `CCTG_TLS_*`, `CCTG_PUBLIC_*` и `CCTG_AGENT_LISTEN`/`CCTG_HOOK_LISTEN` на `0.0.0.0` (для `[IPv6]` на `[::]`). Свои строки `*_LISTEN` установщик помечает комментарием и выбирает заново при каждом запуске (другой `--public-host` меняет и адрес слушателя); строки без пометки ваши и остаются. Строка клиента этой машины идёт на loopback слушателя: `127.0.0.1`, для `[::]` и `[::1]` на `[::1]` (в Windows `[::]` принимает только IPv6); Windows при первом запуске спросит про доступ в брандмауэре. Адрес `[IPv6]` в напечатанных строках стоит в одинарных кавычках: без них `sh` и `zsh` читают скобки как шаблон файлов. Прокси: `--proxy URL` (или вопрос установщика) пишет `HTTPS_PROXY` в `hub.env` (600); hub берёт его оттуда сам, если в его окружении нет прокси (есть: берёт тот, как раньше); в автозапуск, юнит, plist и реестр URL не попадает. Повторный запуск обновляет бинарник и перезапускает hub (в Windows через `cctg.restart`), `--hub --local --uninstall` останавливает hub (в Windows через `cctg.stop`) и убирает автозапуск, `hub.env`, `tls/`, `state/` и лог остаются.

Держите один способ запуска. Supervisor, запущенный руками из той же папки `~/.cctg/bin`, держит блокировку, и автозапуск тогда сразу выходит: установщик ждёт строк hub в `hub.log`, не дожидается и пишет, что надо остановить ручной supervisor. Supervisor старше TASK-046 блокировку не берёт, рядом с новым он даст второй hub. Локальный hub и hub в Docker на одном токене бота мешают друг другу (`getUpdates` отвечает 409), установщик этого не проверяет.

Windows, выход из системы и выключение: Windows завершает консольные процессы пользователя без Ctrl+C, hub не останавливается чисто. `registry.json` и `offset` пишутся атомарно (temp + fsync + rename) при каждом изменении, поэтому теряется только то, что было в полёте, как при сбое.

Лог: `hub.log` уходит в `hub.log.prev` только при старте supervisor (вход в систему, перезагрузка, `systemctl --user restart`). На Linux с linger он растёт до следующего рестарта.

Антивирус и EDR: запуск `.js` через `wscript` из `Run` известен как приём закрепления вредоносных программ. Если средство защиты его блокирует или помещает `start-hub.js` в карантин, запускайте hub вручную (`docs/poc.md`).

## Защита до секрета

Порты открыты всему интернету, поэтому до проверки секрета hub держит соединения коротко:

- агент: одно окно 5 с от TCP-соединения на рукопожатие TLS, `hello` и `register`; первая строка до проверки секрета не длиннее 4 КиБ; одновременно не больше 16 соединений без секрета и не больше 4 из них с одного IP, лишнее закрывается сразу;
- хук: одно окно 2 с от TCP-соединения на рукопожатие TLS и весь запрос; заголовки до проверки секрета не длиннее 8 КиБ, тело читается только после; одновременно не больше 64 запросов и не больше 16 недочитанных с одного IP;
- неверный секрет: сравнение за постоянное время, ответ (у агента `rejected`, у хука 401) только через 250 мс, в логе строка с адресом пира без значения секрета;
- неудачное рукопожатие TLS и соединение без единого байта (сканеры, healthcheck) пишутся только на уровне debug;
- прочие отказы до секрета (неверный секрет, мусор, чужая версия протокола, таймаут) дают не больше одного warning в минуту с одного IP, остальные строки идут на уровне debug;
- `POST /v1/join` (TASK-045) единственный запрос без секрета: в тех же 2 с и местах хуков, тело не больше 1 КиБ, неверный, использованный и просроченный код получают одинаковый 403 через 250 мс, в логе строка с адресом пира без кода.

Остаток: адресов у сканеров много, и 4 источника могут занять все 16 мест агентов; настоящие устройства тогда переподключаются с паузой до 30 с. От этого firewall со списком адресов устройств или нестандартный порт. Устройства за одним NAT делят свои 4 места, но место держится только на время рукопожатия, поэтому это заметно только при одновременном переподключении многих сессий (после рестарта hub), и отказанные повторяют попытку сами.

## Проверка без Telegram

Сертификат, pin и оба канала покрывает `crates/cctg/tests/tls_e2e.rs` (настоящие процессы hub, hook и agent, фейковый Bot API), прокси `crates/cctg/tests/proxy_e2e.rs` (заглушка прокси: `CONNECT` к `.invalid`-хосту и запросы в абсолютной форме, пароль прокси в вывод не попадает). Образ в CI (`.github/workflows/ci.yml`, задача `image`) собирается и проходит `.github/smoke/smoke.py`: compose с фейковым Bot API, healthcheck, хук и агент по TLS с клиентом того же коммита, отсутствие секретов в образе и логах, остановка по SIGTERM.

## Ограничения

- Образ только x86_64. Клиенты: Windows x86_64, Linux x86_64, macOS arm64.
- Смена сертификата требует правки всех устройств и перезапуска их сессий (раздел выше).
- Не больше 32 устройств со своим секретом и 32 неиспользованных кодов. Последний вход устройства hub помнит только до перезапуска.
