# Hub на удалённом сервере

Hub (`cctg hub`) может жить не на рабочей машине, а на сервере в Docker. Устройства с сессиями Claude Code (Windows, Linux, macOS) ходят к нему по TLS: агент держит соединение с `CCTG_HUB_AGENT_ADDR`, хуки шлют POST на `CCTG_HUB_HOOK_ADDR`. Секрет hub идёт только внутри TLS. Локальная схема (hub и сессии на одной машине, `127.0.0.1` без TLS) работает как раньше, для неё ничего настраивать не нужно.

```
устройство (cctg agent, cctg hook) --TLS 1.3, pin сертификата--> сервер: docker, cctg hub --HTTPS (через прокси или напрямую)--> Telegram
```

Hub не читает файлов устройств (TASK-034): транскрипты и файлы сессий отдаёт агент по запросу. Поэтому hub на другой машине видит то же, что локальный.

## Что где лежит

- Образ `ghcr.io/pockerhead/cctg`: статический Linux-бинарник `cctg` (x86_64) на Alpine, пользователь uid 10001, состояние (`registry.json`, `offset`) в томе `/data`. Секретов в образе нет: `.dockerignore` пускает в сборку только исходники. Пакет публичный, сервер тянет образ без логина.
- Теги образа: `latest` и `<версия>` для релизов (git-тег `v*`), `main` и `sha-<коммит>` для каждого пуша в main.
- GitHub Releases (на тег `v*`): `cctg-<тег>-x86_64-pc-windows-msvc.exe`, `cctg-<тег>-x86_64-unknown-linux-musl`, `cctg-<тег>-aarch64-apple-darwin`, `SHA256SUMS`.
- `deploy/compose.yml`, `deploy/compose.host.yml` и `deploy/hub.env.example` в репозитории: всё, что нужно серверу.

## Один раз в GitHub

После первой публикации образа (первый пуш в main после TASK-035) пакет `cctg` в GHCR приватный. Один раз: GitHub, профиль, Packages, `cctg`, Package settings, Change visibility, Public. Репозиторий публичный, в образе нет секретов.

Тег `latest` появляется только с первым релизом (git-тег `v*`, раздел «Обновление»). Пуш в main публикует `main` и `sha-<полный коммит>`. Пока релиза нет, `docker compose up -d` с `compose.yml` как есть падает с `manifest unknown`. Два выхода: поставить первый тег `v0.1.0` на коммит main с зелёным `ci` и дождаться `release`, или до первого релиза написать в `.env` рядом с `compose.yml` `CCTG_IMAGE_TAG=main` (и убрать после релиза: watchtower следит за тегом, с которым запущен контейнер).

## Один раз на сервере

Всё, что ниже, делает одна команда (TASK-031, `<тег>` это релиз, например `v0.1.0`):

```sh
curl -fsSL https://raw.githubusercontent.com/pockerhead/cctg/<тег>/install.sh | sh -s -- --hub
```

Папка `~/cctg-hub` (другая: `--dir`). Команда спрашивает токен бота (скрытый ввод), id группы, id пользователей, прокси и адрес сервера (или берёт `CCTG_BOT_TOKEN`, `--chat-id`, `--users`, `--proxy`, `--public-host`), делает секрет и сертификат, пишет `hub.env` (600) и `.env` с `COMPOSE_FILE` (с `compose.host.yml`, если прокси на `127.0.0.1` хоста), `CCTG_IMAGE_TAG` (образ того же релиза, что и скрипт) и адресом сервера, запускает hub, ждёт в логе `hub started, polling` (бот, группа и права проверены) и печатает строку установки клиента с адресом, портами из `compose.yml`, pin и секретом. Без терминала адрес сервера обязателен (`--public-host`). Повторный запуск оставляет записанные значения, секрет и сертификат; `compose.yml` в том виде, в каком его записал скрипт, обновляется до версии релиза, а изменённый руками (порты) не перезаписывается, новая версия ложится рядом как `compose.yml.new`. `--hub --uninstall` делает `docker compose down` и убирает compose-файлы, `hub.env`, `tls/` и том остаются. Руками то же самое:

Нужны Docker Engine с плагином compose (2.24 или новее, если нужен `compose.host.yml`) и два открытых наружу TCP-порта (по умолчанию 47291 для агентов и 47292 для хуков, другие номера в разделе «Порты»).

1. Папка и файлы:

   ```sh
   mkdir -p /opt/cctg/tls && cd /opt/cctg
   curl -fsSLO https://raw.githubusercontent.com/pockerhead/cctg/main/deploy/compose.yml
   curl -fsSLO https://raw.githubusercontent.com/pockerhead/cctg/main/deploy/compose.host.yml
   curl -fsSL -o hub.env https://raw.githubusercontent.com/pockerhead/cctg/main/deploy/hub.env.example
   chmod 600 hub.env
   ```

   Заполнить `hub.env`: `CCTG_BOT_TOKEN`, `CCTG_CHAT_ID` (`-100<id>`), `CCTG_ALLOWED_USER_IDS`, `CCTG_HUB_SECRET` (16+ видимых ASCII, длинный случайный, например `openssl rand -hex 32`). Файл остаётся только на сервере.

2. Сертификат. Самоподписанный, на 10 лет, ключ EC P-256:

   ```sh
   openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:prime256v1 -nodes \
     -days 3650 -subj "/CN=cctg-hub" -keyout tls/key.pem -out tls/cert.pem
   chown 10001 tls/key.pem && chmod 600 tls/key.pem
   openssl x509 -in tls/cert.pem -noout -fingerprint -sha256
   ```

   Ключ читает только uid 10001 (пользователь hub в образе); без `chown` hub не стартует с ошибкой «CCTG_TLS_KEY cannot be read as a PEM private key». Последняя команда печатает `sha256 Fingerprint=AB:CD:...`: это pin для устройств, не секрет. Имя в сертификате роли не играет: устройства проверяют ровно эти байты сертификата и подпись рукопожатия его ключом, а не имя и не центр сертификации.

3. Запуск (если Telegram с сервера доступен только через прокси, сначала раздел «Прокси»):

   ```sh
   docker compose up -d
   docker compose ps          # STATUS: healthy
   docker compose logs hub    # "TLS certificate loaded sha256=AB:CD:...", "hub started, polling"
   ```

   Hub пишет pin своего сертификата при каждом старте, его можно сверить с шагом 2.

Healthcheck (`cctg health`) проверяет, что оба порта hub принимают соединения. Он не ходит в Telegram и не отправляет ни байта; hub пишет о таких соединениях только на уровне debug. Порты открываются до первого `getMe`, поэтому «healthy» значит «процесс жив и слушает», а не «Telegram доступен»: это видно по строке «hub started, polling» в логе.

## Порты

Порты hub видны всему интернету, поэтому лучше взять не стандартные номера (меньше шума от сканеров; безопасность держат TLS и секрет, не номер). Пример с 52191 и 52192:

- обычная сеть: в `compose.yml` поменять только левые номера, `"52191:47291"` и `"52192:47292"`; внутри контейнера hub слушает те же 47291/47292, healthcheck не меняется;
- сеть хоста (`compose.host.yml`): в `hub.env` `CCTG_AGENT_LISTEN=0.0.0.0:52191` и `CCTG_HOOK_LISTEN=0.0.0.0:52192` (healthcheck читает те же переменные).

На устройствах те же номера в `CCTG_HUB_AGENT_ADDR` и `CCTG_HUB_HOOK_ADDR`. Если адреса устройств постоянные, firewall сервера может пускать на эти порты только их.

## Прокси

Прокси нужен, только если сервер не достаёт до Bot API напрямую (решение 2 TASK-035: адрес, который отдаёт DNS сервера, не отвечает). Тогда hub ходит в Telegram через HTTP-прокси из своего окружения: `HTTPS_PROXY` (и `HTTP_PROXY`, `ALL_PROXY`, `NO_PROXY`) читает сам клиент Bot API. Без этих переменных hub ходит напрямую. Hub пишет при старте одну строку «Bot API requests go through the proxy of the environment», адрес прокси не пишет никогда (в нём бывают логин и пароль). Агенты и хуки прокси не используют: это входящие соединения к hub, `NO_PROXY` для них не нужен.

- Переменная кладётся в `hub.env`: compose передаёт его в окружение процесса. Файл `.env`, который `cctg hub` читает сам (`--env-file`), для прокси не годится: hub не переносит его значения в окружение.
- Прокси слушает только `127.0.0.1` хоста (так у 3x-ui по умолчанию): контейнер в сети хоста, `docker compose -f compose.yml -f compose.host.yml up -d`, в `hub.env` `HTTPS_PROXY=http://127.0.0.1:10809`. Порты hub тогда открываются прямо на хосте. Все команды `docker compose` дальше с теми же двумя `-f`.
- Прокси слушает и адрес моста Docker (обычно `172.17.0.1`): остаётся обычная сеть, в `hub.env` `HTTPS_PROXY=http://host.docker.internal:10809` (`host.docker.internal` в `compose.yml` уже есть).
- Образы из GHCR тянет демон Docker, а не hub: если и `ghcr.io` недоступен напрямую, прокси задаётся демону (systemd drop-in с `HTTPS_PROXY` для `docker.service`, документация Docker «Daemon proxy configuration»).

## Устройство

`~/.cctg/device.env` каждой машины с сессиями:

```
CCTG_HUB_SECRET=<тот же секрет, что в hub.env>
CCTG_HUB_AGENT_ADDR=hub.example.org:47291
CCTG_HUB_HOOK_ADDR=hub.example.org:47292
CCTG_HUB_CERT_SHA256=AB:CD:...
```

- `CCTG_HUB_CERT_SHA256` включает TLS на обоих каналах. Значение это 64 шестнадцатеричные цифры, с двоеточиями или без, в любом регистре: то, что openssl печатает после `Fingerprint=`. Целую строку openssl тоже можно вставить, но только в кавычках (пробел без кавычек ломает файл, и тогда устройство не видит и секрет). Сломанный pin не откатывается на открытый TCP: хук и агент просто молчат и пишут причину в stderr (у агента это debug-лог claude).
- Без pin устройство говорит открытым TCP и только с loopback (`127.x`, `[::1]`, `localhost`). Адрес другой машины без pin не используется вовсе, секрет в открытом виде по сети не уходит. Имя `localhost` разрешает система, поэтому после соединения устройство ещё раз проверяет, что на том конце loopback, и иначе закрывает соединение, ничего не отправив.
- Адрес может быть именем или IP.
- Хуки над TLS ждут дольше: 900 мс (600 мс для `UserPromptSubmit` и тулов) вместо 500/300. Строка статуса держит свои 80 мс: если до сервера далеко, цифры контекста и лимитов в сообщение статуса не дойдут, строка статуса от этого не тормозит.
- Устройство ставит `install.sh` (README, шаг 3): бинарник своего тега из GitHub Releases, этот `device.env`, `~/.cctg/claude/{mcp.json,settings.json}` и обёртку `claude-cctg`. `~/.cctg/bin/cctg doctor` проверяет оба канала, pin и секрет. Руками: бинарник из GitHub Releases того же тега, что образ на сервере (про версии ниже); на Linux и macOS файл из Releases скачивается без права на запуск: `chmod +x` после каждого скачивания, иначе агент и хуки не стартуют (`Permission denied`); регистрация агента и хуков как в `docs/poc.md`: `cctg agent-install`, `docs/hook-settings.json`.
- macOS (Apple Silicon): файл `cctg-<тег>-aarch64-apple-darwin` не подписан. После скачивания `chmod +x` и `xattr -d com.apple.quarantine <файл>`. Управление консолью claude (⏹, `!`-команды, панели, перезапуск по «Обновить») на Linux и macOS работает, когда claude запущен через `claude-cctg` в терминале (TASK-044, `docs/poc.md`); вложенные `claude -p`, перепривязка агента после `/clear` и уборка сессий на macOS работают по обходу родителей процесса, как на Linux.

## Обновление

Выпуск это git-тег `vX.Y.Z` на main, поставленный на коммит с зелёным `ci`, в котором `install.sh` уже говорит `RELEASE=vX.Y.Z` (иначе `release.yml` ничего не публикует; строки установки в README тоже на новый тег). GitHub Actions (`.github/workflows/release.yml`) собирает образ и бинарники одного коммита, с одним и тем же `CCTG_BUILD_ID`, кладёт образ в GHCR (`latest` и `X.Y.Z`) и создаёт релиз с бинарниками. Никаких секретов, кроме встроенного `GITHUB_TOKEN`, workflow не использует. Серверу ssh от оркестратора не нужен.

На сервере одно из двух:

- автоматически: `docker compose --profile autoupdate up -d` поднимает рядом `nickfedor/watchtower` (поддерживаемый форк заархивированного `containrrr/watchtower`). Он раз в 10 минут проверяет `latest`, трогает только контейнер с меткой `com.centurylinklabs.watchtower.enable=true` (это hub), перезапускает его на новом образе и удаляет старый. Ему нужен `/var/run/docker.sock`, то есть права root на хосте: если это неприемлемо, второй вариант;
- руками или по cron: `docker compose pull && docker compose up -d`.

Hub, поставленный `install.sh --hub`, закреплён на образе своего релиза (`CCTG_IMAGE_TAG` в `.env`): его обновляет команда `--hub` нового тега, `pull` и watchtower тянут только тот же релиз.

Hub останавливается по SIGTERM: дописывает `registry.json` в том и выходит (`stop_grace_period: 30s`). Агенты переподключаются сами, хуки на эти секунды складывают `SessionStart`/`SessionEnd` в спул.

## Смена сертификата

Pin это хеш сертификата, поэтому новый сертификат (истёк срок, утёк ключ) это новый pin на всех устройствах:

1. На сервере шаг 2 заново (новые `tls/cert.pem` и `tls/key.pem`), `docker compose restart hub`, pin из лога или из openssl.
2. На каждом устройстве новый `CCTG_HUB_CERT_SHA256` в `device.env`. Хуки берут его со следующего события. Агенты читают `device.env` только при старте, поэтому уже запущенные сессии claude до hub не достучатся, пока их не перезапустить (`/exit`, потом `claude-cctg --resume <id>`).

До правки устройства молчат (хуки пишут в stderr, что событие не доставлено), небезопасного отката на открытый TCP нет.

## Версии клиента и hub

Сборка определяется коммитом, из которого она собрана, а не байтами файла: `cctg --version` печатает `cctg 0.1.0 (<коммит>)`. Hub в Linux-контейнере и клиент одного коммита на любой ОС считаются одной сборкой. Клиент другого коммита получает в теме одно предупреждение «устарел» с кнопкой «Обновить» (номера обеих сборок в тексте).

- Коммит в сборку кладёт `build.rs`: `CCTG_BUILD_ID` из окружения сборки (CI и Docker передают полный коммит), иначе `git rev-parse HEAD`. Если в `crates/`, `Cargo.toml` или `Cargo.lock` есть незакоммиченные изменения, к коммиту добавляется `-dirty` и хеш исполняемого файла: две разные грязные сборки одного коммита не равны. Без git и без переменной сборкой остаётся sha256 файла, как до TASK-035.
- «Обновить» при hub из релиза (образ тега, TASK-050): агент устаревшей сессии сам скачивает `cctg-<тег hub>-<платформа>` и `SHA256SUMS` того же релиза (`https://github.com/pockerhead/cctg/releases/download/<тег>/`, другая база в `CCTG_RELEASE_BASE_URL` окружения claude, прокси из `HTTPS_PROXY`), сверяет sha256 и ставит файл на место своего так же, как `install.sh` (Windows: работающий `cctg.exe` в `cctg.old.exe`), потом подхватывает его. Если файл на диске уже этот, ничего не качается. Ошибка сети, несовпадение суммы или нет сборки для платформы дают ответ в теме, старая сборка остаётся; если скачать не вышло (сеть, нет файла), а на месте файла уже лежит другая сборка (поставленная руками или `install.sh`), агент берёт её. Прокси только из переменных окружения claude (`HTTPS_PROXY`, `ALL_PROXY`, `NO_PROXY`): системный прокси Windows и macOS не читается. «Обновить» ставит ровно сборку hub, а не самую новую: клиент более новой сборки (dev-сборка с main, `--from-source`) при hub из релиза тоже считается устаревшим и по кнопке вернётся на сборку hub. Hub без тега (локальная сборка, образ `:main`) ничего не предлагает скачать: агент берёт новый файл, только если он лежит на месте старого. Порядок тогда: команда установки нового тега (`.../<новый тег>/install.sh`) кладёт бинарник на место старого (работающий `cctg.exe` в Windows переименовывается в `cctg.old.exe`, в Linux и macOS файл получает `chmod` и заменяет старый через `mv`), потом «Обновить» в теме. Руками: скачать бинарник нужного тега из Releases; на Windows переименовать работающий `cctg.exe` (Windows разрешает переименовать запущенный exe) и положить новый под старым именем, на Linux и macOS `chmod +x` новому файлу и заменить им старый (`mv` поверх старого); нажать «Обновить». Если нового файла нет, тема получает подсказку, что делать.
- После первой выкатки TASK-035 старые клиенты (сборка = хеш файла) один раз получат «устарел»: это ожидаемо.

## Hub на своей машине с TLS

Тот же hub без Docker тоже умеет TLS: `CCTG_TLS_CERT` и `CCTG_TLS_KEY` в `.env` (оба или ни одного), `CCTG_AGENT_LISTEN`/`CCTG_HOOK_LISTEN` на нужном адресе. Открытый TCP на не-loopback адресе hub по-прежнему разрешает с предупреждением в логе, но устройства туда без pin не пойдут.

## Защита до секрета

Порты открыты всему интернету, поэтому до проверки секрета hub держит соединения коротко:

- агент: одно окно 5 с от TCP-соединения на рукопожатие TLS, `hello` и `register`; первая строка до проверки секрета не длиннее 4 КиБ; одновременно не больше 16 соединений без секрета и не больше 4 из них с одного IP, лишнее закрывается сразу;
- хук: одно окно 2 с от TCP-соединения на рукопожатие TLS и весь запрос; заголовки до проверки секрета не длиннее 8 КиБ, тело читается только после; одновременно не больше 64 запросов и не больше 16 недочитанных с одного IP;
- неверный секрет: сравнение за постоянное время, ответ (у агента `rejected`, у хука 401) только через 250 мс, в логе строка с адресом пира без значения секрета;
- неудачное рукопожатие TLS и соединение без единого байта (сканеры, healthcheck) пишутся только на уровне debug;
- прочие отказы до секрета (неверный секрет, мусор, чужая версия протокола, таймаут) дают не больше одного warning в минуту с одного IP, остальные строки идут на уровне debug.

Остаток: адресов у сканеров много, и 4 источника могут занять все 16 мест агентов; настоящие устройства тогда переподключаются с паузой до 30 с. От этого firewall со списком адресов устройств или нестандартный порт. Устройства за одним NAT делят свои 4 места, но место держится только на время рукопожатия, поэтому это заметно только при одновременном переподключении многих сессий (после рестарта hub), и отказанные повторяют попытку сами.

## Проверка без Telegram

Сертификат, pin и оба канала покрывает `crates/cctg/tests/tls_e2e.rs` (настоящие процессы hub, hook и agent, фейковый Bot API), прокси `crates/cctg/tests/proxy_e2e.rs` (заглушка прокси: `CONNECT` к `.invalid`-хосту и запросы в абсолютной форме, пароль прокси в вывод не попадает). Образ в CI (`.github/workflows/ci.yml`, задача `image`) собирается и проходит `.github/smoke/smoke.py`: compose с фейковым Bot API, healthcheck, хук и агент по TLS с клиентом того же коммита, отсутствие секретов в образе и логах, остановка по SIGTERM.

## Ограничения

- Образ только x86_64. Клиенты: Windows x86_64, Linux x86_64, macOS arm64.
- Смена сертификата требует правки всех устройств и перезапуска их сессий (раздел выше).
- Все устройства знают один общий секрет hub; секреты по устройствам это TASK-045.
